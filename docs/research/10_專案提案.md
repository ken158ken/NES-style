# 10 專案提案：3 個原創遊戲方案

## 摘要（10 行內）
1. 本文件依 `01`～`09` 的研究結論，提出 **3 個 100% 原創 IP** 的遊戲方案，全部符合文件 09 的 R0/R1 風險等級。[推論]
2. **提案 A《波形迴路 WAVEFORM》**：瀏覽器假復古（NES 規格自律），**直接重用 `../卡比之星` 的引擎與工具鏈**；主角是取樣機器人，把敵人「錄成波形」當武器。[推論]
3. **提案 B《節拍要塞 BEATFORT》**：**真 NES ROM**（cc65 + neslib + FamiStudio）；單畫面節奏防衛動作，敵人隨 BPM 行動 —— 單畫面 = 不用捲動，是第一支 ROM 的最佳題材。[推論]
4. **提案 C《迴聲塔 ECHO TOWER》**：**真 GBC ROM**（GBDK-2020 或 GB Studio）；黑暗塔內用「聲納回聲」照亮視野，把 160×144 的小視野變成設計資產。[推論]
5. 三案共用同一套原創原則：程式繪製像素、程式合成音樂、無任何第三方素材。[推論]
6. 三案都內建「決定性推進 + headless 截圖」的自動化測試路徑（文件 08 第 8 節）。[推論]
7. **推薦順序：A → B → C**。理由：A 可在 4 週內產出可玩版本且零工具鏈風險；B 是「真紅白機」的正統里程碑；C 風險最低但對本專案主題（紅白機）最不直接。[推論]
8. 提案 A 的關鍵價值：`../卡比之星` 已有約 41,000 行 JS 引擎、Playwright 截圖、自動通關機器人、39 項引擎測試 —— **換皮即可上線**。[源]
9. 提案 B 的關鍵風險：6502 / cc65 的學習曲線與「讀 RAM 位址做斷言」的自動化摩擦（文件 08 第 8.5 節）。[推論]
10. 三案的內容規模都刻意壓在「4 週可玩、8 週完整、12 週打磨」的節奏，避免做不完。[推論]

### 1.1 一句話概念
> **你是一台會「取樣」的小型合成器機器人，把敵人錄成波形，再把兩種波形疊加成新武器，一路打進失控的音訊迴路核心。**

## 2. 提案 B《節拍要塞 BEATFORT》

### 2.1 一句話概念
> **在一座單畫面的音訊要塞裡，敵人只在節拍上移動；你要在同一個 BPM 上出手，用四種聲道武器守住核心。**

### 2.2 類型與參考骨架
| 項目 | 內容 | 標註 |
|---|---|---|
| 類型 | 單畫面動作 + 節奏同步 + 波次防衛 | [推論] |
| 參考骨架（機制層，R1） | 「單畫面 arena 波次」骨架（如 8-bit 時代的單畫面射擊 / 防衛遊戲） | [推論] |
| 原創差異化 | 敵人行動與音樂 **同一個 frame counter**：BPM 140 @ 60fps ⇒ 每拍約 25.7 幀；玩家在拍點 ±4 幀內出手有「Perfect」加成 | [推論] |
| 為何適合 NES | **單畫面 = 不需要捲動**，省掉 NES 開發最難的部分（nametable 更新、attribute 更新、sprite 0 split）；且音樂驅動與遊戲邏輯同在 NMI，天生同步 | [推論]（NES 捲動難度見文件 01 [源]） |

### 2.3 目標平台與路線
| 項目 | 內容 | 標註 |
|---|---|---|
| 路線 | **路線 2：真 NES ROM** | [推論] |
| 工具鏈 | **cc65 / ca65 / ld65 + neslib**（依 nesdoug 教學模板） | [源] |
| 圖形 | **NEXXT**（CHR / nametable / metasprite / 調色盤） | [推論] |
| 音樂 | **FamiStudio** → 匯出 FamiStudio Sound Engine 組語（支援 2A03 前 4 聲道、96 音、占空比 / 音量 / 音高 / 琶音包絡） | [源] |
| 除錯 | **Mesen 2 / MesenCE**（Lua 腳本、Trace Logger、全記憶體存取、截圖回傳 PNG 字串） | [源] |
| 自動化 | Mesen 或 FCEUX Lua：`emu.frameadvance()` + `joypad.set()` + 截圖 + `memory.readbyterange()` 斷言；`xvfb-run` 做 headless | [源]（API [源]、xvfb [推論]） |
| mapper | 起步用 **NROM（32 KB PRG + 8 KB CHR）**；若容量不足升 UNROM / MMC1 | [推論] |
| 產物 | `.nes`（含有效 iNES 標頭）；可燒 mapper 30 卡帶或走 EverDrive | [源] |

### 2.4 核心迴圈
```
波次開始（BGM 起拍）
   ↓
敵人沿格線「跳」向核心（每拍移動 1 格，行為原型：巡邏 / 追蹤 / 射擊 / 產生器）
   ↓
玩家在 4 個聲道武器間切換（方波 / 方波 2 / 三角 / 雜訊），各有射程與冷卻
   ↓
在拍點 ±4 幀出手 → Perfect（傷害 ×2、加能量）；離拍 → 普通；連續 Perfect → 連段倍率
   ↓
波次清空 → 短暫喘息（文件 04 的鋸齒難度曲線）→ BPM +4 → 下一波
   ↓
每 5 波一個魔王（有可讀的攻擊模式循環 + 預警幀 + 弱點窗口）
```
| 迴圈層級 | 長度 | 標註 |
|---|---|---|
| 微 | 1 拍（約 0.43 秒 @ 140 BPM） | [推論] |
| 中 | 1 波 30～60 秒 | [推論] |
| 大 | 1 場 = 15 波 + 3 魔王，約 12～15 分鐘 | [推論] |
| 長期 | 高分榜（密碼制或電池 SRAM）、難度模式、新武器解鎖 | [推論] |

### 2.5 技術規格
| 項目 | 規格 | 標註 |
|---|---|---|
| 解析度 | 256×240 輸出，安全區 **256×224** | [源]（文件 01） |
| 畫面配置 | 遊戲格線 12×10 格（每格 16×16 像素 = 192×160），四周留框；HUD 在上方 32px | [推論] |
| 調色盤 | 背景 4 組 × 3 色 + 共用底色；精靈 4 組 × 3 色（電子風：青 / 洋紅 / 黃 / 白 為主） | [源] |
| 屬性格 | 背景以 16×16 為配色單位（格線設計剛好對齊，等於免費避開屬性衝突） | [源]（限制 [源]、設計解法 [推論]） |

## 3. 提案 C《迴聲塔 ECHO TOWER》

### 3.1 一句話概念
> **一座漆黑的塔裡，你只能靠「發出聲音、聽回聲」看見周圍；但發聲會引來塔中的東西。**

### 3.2 類型與參考骨架
| 項目 | 內容 | 標註 |
|---|---|---|
| 類型 | 俯視探索 + 解謎 + 輕度潛行 | [推論] |
| 參考骨架（機制層，R1） | 「俯視地城探索 + 鑰匙 / 門 / 道具解鎖」骨架 | [推論] |
| 原創差異化 | **視野即資源**：畫面預設近乎全黑，按 A 發出「脈衝」→ 以波紋形式逐格點亮周圍 3～5 格，數秒後熄滅；發聲會讓敵人往聲源移動 ⇒ 「看清楚」與「被發現」是同一個按鍵的代價 | [推論] |
| 為何適合 GB / GBC | 160×144 只看得到 10×9 格（16px 格），**小視野本來是缺點，這裡變成核心機制**；而且「黑底 + 少數亮格」的畫面在 4 階灰 / 4 色調色盤下最好看、最省磁磚 | [源]（視野換算見文件 07）／[推論] |

### 3.3 目標平台與路線
| 項目 | 內容 | 標註 |
|---|---|---|
| 路線 | **路線 3：真 GB / GBC ROM** | [推論] |
| 主選項 | **GBDK-2020**（C 語言，lcc 驅動 SDCC）；目標 `gbc`，同一份程式碼也能出 Analogue Pocket 版 | [源] |
| 備選 | **GB Studio 4**（無程式碼、可同時輸出 ROM 與網頁版、有 Color Only 模式與內建除錯器）——若 4 週內想先看到成果，可先用它做原型 | [源] |
| 音樂 | **hUGETracker + hUGEDriver**（public domain，GBDK 官方推薦，可匯出 `.c` 給 GBDK 用；也內建於 GB Studio） | [源] |

| 自動化 | mGBA Lua：`emu:runFrame()` / `emu:setKeys()` / `emu:screenshot()` / `emu:readRange()`；`xvfb-run` headless | [源] |
| ROM | 目標 ≤ 256 KB（MBC5 + 電池 SRAM 存檔）；GBC 上限 8 MB 綽綽有餘 | [源] |
| 產物 | `.gbc`（GBC 專用）+ GB Studio 路線可另出網頁版 | [源] |

### 3.4 核心迴圈
```
進入黑暗房間
   ↓
按 A 發「脈衝」 → 波紋逐格點亮（3~5 格半徑，持續約 3 秒後衰減）
   ↓
記住地形（玩家腦中的地圖，也可按 SELECT 看已探索的粗略地圖）
   ↓
移動 / 撿物 / 解機關                    敵人聽見聲音 → 往聲源移動
   ↓                                        ↓
找到樓梯 → 上一層（BPM / 音階上升一階）   被抓到 → 掉一層或損失一個「電池」
   ↓
每 5 層一個「守門者」（靠聲音判位的魔王，弱點是讓它自己撞牆）
```
| 迴圈層級 | 長度 | 標註 |
|---|---|---|
| 微 | 一次脈衝約 3 秒 | [推論] |
| 中 | 一層 2～4 分鐘（符合掌機短時段遊玩，文件 07 第 11.4 節） | [源]／[推論] |
| 大 | 5 層一章，約 15 分鐘 | [推論] |
| 長期 | 塔共 20 層 + 收集要素；電池 SRAM 隨時存檔 | [推論] |

## 5. 推薦順序與理由

### 🥇 第一順位：**提案 A《波形迴路 WAVEFORM》**（瀏覽器假復古 + 重用 `../卡比之星` 引擎）

| 理由 | 說明 | 標註 |
|---|---|---|
| **成本最低、確定性最高** | 41,000 行引擎、Playwright 截圖、自動通關機器人、39 項引擎測試、關卡靜態檢查、單檔打包 —— **全部現成** | [源] |
| **AI agent 效率最高** | 「改一行 → 截圖 → Read 看圖」的迴圈只要幾十秒；ROM 路線每輪要編譯 + 啟模擬器 + 讀 RAM 位址 | [推論]（對比見文件 08 第 8.5 節） |
| **法律最乾淨** | 換皮只需改美術與名稱，程式碼 0 改動即可從 R3（同人）降到 R1（機制致敬） | [推論]（文件 09 第 9.1 節） |
| **主題最貼合** | 「電子音樂 × 像素風」正是本專案 README 的目標；波形能力直接把音樂變成玩法 | [源]（README） |
| **可展示** | 一個網址就能給人玩，不需要教對方裝模擬器 | [推論] |
| **可升級** | 若資料格式（關卡 JSON、精靈字串、音序表）從一開始就中性化，未來能寫轉檔器移植成真 ROM | [推論] |

> **唯一要嚴防的事**：別讓它看起來還是卡比。第 1 週就要通過剪影測試與三特徵測試，
> 並且**把 NES 自律寫成 `nes_lint.py`**，否則「假復古」會變成「只是像素風」。[推論]

### 🥈 第二順位：**提案 B《節拍要塞 BEATFORT》**（真 NES ROM）

| 理由 | 說明 | 標註 |
|---|---|---|
| 本專案的「正統終點」 | 專案名叫「紅白機遊戲開發」，做出一支真的 `.nes` 才算完成閉環 | [推論] |
| 題材選得好 | **單畫面 = 不用捲動**，直接迴避 NES 開發最難的部分；格線配色天然對齊 16×16 屬性格 | [推論]（限制 [源]） |
| 技術成長最大 | 6502、PPU 時序、VBlank 預算、mapper、FamiStudio 驅動 —— 全是無可取代的經驗 | [推論] |
| 建議時機 | **在 A 完成 8 週版之後**，或與 A 並行由另一條時間線進行（每週固定投入 1 天） | [推論] |
| 降風險方案 | 若 6502 卡關超過 2 週，改用 **NESmaker**（US$36）先產出可玩版，再回頭學 cc65 | [源]（定價 [源]） |

### 🥉 第三順位：**提案 C《迴聲塔 ECHO TOWER》**（真 GBC ROM）

| 理由 | 說明 | 標註 |
|---|---|---|
| 機制最原創、最不像任何既有作品 | 「發聲照明 vs 引來敵人」是單一按鍵承載正負後果的乾淨設計 | [推論] |
| 工具鏈風險低於 NES | GBDK-2020 Linux tarball 解壓即用；GB Studio 可做極速原型；hUGEDriver 為 public domain | [源] |
| 但主題偏離 | 專案定位是紅白機，GBC 屬於延伸；建議作為「A 或 B 完成後的第二作」 | [推論] |
| 額外好處 | GBDK-2020 同時支援 **NES 目標**，所以 C 的程式碼經驗可部分轉移到 NES | [源] |

### 5.1 建議的 12 週執行方案（綜合）
| 週 | 主線（80% 時間） | 副線（20% 時間） | 標註 |
|---|---|---|---|
| W1-4 | **A**：換皮 + 第 1 區 + 可玩 Demo | 讀 nesdoug 教學、裝 cc65 / Mesen、跑通 Hello NES | [推論] |
| W5-8 | **A**：完整版（4 區 4 魔王 8 曲） | **B**：專案骨架 + 節拍移動原型 | [推論] |
| W9-12 | **A**：打磨 + 發佈 | **B**：5 波可玩 Demo | [推論] |
| 之後 | **B** 轉主線（12 週完整版） | **C** 用 GB Studio 做 1 週原型驗證「黑暗 + 脈衝」好不好玩 | [推論] |

> 這個安排讓「一定做得完的 A」保證有產出，同時用低強度副線把 B 的學習曲線攤平到 8 週，
> 避免「一開始就啃 6502，四週後什麼都沒有」的常見失敗模式。[推論]
