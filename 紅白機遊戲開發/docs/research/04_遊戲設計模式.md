# 04 遊戲設計模式（關卡 / 敵人 / 魔王 / 道具 / 難度 / 手感 / UI / 存檔）

## 摘要（10 行內）

1. 8 位元時代的關卡設計普遍可用「起承轉合（Kishōtenketsu）」四段結構解讀：安全教學 → 變化 → 翻轉 → 收尾，這是任天堂內部明說過的方法論 [源]。
2. 《超級瑪利歐兄弟》World 1-1 是「不用文字教學」的典範；栗寶寶（Goomba）甚至是為了讓第一隻敵人夠好懂而發明的 [源]。
3. 敵人設計可歸納成六個行為原型（巡邏 / 追蹤 / 射擊 / 跳躍 / 飛行 / 產生器），關卡難度多半來自「組合」而非單體強度 [推論]。
4. 魔王設計的核心是「可讀的模式循環 + 預警幀 + 弱點窗口」；《洛克人》的弱點鏈明言取自剪刀石頭布 [源]。
5. 難度曲線應為鋸齒狀（緊張—放鬆交替）而非直線，理論根源是 Csikszentmihalyi 的心流通道 [源]。
6. 手感（Game Feel）的關鍵在「可變跳躍高度 + 子像素 + 打擊停頓 + 畫面震動 + 無敵閃爍」；NES 時代已有 16 子像素與按住 A 減重力的實作 [源]。
7. Coyote time / 輸入緩衝在 8 位元時代多以「狀態機容忍幀」的形式存在，現代建議值為 5~8 幀與 6~9 幀 [源]。
8. 存檔分三路：電池 SRAM（《薩爾達傳說》為 NES 首例）、密碼（《銀河戰士》24 字元 / 8 bit 校驗和）、續關次數 [源]。
9. 作弊碼文化源自 Konami Code（橋本和久為《宇宙巡航機》NES 版除錯用，忘了拿掉）[源]。
10. 文末附「原創遊戲設計檢查表 30 條」，可直接當開發驗收清單 [推論]。

## ① 關卡設計模式

### 1.1 起承轉合（Kishōtenketsu）

《超級瑪利歐 3D 大陸》/《3D 世界》總監林田宏一（Koichi Hayashida）公開表示，他的關卡設計建立在日本四格漫畫與漢詩的「起承轉合」四段結構上，而這個想法可追溯到宮本茂畫漫畫的經歷 [源]。

| 段 | 日文 | 關卡功能 | 玩家情緒 | 典型長度 |
|---|---|---|---|---|
| 起（Ki） | 起 | 在**零風險**環境介紹新機制（單一元素、可失敗不致死） | 「這是什麼？」 | 10~20% |
| 承（Shō） | 承 | 同一機制加量、加速、加高度差 | 「我會了」 | 25~35% |
| 轉（Ten） | 転 | 把機制**翻轉**：與既有元素組合、反轉規則、換視角 | 「原來還能這樣！」 | 25~35% |
| 結（Ketsu） | 結 | 綜合考驗 + 收尾獎勵（旗桿 / 出口 / 寶箱） | 「我掌握了」 | 15~25% |

- 關鍵在於「一個關卡只教一個想法，教完就丟掉」，整段流程約 3~5 分鐘 [源]。
- [推論] 8 位元橫向捲軸關卡（單向推進、無存檔點）特別適合這個結構，因為玩家沒有回頭複習的成本，設計者必須在同一條路徑上完成教學。

### 1.2 安全教學區（Safe Tutorial Space）

《超級瑪利歐兄弟》World 1-1 的開場是公認的教科書：先給一段空地與一隻敵人，中段才出現水管與坑洞，把敵人群與階梯留到最後 [源]。宮本茂說他們「不斷模擬玩家會做什麼」，要讓玩家「自然而然地理解自己在做什麼」[源]。第一隻敵人原本要用慢慢龜（Koopa Troopa），但「踩 + 踢」兩段動作對開場太難教，於是發明了一踩就扁的栗寶寶 [源]。

安全教學區的具體做法 [推論，整理自上述案例]：

| 手法 | 說明 | NES 實例 |
|---|---|---|
| 無坑洞地板 | 失敗只會被扣血不會即死 | SMB 1-1 前段 |
| 單一變數 | 畫面上只有一種新元素 | SMB 1-1 的第一隻栗寶寶 |
| 強制遭遇 | 新機制放在唯一通路上，不可繞過 | SMB 1-1 的第一個問號磚 |
| 視覺引導 | 用地形 / 金幣排列把視線帶到重點 | SMB 金幣拱形指向磚塊 |
| 無時間壓力 | 教學段的計時器寬鬆 | SMB 400 秒 |

### 1.3 風險回報分支（Risk / Reward Branch）

| 模式 | 結構 | 設計要點 |
|---|---|---|
| 高路 / 低路 | 高處路徑較短、獎勵多、失手即死；低處安全但慢 | 高低差要在同一畫面內同時可見 [推論] |
| 貪心走廊 | 一排金幣延伸到危險區 | 用「可見的誘餌」誘導越線 [推論] |
| 單向門 | 進入後無法回頭的獎勵房 | 必須讓玩家事前判斷 [推論] |
| 敵人上方通道 | 踩敵人連跳才能到達 | 把技巧練習變成獎勵 [推論] |

[推論] 風險回報分支的黃金比例：獎勵價值 ≈ 失敗成本 × 1.5。8 位元遊戲常以「1UP / 大量分數 / 隱藏道具」當高風險路徑的獎品。

### 1.4 祕密牆與隱藏房

| 類型 | 提示方式 | 代表 |
|---|---|---|
| 可炸開的牆 | 地形紋理微妙差異、房間格局不對稱 | 《薩爾達傳說》《銀河戰士》 |
| 可燒的樹叢 | 與周圍植被同形但獨立擺放 | 《薩爾達傳說》 |
| 藏磚（隱形磚塊） | 上方有無法到達的金幣 / 道具 | 《超級瑪利歐兄弟》 |
| 假地板 / 假牆 | 走進去即穿過 | 《銀河戰士》 |
| 藏管 / 傳送門 | 需特殊輸入（蹲下） | SMB 的 Warp Zone |

《薩爾達傳說》把「可燒樹叢 / 可炸牆」變成主要探索語彙；GMTK 的 Boss Keys 系列以「依賴圖（dependency graph）」把這種鎖鑰關係視覺化，成為分析非線性關卡的通用方法 [源]。

設計守則 [推論]：
1. 祕密要「可被推理」而非「只能暴力測試」——至少要有一個異常訊號（構圖不對稱、多餘空間、音效差異）。
2. 每個祕密要有「近失（near miss）」設計：玩家經過時會覺得「這裡怪怪的」。
3. 祕密的報酬不該是通關必需品（除非給了足夠提示），否則變成卡關。

### 1.5 檢查點、命數與續關經濟

| 制度 | 典型參數 | 效果 |
|---|---|---|
| 無檢查點 | 死亡回關卡起點 | 壓力最大，關卡必須短（2~4 分鐘）[推論] |
| 單一中點檢查點 | 關卡中段 | 主流；把關卡切成兩個可容忍的段落 [推論] |
| 房間即檢查點 | 每房重生 | 現代做法，適合高死亡率設計 [推論] |
| 命數（Lives） | 起始 3，100 分 / 金幣給 1UP | 來自街機投幣制的遺產 [推論] |
| 續關（Continue） | 有限 3 次 / 無限 / 需密碼 | 有限續關是 8 位元難度的主要來源之一 [推論] |

[推論] 現代原創作品建議：保留「命數」的**視覺與音效儀式**（1UP 音效很有價值），但把實際懲罰降到「回到房間起點」，避免玩家因重複前段內容而流失。

### 1.6 關卡長度與節奏曲線

| 類型 | 建議長度 | 節奏 |
|---|---|---|
| 教學關 | 60~120 秒 | 全程低張力 |
| 標準關 | 150~240 秒 | 3~4 個張力峰 |
| 魔王前關 | 180~300 秒 | 峰值逐漸抬高，結尾留 10 秒回血區 |
| 魔王戰 | 60~180 秒 | 單一高原 |

節奏理論：好的難度曲線「從來不是直線」，而是鋸齒狀的緊張—放鬆交替；理論根源是心流通道（challenge 與 skill 同步成長，過高焦慮、過低無聊）[源]。分形式作法是「下一關的開頭比上一關的結尾容易」，整體仍向上 [源]。

### 1.7 自動捲動關卡（Auto-scroll）

| 設計要點 | 說明 |
|---|---|
| 捲動速度 | 略慢於玩家最高移動速度，讓玩家能超前也能落後 [推論] |
| 擠壓死亡 | 被畫面邊緣推入牆壁即死 → 必須給玩家清楚的邊界提示 [推論] |
| 節奏強制 | 自動捲動把「玩家自訂節奏」換成「設計者指定節奏」，適合搭配音樂 [推論] |
| 使用頻率 | 一款遊戲 1~2 關為宜；過多會讓玩家失去主導感 [推論] |

[推論] 電子音樂像素遊戲特別適合自動捲動段：捲動速率可鎖定 BPM，讓障礙物落在拍點上。

### 1.8 垂直房與垂直捲動

| 模式 | 特徵 | 注意事項 |
|---|---|---|
| 垂直上升 | 平台往上堆疊，鏡頭跟隨最高點 | 下方畫面外要判定為死亡或安全，需明確 [推論] |
| 垂直下降 | 往下跳，落點在畫面外 | 必須提供「先看後跳」手段（下壓看下方 / 落點提示）[推論] |
| 塔型房 | 單房內上下捲動 | NES 上以雙 nametable 垂直鏡像實作 [推論] |

[推論] NES 的 nametable 鏡像方式（水平 / 垂直）直接決定遊戲能平順捲動的方向；規劃關卡拓樸前必須先定卡帶的鏡像設定。

## ② 敵人設計

### 2.1 行為原型分類

| 原型 | 行為 | CPU / 記憶體成本 | 教學價值 | 典型變體 |
|---|---|---|---|---|
| 巡邏（Patroller） | 定速直線移動，碰壁轉向 | 極低 | 教「踩 / 閃」 | 會掉落 / 不掉落邊緣 |
| 追蹤（Chaser） | 朝玩家方向移動 | 低 | 教「走位」 | 有加速 / 有冷卻 |
| 射擊（Shooter） | 固定或瞄準射擊 | 中 | 教「掩體與節奏」 | 定時 / 視線觸發 / 扇形彈 |
| 跳躍（Jumper） | 週期性拋物線 | 低 | 教「時機」 | 固定週期 / 瞄準玩家 |
| 飛行（Flyer） | 正弦波 / 盤旋 / 俯衝 | 中 | 教「高度控制」 | 可被打斷路徑 |
| 產生器（Spawner） | 定時產生小怪，本體可破壞 | 中 | 教「優先目標」 | 有上限 / 無上限 |

[推論] 六原型足以支撐一款完整 8 位元動作遊戲；把資源花在「同一原型的參數變體 + 換皮」比新增原型划算得多（程式碼重用，CHR 也能共用部分磁磚）。

### 2.2 敵人組合作為謎題

| 組合 | 產生的問題 | 玩家必須學會 |
|---|---|---|
| 巡邏 + 窄平台 | 沒有閃避空間 | 精準跳躍時機 |
| 射擊 + 巡邏 | 閃子彈時會撞到巡邏兵 | 兩個節奏的最小公倍數 |
| 飛行 + 坑洞 | 空中被撞＝墜落 | 跳躍前先清場 |
| 產生器 + 有限空間 | 不處理本體就會被淹沒 | 目標優先序 |
| 跳躍 + 移動平台 | 兩個週期疊加 | 觀察與等待 |

[推論] 「敵人配置即謎題」是 8 位元關卡設計的核心：敵人本身弱，但**擺放位置**決定難度。設計時應先畫地形，再問「這裡最討厭的擺法是什麼」，然後往回退一級。

### 2.3 生成 / 復活規則

| 規則 | 說明 | 影響 |
|---|---|---|
| 畫面外即消失 | 敵人離開畫面就回收 | 省記憶體；但玩家可用「退一步再回來」刷新 [推論] |
| 捲動觸發生成 | 敵人在畫面邊緣進入時生成 | 最常見的 NES 作法 [推論] |
| 一次性旗標 | 擊殺後在本次進入不再生成 | 適合掉寶敵人，防刷 [推論] |
| 同屏上限 | 同時最多 N 隻（常見 3~6） | 直接受「每掃描線 8 精靈」限制驅動 [源: NES 硬體限制] |
| 房間重置 | 離開房間再回來全部復活 | 《銀河戰士》式探索遊戲的標準 [推論] |

NES 的硬體事實：PPU 最多 64 個精靈，且**每條掃描線只顯示 8 個**，超出者被丟棄 [源]。因此敵人同屏數量不是美術決定，是硬體決定。

### 2.4 敵人的「教學」順序

[推論] 建議的敵人引入節奏（以 8~10 關的遊戲為例）：

| 關卡 | 新敵人 | 引入方式 |
|---|---|---|
| 1 | 巡邏 | 安全地板單隻 |
| 1 後段 | 巡邏 ×3 | 密度提升 |
| 2 | 跳躍 | 單隻、可繞過 |
| 2 後段 | 巡邏 + 跳躍 | 首次組合 |
| 3 | 射擊 | 給掩體 |
| 4 | 飛行 | 在無坑洞區 |
| 5 | 飛行 + 坑洞 | 首次致命組合 |
| 6 | 產生器 | 單獨房間 |
| 7+ | 全組合 | 不再新增原型，只調參數 |

守則：**新敵人第一次出現時，畫面上不能有其他威脅**；第二次出現才允許組合 [推論，與 SMB 1-1 的教學法一致 [源]]。

## ③ 魔王設計

### 3.1 模式循環（Pattern Loop）

| 元素 | 建議值 | 理由 |
|---|---|---|
| 模式數量 | 2~4 個 | 少於 2 太單調，多於 4 玩家記不住 [推論] |
| 單一循環長度 | 6~12 秒 | 玩家能在 2~3 次死亡內背起來 [推論] |
| 隨機性 | 只在「選哪個模式」上隨機，模式內部固定 | 保留意外感但可學習 [推論] |
| 連續同模式 | 最多 2 次 | 避免運氣爆死 [推論] |

### 3.2 可讀性與預警幀（Tell / Wind-up）

| 預警手段 | 幀數建議（60fps） | 說明 |
|---|---|---|
| 姿勢變化 | 12~20 幀 | 攻擊前的蓄力姿勢，是最重要的一項 [推論] |
| 顏色閃爍 | 8~16 幀 | NES 上成本最低（換調色盤即可）[推論] |
| 音效前置 | 提前 10~15 幀 | 聲音比畫面更早被察覺 [推論] |
| 位置提示 | 攻擊落點先出現標記 | 適合範圍攻擊 [推論] |

[推論] 8 位元硬體上最划算的預警是「調色盤閃爍 + 音效」，因為完全不需要新增 CHR 磁磚。

### 3.3 弱點窗口（Vulnerability Window）

| 設計 | 說明 |
|---|---|
| 攻擊後硬直 | 魔王攻擊結束後 30~60 幀可被打 [推論] |
| 部位弱點 | 只有特定部位可造成傷害（眼睛 / 核心） |
| 狀態弱點 | 需先破壞護盾 / 使其暈眩 |
| 屬性弱點 | 特定武器傷害倍增 |

《洛克人》的屬性弱點鏈明白取自剪刀石頭布：共同開發者稻船敬二在 2003 年 G4 訪談說「世上沒有東西是絕對最強的……就像剪刀贏紙但輸給石頭」；例如古斯人的超級手臂（丟石頭）剋切割人的迴力刀 [源]。

[推論] 弱點鏈的設計價值：
1. 讓「打敗順序」本身成為玩家要解的謎題（非線性選關 + 隱藏最佳路線）。
2. 讓玩家的每次勝利立刻轉換成下一場的優勢，形成正向循環。
3. 但必須確保「用基礎武器也能打贏所有魔王」，否則會死鎖。

### 3.4 多階段（Phase）

| 階段轉換觸發 | 玩家感受 |
|---|---|
| 血量 50% / 25% | 最常見，可預期 |
| 時間經過 | 製造壓迫感 |
| 特定部位被破壞 | 獎勵針對性打法 |
| 競技場改變（地板塌陷） | 重新學習空間 |

[推論] 8 位元魔王建議 2 階段為主；第二階段應「加速既有模式 + 新增 1 個模式」，而不是整套換掉——換掉等於重新教學，違反血量已低的壓力節奏。

### 3.5 競技場（Arena）設計

| 型態 | 適合的魔王 | 注意 |
|---|---|---|
| 平坦封閉房 | 地面型、跳躍型 | 最易讀；預設選擇 |
| 雙層平台 | 飛行型 | 給玩家高度選擇 |
| 有坑洞 | 擊退型 | 難度暴增，慎用 |
| 垂直捲動 | 攀爬型 | 鏡頭規則要極明確 |
| 輸送帶 / 強制移動 | 靜止型 | 讓靜態魔王產生張力 |

守則 [推論]：競技場的長寬應該讓玩家「能跑到最遠角落閃過任何一次攻擊」，但「不能永遠待在角落」。常見手法是讓某個模式專打角落。

### 3.6 魔王衝刺（Boss Rush）

| 設計項 | 建議 |
|---|---|
| 位置 | 最終關中段，通關前的回顧 |
| 順序 | 固定或玩家自選（自選＝讓玩家用最佳武器規劃）[推論] |
| 補給 | 每場之間給小量補血；不給則難度過高 [推論] |
| 縮短版 | 血量降至 70~80%，模式不變 [推論] |
| 敘事功能 | 讓玩家感受到自己變強了（同樣的魔王現在很好打）[推論] |

## ④ 道具與成長

### 4.1 能力取得節奏

| 節奏 | 說明 | 適合類型 |
|---|---|---|
| 線性發放 | 每 1~2 關給一個新能力 | 關卡制動作遊戲 |
| 探索取得 | 能力藏在地圖中，取得後解鎖新區域 | 銀河城（Metroidvania） |
| 選關取得 | 打敗魔王取得其武器 | 洛克人式 |
| 消耗品 | 每次撿到只能用一段時間 | 瑪利歐式 |

銀河城的核心是「鎖與鑰」：某個點在取得特定能力前無法通過，GMTK 用依賴圖分析整個遊戲的鎖鑰關係 [源]。

[推論] 能力發放的經驗法則：
- 前 25% 的遊戲時間內要給出 2~3 個能力，讓玩家建立「會持續變強」的預期。
- 每個能力至少要有一個「回頭可用」的舊區域（讓玩家感到世界變大）。
- 最後 20% 不再給新能力，只給數值 / 純獎勵，避免臨門學新操作。

### 4.2 暫時強化 vs. 永久強化

| 類型 | 例 | 設計效果 | 風險 |
|---|---|---|---|
| 暫時（有時限） | 無敵星、狂暴 | 製造爆發高潮；可安排在難點前 | 玩家會囤積不用 [推論] |
| 暫時（有次數） | 有限彈藥的特殊武器 | 資源管理趣味 | 玩家捨不得用 [推論] |
| 暫時（打到就掉） | 瑪利歐的火力狀態 | 形成「保住狀態」的次要目標 | 挫折感 [推論] |
| 永久（能力） | 二段跳、衝刺 | 改變關卡設計空間 | 舊關卡需重新平衡 [推論] |
| 永久（數值） | 血量上限、攻擊力 | 平滑難度 | 缺乏驚喜 [推論] |

[推論] 解「捨不得用」的手法：(1) 上限很低（最多存 3 個），(2) 換關即清空，(3) 在魔王房門口強制補滿。

### 4.3 金錢 / 分數的用途

| 制度 | 用途 | 時代背景 |
|---|---|---|
| 純分數 | 排行榜、每 N 分給 1UP | 街機遺產；沒有商店的遊戲 [推論] |
| 金錢 → 商店 | 買道具 / 升級 | 《薩爾達傳說》式 |
| 金錢 → 續關 | 用錢換命 | 讓探索與生存互換 [推論] |
| 收集品 → 解鎖 | 集滿開啟隱藏關 | 提高重玩價值 [推論] |

[推論] 如果沒有商店，分數必須有其他出口（1UP、結算評價、排行），否則玩家會完全忽略它；「無出口的分數」是 8 位元設計最常見的浪費。

### 4.4 隱藏道具

| 放置原則 | 說明 |
|---|---|
| 可推理 | 有異常訊號（多餘空間、金幣指向、地形不對稱）[推論] |
| 可跳過 | 不是通關必需 [推論] |
| 分級 | 第一層（觀察可得）/ 第二層（需技巧）/ 第三層（需特定能力回訪）[推論] |
| 有回饋 | 取得瞬間要有專屬音效與畫面停頓 [推論] |

## ⑤ 難度

### 5.1 難度曲線形狀

| 形狀 | 描述 | 適用 |
|---|---|---|
| 鋸齒上升（推薦） | 每關內部上升，關與關之間回落，整體向上 | 通用 [源: 分形心流曲線] |
| 階梯 | 每 N 關跳一級 | 選關制 |
| 平緩 + 尾部陡升 | 前期輕鬆，最終關暴難 | 8 位元常見，但易勸退 [推論] |
| 沙漏 | 中段最難，結尾放鬆 | 敘事導向 [推論] |

心流通道：挑戰與技巧要同步成長；挑戰過高 → 焦慮與棄坑，挑戰過低 → 無聊與流失 [源]。

### 5.2 死亡懲罰

| 懲罰 | 強度 | 說明 |
|---|---|---|
| 回到房間起點 | 低 | 現代標準 |
| 回到檢查點 | 中 | 8 位元主流 |
| 回到關卡起點 | 高 | 需要關卡夠短 |
| 失去道具 / 狀態 | 中高 | 疊加在上述之上 |
| 失去金錢 | 中 | 可設計成「掉在原地可撿回」 |
| 回到世界起點（全失） | 極高 | 僅適合極短流程 |

[推論] 死亡懲罰的正確衡量標準是「重來一次需要的時間」，30 秒是心理上的分水嶺；超過 60 秒，玩家開始把死亡視為懲罰而非學習機會。

### 5.3 輔助系統

| 輔助 | 8 位元時代做法 | 現代做法 |
|---|---|---|
| 多出來的命 | 1UP、藏命 | 無限命 |
| 難度選擇 | 隱藏的 Hard Mode | 開場即選，可中途改 |
| 續關碼 | 密碼 | 自動存檔 |
| 無敵作弊 | Konami Code 類 | 輔助模式（減速、無敵、跳關） |
| 隱形輔助 | 擊中判定比精靈小、Coyote time | 動態難度調整 |

[推論] 對原創作品的建議：把「輔助模式」做成一個正式、無恥辱感的選單項（減速 50% / 無限命 / 跳過本關），並且不因此鎖住成就。

### 5.4 Konami Code 類作弊

Konami Code（↑↑↓↓←→←→ B A）由橋本和久（Kazuhisa Hashimoto）在製作 1985 年街機遊戲《宇宙巡航機（Gradius）》的 NES 移植版（1986）時寫出——他覺得測試時太難打，就寫了一個一次給滿所有強化的除錯碼，結果忘了拿掉就出貨了 [源]。後來在北美因《魂斗羅》NES 版而被稱為「30 條命碼」；《沙羅曼蛇 / Life Force》NES 版在標題畫面輸入可得 30 命 [源]。

[推論] 原創遊戲的作弊碼設計原則：
1. 放在標題畫面而非遊戲中（避免誤觸）。
2. 給予「明顯但非破壞性」的好處（音效測試、關卡選擇、額外命）。
3. 用它當成隱藏內容的鑰匙，而不是難度的替代方案。
4. 輸入成功要有專屬音效 —— 這是作弊碼文化的一半樂趣。

### 5.5 密碼系統設計

《銀河戰士》的密碼是 24 個字元、每格 64 種字元（6 bit），共 144 bit；其中 136 bit 存遊戲狀態、最後 8 bit 是前 136 bit 的加總校驗和，並加入位移運算，讓亂打的密碼不會輕易被接受 [源]。存的內容包含：飛彈數、已取得裝備、已拿的飛彈槽與能量槽、遊玩時間、已開的門、起始位置、雕像狀態、是否穿太空裝、已破壞的 Zebetite、已擊敗的魔王 [源]。

密碼系統設計表 [推論，格式依上述事實推導]：

| 設計項 | 建議 |
|---|---|
| 字元集 | 避開易混字（0/O、1/I/l、5/S、8/B），實務上取 32 字元（5 bit）比 64 字元更好輸入 |
| 長度 | 家用機建議 ≤ 16 字元；每字元 5 bit → 80 bit 可用 |
| 校驗 | 至少 6~8 bit 校驗和，並對資料做位元打散（避免「改一個字元＝改一項能力」被輕易破解） |
| 打散方式 | 以固定表做位元置換 + XOR 常數，成本低但有效 |
| 顯示 | 密碼畫面要能「看到自己輸的是什麼」且可修改單格 |
| 容錯 | 輸錯時提示「密碼無效」而非直接開始，並保留已輸入內容 |

[推論] 現代原創作品若要走復古味，建議「密碼 + localStorage 自動存檔」雙軌：密碼當成可分享的彩蛋（可以貼給朋友），自動存檔當成真正的續玩手段。

## ⑥ 手感 Game Feel

### 6.1 跳躍曲線

[推論，依 8 位元實作慣例整理]

| 參數 | 說明 | 典型值（60fps） |
|---|---|---|
| 起跳初速 | 決定最高點 | 4.0~5.5 px/frame |
| 上升重力 | 按住跳躍鍵時 | 0.15~0.25 px/frame² |
| 下降重力 | 通常大於上升重力 | 上升的 1.5~2.0 倍 |
| 最大落速 | 防止穿牆與失控 | 6~8 px/frame |
| 跳躍總幀數 | 起跳到落地 | 30~45 幀（0.5~0.75 秒）|
| 最高點停留 | 頂點附近重力減半（hang time） | 3~6 幀 |

「下降比上升快」與「頂點懸停」是讓跳躍感覺良好的兩個關鍵，兩者都不符合真實物理但符合直覺 [推論]。

### 6.2 可變跳躍高度

《超級瑪利歐兄弟》的實作：**按住 A 鍵時，只要垂直速度仍向上，重力就會被降低**；放開 A 鍵即恢復正常重力，因此按多久決定跳多高 [源]。此外瑪利歐的水平速度會影響跳躍參數，最高速時的跳躍最遠 [源]。

[推論] 三種可變跳躍實作法：
1. **重力切換法**（SMB 式）：按住＝小重力、放開＝大重力。最平滑，推薦。
2. **速度截斷法**：放開時若上升速度 > 閾值就截到閾值。實作最簡單，但有輕微頓挫。
3. **計時法**：按住每幀加一點上升速度，最多 N 幀。容易做出「持續上升」的浮空感。

### 6.3 子像素（Subpixel）

《超級瑪利歐兄弟》中「16 個子像素構成 1 個像素」，位置的低位不會被畫出來但會累積 [源]。這讓 8 位元遊戲能表現遠小於 1 px/frame 的加速度與慣性。

[推論] 實作建議：位置用 16.8 或 8.8 定點數（整數部分 = 像素，小數部分 = 子像素）。若用 JavaScript 浮點數，仍應在繪製時 `Math.floor` 到整數像素，否則像素藝術會出現邊緣模糊。

### 6.4 輸入緩衝與 Coyote Time

- **Coyote time**：離開平台邊緣後的短暫時間內仍接受跳躍輸入（名稱來自威利狼跑出懸崖後不會馬上掉下去）[源]。
- **輸入緩衝（Jump buffer）**：落地前按下的跳躍鍵會被記住，落地瞬間自動執行 [源]。
- 現代建議值：Coyote time 5~8 幀、輸入緩衝 6~9 幀 [源]。
- 兩者都「看不見但感覺得到」，是平台遊戲寬容機制中影響最大的兩項 [源]。

[推論] 8 位元時代的實際做法：當時多半沒有明確命名的 coyote time，但等效效果來自狀態機的實作方式——角色離開地面後仍停留在「on ground」狀態一兩幀才切換，或碰撞檢測每幀只做一次而地面判定有容忍值。在原創遊戲中應**明確、有意識地**加入這兩個機制，而非依賴 bug。

### 6.5 無敵幀（i-frames）

受傷後的短暫無敵是經典設計，通常伴隨精靈閃爍作為視覺回饋 [源]。閃爍同時解決了兩件事：告知玩家目前無敵、以及用最低成本（跳過繪製）製造效果 [源]。

[推論] 建議參數：

| 情境 | 無敵長度 | 視覺 |
|---|---|---|
| 受傷 | 60~90 幀（1~1.5 秒） | 每 4 幀閃一次 |
| 重生 | 90~120 幀 | 每 8 幀閃一次（較慢＝較安全的暗示） |
| 翻滾 / 衝刺 | 8~14 幀 | 殘影而非閃爍 |
| 無敵道具 | 600~900 幀 | 調色盤循環 |

### 6.6 打擊停頓（Hit Stop）與畫面震動

Vlambeer 的 Jan Willem Nijman 在《The Art of Screenshake》裡示範了 30 個讓動作遊戲變好玩的微調，其中包含：敵人死亡 / 玩家受擊 / 爆炸時**暫停畫面 1~2 幀**製造蓄勢感、以及在重要事件時晃動畫面讓反應變得「有實體感」；其他還有槍口後座、彈殼掉落、屍體留在場上（永續性）、降低武器精度、動態鏡頭等 [源]。

[推論] 8 位元實作的數值建議：

| 事件 | Hit stop | 震動幅度 | 震動長度 |
|---|---|---|---|
| 普通命中 | 2 幀 | 0 px | 0 |
| 擊殺小怪 | 3 幀 | 1 px | 4 幀 |
| 玩家受傷 | 6 幀 | 2 px | 8 幀 |
| 魔王階段轉換 | 12 幀 | 3 px | 20 幀 |
| 爆炸 | 4 幀 | 2 px | 10 幀 |

震動實作注意：NES 上用改寫捲動值（scroll）做垂直震動成本極低；但**震動幅度超過 4 px 會讓像素藝術難以辨識**，且容易引起不適，應提供關閉選項 [推論]。

### 6.7 加速度表（建議數值總表）

[推論，60fps、角色高度 16~24 px 的橫向動作遊戲]

| 參數 | 慢速沉重型 | 標準型 | 敏捷型 |
|---|---|---|---|
| 最高步行速 | 1.0 px/f | 1.5 px/f | 2.0 px/f |
| 最高奔跑速 | 1.8 px/f | 2.5 px/f | 3.5 px/f |
| 地面加速度 | 0.05 | 0.12 | 0.25 |
| 地面摩擦 | 0.05 | 0.15 | 0.35 |
| 空中加速度 | 0.02 | 0.08 | 0.20 |
| 起跳初速 | 4.0 | 4.8 | 5.4 |
| 上升重力 | 0.14 | 0.20 | 0.26 |
| 下降重力 | 0.25 | 0.36 | 0.45 |
| 最大落速 | 5.0 | 6.5 | 8.0 |
| 轉向延遲 | 4 幀 | 2 幀 | 0 幀 |

[推論] 調參順序建議：先定「一次跳躍的水平距離」與「跳躍最高點高度」（因為它們決定關卡的格線），再反推初速與重力。若磁磚為 16 px，常見設定為「跳高 4 磁磚、跳遠 5~6 磁磚」。

## ⑦ UI / HUD 慣例

### 7.1 狀態列（Status Bar）

NES 上的固定狀態列靠 **sprite 0 hit** 實作：PPU 狀態暫存器 bit 6 會在 0 號精靈的不透明像素與背景不透明像素重疊時被設起；程式偵測到後修改捲動值，讓下方掃描線用不同的捲動量，形成「上方固定、下方捲動」的效果 [源]。《超級瑪利歐兄弟》的做法是把狀態列裡閃爍金幣的下面兩列像素複製到 0 號精靈上，並讓它排在背景之後 [源]。

[推論] 限制與對策：
- 一幀只能有一次 sprite 0 hit；要做兩條分割線就得靠 mapper IRQ（如 MMC3）或 DPCM 分割 [源]。
- 狀態列高度通常為 2~4 個磁磚列（16~32 px），佔 240 px 畫面的 7~13%。
- 狀態列應放在**上方**：因為 NES 的 overscan 讓下方更容易被電視切掉 [推論]。

### 7.2 生命條 vs. 生命點

| 形式 | 優點 | 缺點 | 實作成本 |
|---|---|---|---|
| 心形 / 圖示（離散） | 一眼可數、復古感強 | 上限受畫面寬度限制 | 極低（重用同一磁磚） |
| 橫條（連續） | 上限彈性大 | 精確值不易讀 | 低（用局部填充磁磚） |
| 數字 | 最精確 | 最不直觀 | 低 |
| 直條（洛克人式） | 省水平空間、可並排顯示武器能量 | 需要垂直空間 | 低 |

[推論] 8 位元建議：心形上限 ≤ 8 顆（超過就做成雙排或升級為橫條）；每顆心可切「半心」以增加解析度。

### 7.3 選單

| 元素 | 慣例 |
|---|---|
| 游標 | 用一個精靈（箭頭 / 星星）而非反白，成本最低 [推論] |
| 導航 | 上下選、A 確定、B 返回 [推論] |
| 音效 | 移動音（短促）與確定音（上揚）必須不同 [推論] |
| 循環 | 選單首尾相接（從最後一項往下回到第一項）[推論] |
| 預設焦點 | 落在「繼續遊戲」而非「新遊戲」，避免誤覆蓋存檔 [推論] |
| 延遲 | 第一次按住 16 幀後才開始連續移動，之後每 6 幀一格 [推論] |

### 7.4 字型 8×8

[推論] NES / GB 的文字都建立在 8×8 磁磚上：

| 項目 | 建議 |
|---|---|
| 有效字面 | 8×8 的格子裡實際畫 5×7，留 1 px 右側與 1 px 底部間距 |
| 大寫優先 | 大寫拉丁字母在 5×7 內最清楚；小寫需要下伸部（descender），會吃掉間距 |
| 數字 | 數字要做成等寬，避免計分跳動 |
| 中文 | 8×8 無法顯示漢字；最小可讀漢字約 12×12，實務上 NES 中文遊戲用 2×2 磁磚（16×16） |
| 每行字數 | 256 px 寬 ÷ 8 = 32 字元；扣掉左右邊界建議 28 字元 |
| 磁磚成本 | 大寫 26 + 數字 10 + 標點 10 ≈ 46 個磁磚，約佔 256 磁磚的 18% |

### 7.5 對話框

| 參數 | 建議 |
|---|---|
| 位置 | 畫面下方 1/3，避免遮住角色 [推論] |
| 尺寸 | 寬 26~28 字元 × 高 3~4 行 [推論] |
| 逐字顯示速度 | 每字 2~3 幀；按鍵可快轉到整段顯示 [推論] |
| 換頁 | 顯示閃爍的「▼」提示 [推論] |
| 邊框 | 用 9 個磁磚（4 角 + 4 邊 + 1 內）即可組出任意大小 [推論] |
| 音效 | 每 2~3 個字播一次短音，形成「說話感」 [推論] |

## ⑧ 存檔 / 密碼 / 續關

### 8.1 三種持久化機制比較

| 機制 | 成本 | 玩家體驗 | 代表 |
|---|---|---|---|
| 電池 SRAM | 需要卡帶內加 SRAM + 鈕扣電池，成本最高 | 最佳 | 《薩爾達傳說》為 NES 首款具備存檔能力的遊戲，用 SRAM + 鈕扣電池，可存 3 個檔案 [源] |
| 密碼 | 零硬體成本 | 抄寫麻煩，但可分享 | 《銀河戰士》24 字元密碼 [源] |
| 續關次數 | 零成本 | 最嚴苛 | 多數街機移植作 [推論] |

《薩爾達傳說》的存檔畫面預設只在角色死亡時出現；玩家後來發現暫停後用二號手把按住上 + A 可以隨時叫出存檔畫面 [源]。

### 8.2 存檔點設計

| 模式 | 說明 | 適合 |
|---|---|---|
| 死亡時存檔 | 只在死亡 / 結束時寫入 | 早期 ARPG |
| 存檔房 | 特定房間可存 | 探索型（同時兼作補給點與重生點） |
| 自動存檔 | 每過關 / 每房間 | 現代標準 |
| 隨時存檔 | 任意時刻 | 會削弱關卡張力 [推論] |

[推論] 存檔房的雙重角色（重生點 + 補給點）是探索型遊戲的重要節奏工具：它把整張地圖切成「以存檔房為圓心的可承受風險半徑」。

### 8.3 續關經濟

[推論]

| 參數 | 嚴苛 | 平衡（建議） | 寬鬆 |
|---|---|---|---|
| 起始命數 | 3 | 3 | 無限 |
| 續關次數 | 3 | 無限 | 無限 |
| 續關後的位置 | 世界起點 | 該關起點 | 檢查點 |
| 續關後的道具 | 全失 | 保留永久能力 | 全保留 |
| 1UP 取得率 | 每關 0~1 | 每關 1~2 | 不適用 |

## ⑨ 多人與競爭

### 9.1 8 位元多人模式的三種型態

| 型態 | 說明 | 硬體代價 | 代表類型 |
|---|---|---|---|
| 輪流制（Alternating） | 一號機死了換二號機 | 幾乎為零 | 瑪利歐式 |
| 同屏合作（Co-op） | 兩人同時在場 | 精靈預算加倍、每掃描線 8 精靈更吃緊 | 魂斗羅式 |
| 同屏對戰（Versus） | 兩人互相競爭 | 同上，另需勝負判定 | 對戰式 |

[推論] 每掃描線 8 精靈的限制讓「同屏雙人」在 NES 上非常昂貴：兩個各用 6~9 個 8×8 精靈的角色若處於同一高度，就會立刻觸發閃爍。對策是讓兩位角色的精靈總量控制在 8 個以內（例如各用 8×16 精靈，4 個組成 16×32 的角色）。

### 9.2 競爭設計要素

| 要素 | 說明 |
|---|---|
| 落後補償 | 落後者取得較好的道具（橡皮筋機制）[推論] |
| 可見的分差 | 隨時顯示雙方分數，維持張力 [推論] |
| 短局 | 單局 60~120 秒，便於再來一局 [推論] |
| 非對稱 | 兩方能力不同可增加重玩性，但平衡成本高 [推論] |
| 觀戰趣味 | 死亡者不該完全沒事做（可干擾 / 可下注）[推論] |

### 9.3 合作設計要素

| 要素 | 說明 |
|---|---|
| 友傷開關 | 預設關閉；開啟當作高難度模式 [推論] |
| 共享鏡頭 | 鏡頭夾在兩人之間；離太遠時把落後者拉過來（或判定死亡）[推論] |
| 共享資源 | 共用命數池可降低「拖累感」，但也降低責任感 [推論] |
| 復活機制 | 讓存活者能救回死亡者，是合作遊戲最重要的情緒點 [推論] |
