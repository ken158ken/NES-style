# 08 開發工具鏈與模擬器

## 摘要（10 行內）
1. 三條路線：**(1) 瀏覽器假復古**（Canvas + Web Audio，如 `../卡比之星`）、**(2) 真 NES ROM**（cc65/ca65 + neslib、NESmaker）、**(3) 真 GB/GBA ROM**（GBDK-2020 / GB Studio；devkitARM + libtonc / Butano）。[推論]
2. **學習曲線**：GB Studio ≪ 瀏覽器 Canvas < GBDK-2020(C) < Butano(C++) < cc65+neslib(C/6502) < 純 6502 組語。[推論]
3. **效果上限**：GBA(Butano) > 瀏覽器(無硬體限制) > NES > GB/GBC；但「像素風純度」剛好相反。[推論]
4. **自動化測試**：瀏覽器用 Playwright（本專案 `../卡比之星` 已驗證可行）；NES 用 FCEUX/Mesen Lua（`emu.frameadvance` + 截圖）；GB/GBA 用 mGBA Lua（`emu:runFrame()` + `emu:screenshot()`）。[源]
5. mGBA 自 0.10 起內建 Lua 腳本，支援 GBA 與 GB/GBC 核心，有 `runFrame / screenshot / setKeys / read8 / saveStateSlot` 與 frame callback。[源]
6. Mesen 2 支援 NES/SNES/GB/GBA/PCE/SMS/GG/WS，Linux 有 AppImage，GPLv3；Lua API 可截圖（回傳 PNG 字串，不必落地）。[源]
7. FCEUX 的 Lua 載入後**會把主迴圈交給腳本**，必須自行呼叫 `emu.frameadvance()`，否則模擬器凍結。[源]
8. GB/GBC 準確度：SameBoy（T-cycle 級，~2800 款自動測試 >99.9% 通過）、BGB（準確且 link 支援近乎完美）；GBA 準確度首選 mGBA。[源]
9. 發佈：瀏覽器 → itch.io / 靜態網頁；ROM → `.nes` / `.gb` / `.gba` 檔 + itch.io；實體 → NESmaker mapper 30 卡帶、EverDrive / EZ-Flash。[源]
10. **建議 AI agent 工作流**：每次建置後由 headless 模擬器（xvfb + mGBA Lua 腳本 / FCEUX Lua）跑到指定幀截圖 → PNG 存檔 → agent 用 Read 工具看圖驗證，與 `../卡比之星` 的 `tools/shot.py` 完全同構。[推論]

### 2.1 `../卡比之星` 的做法（已驗證可行的參考實作）

| 面向 | 做法 | 標註 |
|---|---|---|
| 技術棧 | 純 HTML + JS（ES2020，**classic script**，不用 ES module → 可直接 `file://` 開） | [源]（該專案 SPEC.md） |

| 打包 | `tools/build.py` 內嵌所有 js 成單一 `dist/*.html` | [源] |
| 規模 | `src/` + `src/art/` 合計約 **41,000 行 JS** | [源]（`wc -l` 實測） |

### 2.2 優點
| 優點 | 說明 | 標註 |
|---|---|---|
| 零工具鏈 | 不用裝編譯器、不用 make；改完存檔重整就看到 | [推論] |
| 迭代最快 | 對 AI agent 極友善：改一行 → 截圖 → 看圖，30 秒一輪 | [推論] |
| 發佈最容易 | 單一 HTML 檔，雙擊即玩，也能直接丟 itch.io / GitHub Pages | [推論] |
| 無資源上限 | 想要 300 個粒子、Alpha、旋轉縮放都可以 | [推論] |
| 中文友善 | 可用系統字或自繪點陣字（但見下方缺點） | [源]（該專案已知問題） |
| 測試自動化成熟 | Playwright + 決定性 `step(n)` API 是完整的 CI 方案 | [源] |

### 2.3 缺點
| 缺點 | 說明 | 標註 |
|---|---|---|
| 沒有「真的」 | 玩家 / 社群不會認為那是 NES 遊戲；不能上實體卡帶 | [推論] |
| 容易破功 | 沒有硬體約束，很容易不自覺地畫出 NES 不可能的畫面（幾百色、半透明、平滑捲動子像素） | [推論] |
| 音色要自己做 | Web Audio 的方波 / 三角波要手動加上包絡、掃頻才像 2A03 | [推論] |
| 字型踩雷 | 中文靠系統字 rasterize，在無對應字體的 Linux 上 12px 會變細線不可讀 | [源]（`../卡比之星` 已知問題） |

### 2.4 如何自我約束成「NES 規格」
把限制寫成**可測試的 lint 規則**，交給 agent 每次建置時跑：

| 規則 | 具體數值 | 檢查方式 | 標註 |
|---|---|---|---|
| 解析度 | 內部 canvas 固定 256×240（或可見 256×224） | 讀 canvas.width/height | [推論] |
| 調色盤 | 全域只允許 1 個 54 色 NES 主調色盤；背景 4 組×3 色 + 1 共用底色；精靈 4 組×3 色 | 掃描所有 `PAL` 物件，比對色碼是否都在主盤內 | [推論] |
| 屬性格 | 背景每 16×16 像素只能用同一組 3 色 | 對背景 render 結果分 16×16 區塊統計唯一色數 ≤ 4 | [推論] |
| 磁磚數 | 背景 + 精靈圖樣各 ≤ 256 片 8×8 | 統計唯一 8×8 圖樣數 | [推論] |
| 精靈 | 同屏 ≤ 64 個 8×8；每條掃描線 ≤ 8（超過就刻意閃爍） | 每幀統計 OAM 等價清單 | [推論] |
| 捲動 | 整數像素捲動（不要 0.5px） | camera x/y 取 `Math.floor` | [推論] |
| 透明度 | 禁用 `globalAlpha`、禁用漸層填色 | grep 原始碼 | [推論] |
| 音訊 | 只准 2 方波（4 種工作週期）+ 1 三角（固定音量）+ 1 雜訊 + 1 DPCM 取樣 | audio.js 架構上限制聲部數 | [推論] |
| 幀率 | 固定 60 步進、輸入每幀取樣一次 | 已由 `dt=1 幀` 保證 | [源] |

> **建議**：寫一支 `tools/nes_lint.py`，在 `build.py` 前跑，違規就 fail。這樣「假復古」就有了硬約束，
> 畫面也會自然帶上真正的 NES 味。[推論]

## 3. 路線 2：真 NES ROM

### 3.1 工具鏈組成
| 工具 | 角色 | 說明 | 標註 |
|---|---|---|---|
| **cc65 / ca65 / ld65** | C 編譯器 / 6502 組譯器 / 連結器 | 流程：C → cc65 → 6502 asm → ca65 → `.o` → ld65（吃 `.cfg` 設定檔）→ `.nes` | [源] |
| **neslib** | NES 函式庫 | Shiru 所作，處理 VRAM buffer、精靈、捲動、搖桿、音樂播放；nesdoug 的教學模板即以 neslib 為前提 | [源] |
| **nesdoug 教學** | 入門教材 | 章節：Introduction / What you need / How cc65 works / Our first program / What's a v-blank / VRAM buffer / Full Background / Palettes / Sprites / Controllers and sprite collisions / BG collisions / Scrolling；程式碼全在 GitHub | [源] |
| **NESmaker** | 無程式碼工具 | 完整套件（圖形、音樂、關卡、對話、輸入），編譯後可燒進實體卡帶；基本版 **US$36 一次買斷**；開發套件另含 mapper 30 可重燒卡帶 + 燒錄器 | [源] |
| **asm6f** | 單檔 6502 組譯器 | asm6 的 fork，加了 NES 相關指令與除錯符號輸出；適合「不想用 C、也不想搞 ld65 設定檔」的人 | [推論] |
| **NEXXT** | 圖形 / 磁磚 / nametable 編輯器 | NES Screen Tool 的後繼，做 CHR、nametable、metasprite、調色盤 | [推論] |
| **FamiStudio** | 音樂編輯器 | 可匯出 WAV / ROM / NSF / **FamiTone2 / FamiStudio Sound Engine 組語** / FamiStudio Text / FamiTracker Text；用 DPCM 時另出 `.dmc` | [源] |
| **FamiStudio Sound Engine** | 音樂驅動 | 支援 2A03 前 4 聲道（2 方波 + 三角 + 雜訊）、96 個音（C0–B7）、工作週期 / 音量 / 音高 / 琶音包絡 | [源] |
| **Mesen 2** | 模擬器 + 除錯器 | 見下節 | [源] |

### 3.2 典型專案骨架
```
project/
  src/main.c          # C 主程式（呼叫 neslib）
  src/crt0.s          # 啟動碼 / iNES 標頭（.segment "HEADER"）
  src/music.s         # FamiStudio 匯出的組語
  chr/tiles.chr       # NEXXT 匯出的 8 KB 圖樣表
  nes.cfg             # ld65 記憶體配置（ZP / RAM / PRG / CHR / VECTORS）
  Makefile            # cc65 → ca65 → ld65 → game.nes
```
（骨架為 nesdoug 教學模板的通用形狀，細節請以官方模板為準。[推論]）

### 3.3 Mesen 的除錯功能（做 NES 最大的理由）
| 功能 | 用途 | 標註 |
|---|---|---|
| **Lua Script Window** | 以 `emu.*` API 與模擬核心互動：記錄、繪圖、實作 AI；可同時開多個腳本視窗；編輯器有自動完成（打 `emu.` 即列出全部 API 與參數說明） | [源] |
| 記憶體存取 | 讀寫 **CPU / PPU / CHR ROM / CHR RAM / PRG ROM / PRG RAM / OAM** 各類記憶體 | [源] |
| 截圖 | 取得截圖並**以字串回傳 PNG，不必寫入磁碟** | [源] |
| 事件回呼 | NMI、IRQ、frame start / end、reset、savestate 事件 | [源] |
| Trace Logger | 指令級追蹤 | [源] |
| 其他除錯工具 | 除錯器、PPU 檢視器等（官方文件 `mesen.ca/docs/debugging.html`） | [源] |
| 授權 / 平台 | **GPLv3**；Windows / Linux / macOS；Linux 原生需 SDL2、.NET 8（ARM64 AppImage 除外） | [源] |
| 狀態 | 原 `SourMesen/Mesen2` 於 2026 年 6 月封存，社群 fork **MesenCE** 接手維護 | [源] |

### 3.4 學習曲線與效率
| 面向 | 評估 | 標註 |
|---|---|---|
| 上手 | 需理解 v-blank、VRAM buffer、attribute table、mapper、bank switching；nesdoug 教學約 12 章 | [源]（章節 [源]、難度 [推論]） |
| C 的代價 | 6502 沒有硬體乘除、堆疊只有 256 bytes，cc65 產出的碼比手寫組語慢數倍；熱迴圈仍要寫組語 | [推論] |
| 開發效率 | 改一行 → make → 載入 Mesen，約 5～20 秒；比瀏覽器慢但可接受 | [推論] |
| 效果上限 | 受硬體硬限制（見文件 01 / 07）：同屏 25 色、每行 8 精靈、2 KB RAM | [源] |
| 捷徑 | **NESmaker** 可跳過大部分組語，代價是引擎行為被框住、社群資源較封閉 | [推論]（產品定位 [源]） |

### 4.5 GBA 程式的效能原則（來自硬體）
| 原則 | 原因 | 標註 |
|---|---|---|
| 預設用 Thumb 編譯 | 大部分記憶體只有 16-bit 匯流排 | [源] |

## 8. 自動化測試 / 截圖

### 8.1 瀏覽器（Playwright）— 已驗證
`../卡比之星` 的做法可直接抄：
1. 頁面提供**決定性推進 API**（`__kb.step(n)` 不用 requestAnimationFrame）。[源]
2. `tools/shot.py` 用 Playwright 開 Chromium，`--script "press right 40; tap attack 1; step 10"` 模擬輸入。[源]
3. 截圖存 `shots/agent_<名稱>/*.png`，**agent 用 Read 工具實際看圖**確認畫面。[源]
4. 另有 `engine_test.py` / `enemy_test.py` / `boss_test.py` / `playthrough.py`（自動通關）/ `level_check.js`（關卡靜態檢查）。[源]

### 8.2 NES（FCEUX Lua）
| API | 用途 | 標註 |
|---|---|---|
| `emu.frameadvance()` | 推進一幀；**腳本必須在主迴圈呼叫，否則模擬器凍結** | [源] |
| `gui.savescreenshotas(name)` | 存截圖 | [源] |
| `memory.readbyterange(addr, len)` | 讀記憶體區段（可做狀態斷言） | [源] |
| 載入行為 | 腳本載入後模擬器進入暫停、控制權交給 Lua | [源] |

骨架（概念）：
```lua
-- test_frame200.lua
for i = 1, 200 do
  if i > 60 then joypad.set(1, {right = true}) end
  emu.frameadvance()
end
gui.savescreenshotas("shots/frame200.png")
os.exit()   -- 依版本可能需改用 emu.exit() / emu.pause()   [推論]
```

### 8.3 NES（Mesen Lua）
| API | 用途 | 標註 |
|---|---|---|
| 讀寫各類記憶體 | CPU / PPU / CHR ROM / CHR RAM / PRG ROM / PRG RAM / OAM | [源] |
| 截圖 | **以字串回傳 PNG，不必寫入磁碟**（適合直接進管線 / base64） | [源] |
| 事件回呼 | NMI / IRQ / frame start / frame end / reset / savestate | [源] |
| 多腳本 | 可同時開多個 Script Window 疊加效果 | [源] |

### 8.4 GB / GBC / GBA（mGBA Lua，0.10.2+）
| API | 用途 | 標註 |
|---|---|---|
| `emu:runFrame()` | 執行一幀 | [源] |
| `emu:screenshot(filename)` | 擷取並存檔 | [源] |
| `emu:setKeys(keys)` / `emu:addKey(key)` / `emu:getKeys()` | 輸入控制 | [源] |
| `emu:read8/16/32(addr)`、`emu:write8/16/32`、`emu:readRange(addr, len)` | 記憶體存取 | [源] |
| `emu:saveStateSlot(slot)` / `emu:loadStateSlot(slot)` | 存 / 讀即時存檔 | [源] |
| callbacks | `frame`（幀結束後）、`keysRead`（輪詢輸入時）、reset / shutdown / savedata | [源] |
| `console` | 記錄訊息 | [源] |
| `socket` | Lua 內的 TCP 網路（可做「模擬器 ↔ agent」雙向通訊） | [源] |
| 支援核心 | **GBA 與 GB/GBC 都支援** | [源] |

Headless：社群專案（如 `mgba-mcp`）的做法是**以 xvfb 跑 mGBA 達成 headless 自動測試，並在任意幀取得 PNG 截圖**。[源]

骨架（概念）：
```lua
-- shot.lua：跑到第 300 幀、期間按右，然後截圖離開
local target = 300
callbacks:add("frame", function()
  local f = emu:currentFrame()              -- 名稱請以 0.10.2 文件為準  [推論]
  if f > 60 then emu:setKeys(0x10) end      -- 0x10 = Right（位元定義見文件）[推論]
  if f >= target then
    emu:screenshot("shots/frame300.png")
    os.exit(0)
  end
end)
```
搭配：
```bash
xvfb-run -a mgba-qt --script shot.lua game.gba     # 旗標名稱請以本機 `mgba-qt --help` 為準  [推論]
```

### 8.5 自動化能力比較
| 路線 | 決定性推進 | 輸入注入 | 截圖 | 狀態斷言 | 無頭 | 綜評 | 標註 |
|---|---|---|---|---|---|---|---|
| 瀏覽器 | ✅ `step(n)` | ✅ | ✅ Playwright | ✅ 直接讀 JS 物件 | ✅ headless Chromium | **最佳** | [源] |
| NES / FCEUX | ✅ `frameadvance` | ✅ `joypad.set` | ✅ | ✅ 讀記憶體 | ⚠️ 需 xvfb | 佳 | [源]（xvfb [推論]） |
| NES / Mesen | ✅ 事件回呼 | ✅ | ✅（回傳 PNG 字串） | ✅ 全記憶體 | ⚠️ 需 xvfb | 佳 | [源]（xvfb [推論]） |
| GB/GBA / mGBA | ✅ `runFrame` | ✅ `setKeys` | ✅ `screenshot` | ✅ `readRange` | ✅ xvfb 已有社群實例 | 佳 | [源] |
| GB Studio | ❌ 需自行匯出 ROM 再走 mGBA | — | — | — | — | 尚可 | [推論] |

> **關鍵洞察**：ROM 路線的斷言是「讀 RAM 位址」，比瀏覽器的「讀 JS 物件」難寫得多
> （要先知道變數在哪個位址，需靠 ld65 / lcc 的符號表或 debug 檔）。這是 ROM 路線在 AI 自動開發上的最大摩擦。[推論]

## 9. 用 AI agent 自動化開發的工作流程建議

### 9.1 通用迴圈
```
[1] agent 改程式碼 / 資料
[2] 建置（build.py / make）            → 失敗就把編譯錯誤回饋給 agent
[3] 靜態檢查（lint：規格約束、關卡合法性）→ 失敗就回饋
[4] 單元 / 機制測試（決定性推進 N 幀後斷言狀態）
[5] headless 模擬器跑到指定幀截圖 → PNG
[6] agent 用 Read 工具「實際看圖」確認畫面正確
[7] 寫進度到 PROGRESS.md（時間 / 完成 / 驗證指令 / 截圖路徑 / 下一步）
```
這正是 `../卡比之星` 已在用的協定（步驟 5、6、7 有明文規定）。[源]

### 9.2 ROM 路線的具體配方
| 步驟 | 瀏覽器 | NES ROM | GB / GBA ROM |
|---|---|---|---|
| 建置 | `python tools/build.py` | `make`（cc65 → `.nes`） | `lcc`/`make`（→ `.gb`/`.gba`） |
| 截圖 | `python tools/shot.py --scene ... --out X.png` | `xvfb-run fceux --loadlua shot.lua game.nes` | `xvfb-run mgba-qt --script shot.lua game.gba` |
| 輸入腳本 | `--script "press right 40; tap attack 1"` | `joypad.set(1, {right=true})` | `emu:setKeys(bits)` |
| 斷言 | 讀 `__kb.state()` JSON | `memory.readbyterange(addr, len)` | `emu:readRange(addr, len)` |
| 看圖 | Read 工具開 PNG | 同左 | 同左 |

### 9.3 讓 ROM 路線的斷言變容易（建議）
| 做法 | 說明 | 標註 |
|---|---|---|
| 固定一塊「除錯 RAM 區」 | 在連結器設定檔（ld65 `.cfg` / GBDK banking）保留 16～32 bytes 固定位址，遊戲每幀把關鍵狀態（場景 id、玩家 x/y/hp、敵人數、RNG seed）寫進去 | [推論] |
| 匯出符號表 | 讓建置產生 `.sym` / `.map`，Lua 腳本讀它取得位址，避免硬編碼 | [推論] |
| 幀數印記 | 除錯 RAM 放一個 frame counter，截圖時一併讀出寫進檔名，確保重現性 | [推論] |
| socket 通道 | mGBA Lua 有 `socket`，可讓模擬器把狀態直接推給 agent 的本機伺服器 | [源]（socket [源]、用法 [推論]） |
| 黃金圖比對 | 截圖與基準圖做像素差比對（Pillow），差異 > 閾值才要人看 | [推論] |

### 9.4 「先瀏覽器、後 ROM」的雙軌建議
| 階段 | 做法 | 理由 | 標註 |
|---|---|---|---|
| 原型 | 在瀏覽器用 NES 規格約束做完整玩法 | 迭代快 100 倍，agent 每分鐘可跑多輪 | [推論] |
| 資料格式先行 | 關卡、精靈、調色盤、音樂**都用可匯出的中性格式**（JSON / PNG / 文字 tracker） | 之後能寫轉檔器直接吐成 CHR / nametable / FamiStudio asm | [推論] |
| 移植 | 玩法定稿後才寫 ROM 版 | 避免在 6502 上反覆改設計 | [推論] |
| 風險 | 兩份程式碼會分岔 | 只移植「已凍結」的關卡，並保留瀏覽器版為 canonical 設計文件 | [推論] |
