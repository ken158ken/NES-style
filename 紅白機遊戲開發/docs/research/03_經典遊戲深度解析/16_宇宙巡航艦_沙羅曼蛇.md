# 16 宇宙巡航艦 / 沙羅曼蛇（Gradius / Salamander・Life Force，1985–1988）

## 摘要（10 行內）
1. 1985-05 街機《Gradius》（歐美名 **Nemesis**）→ 1986-04-25 FC《宇宙巡航艦》；1986-07 街機《沙羅曼蛇》（北美名 **Life Force**）→ 1987-09-25 FC《沙羅曼蛇》（美版 1988-08 改名 Life Force）。兩者是**不同作品**。[源]
2. 台灣 / 華語圈的合卡與口耳相傳長期把兩款都叫「沙羅曼蛇」，是本專案資料最容易搞混的一點。[源]
3. FC 版《宇宙巡航艦》= **CNROM / mapper 3**，PRG 32 KiB 不分頁、CHR 4 × 8 KiB 整塊切換、垂直鏡像；日本銷量破 **100 萬套**。[源]
4. 畫面 = **兩個光柵帶**：0–211 線遊戲區、212–239 線狀態列，靠 **sprite 0 命中** 分割，並在分割點換 CHR bank 才有 HUD 字型。[源]
5. 精靈 8×16、每線 8 顆；閃爍是**遊戲自己做的**——每幀把影子 OAM 基底 `$2F` 加 `$44`（= 輪替 17 顆精靈）。[源]
6. 能量表 6 格 `SPEED / MISSILE / DOUBLE / LASER / OPTION / ?`；第 7 顆膠囊**回捲到第 1 格（不是 0）**；已擁有的格子按下去**不消耗膠囊**；SPEED UP **沒有上限也沒有已擁有檢查**。[源]
7. 船速公式（反組譯實測）：`速度 = min(($40 + 2) & $FF, 16) / 2` px/幀，`$40 = 0` → **1.0**、`$40 = 14` → **8.0 飽和**；斜向不正規化 = ×√2。[源]
8. Option 是**24 筆環形位置緩衝**，兩顆分別落後 **11 / 22 筆**，而且**只有按著方向鍵時環才前進**（停手 = 整串凍結）。[源]
9. 捲動基礎速度 **0.5 px/幀**；檢查點 = `min(世界X頁碼 & $0E, 8)`，**每關 5 個、間隔 512 px**；死亡清光 `$40–$46` 全部強化。[源]
10. rank `$17 = (有主武器) + Option 數 + (有護盾) + (關卡旗標)`，每幀重算、死亡即歸零；`≥2` 敵彈加速 25%、`≥3` 改成預判射擊。[源]

### 1-3 台灣 / 華語圈的混用現象

- 台灣的 FC 合卡（多合一盜版卡帶）與早期雜誌，**兩款遊戲的選單標題經常都印「沙羅曼蛇」**；許多玩家長大後才知道自己玩的其實是初代 Gradius。[源]
- 成因推測：沙羅曼蛇（1987）在台灣普及度高、名字響亮又好記；合卡製作者把同系列、同美術風格的射擊遊戲一律套用同一個標題。[推論]
- 另一層混淆：北美 NES 的《Life Force》與日版 FC《沙羅曼蛇》**是同一個 ROM 家族**，但北美街機《Life Force》又是 1986 沙羅曼蛇的改版、日本 1987《Life Force》又是再一次的改版。這條「Salamander → Life Force(US AC) → Life Force(JP AC) → FC 沙羅曼蛇 = NES Life Force」的鏈是資料整理最容易出錯的地方。[源]
- **本專案的處理原則**：任何時候提到「Gradius 手感」都指 **FC 初代《宇宙巡航艦》**；提到「沙羅曼蛇式」一律指 **FC 1987 那款（= NES Life Force）**。

## ② FC《宇宙巡航艦》技術規格

### 2-1 卡匣 / Mapper

| 項目 | 內容 | 標記 |
|---|---|---|
| Mapper | **CNROM（iNES mapper 3）** | [源] |
| PRG-ROM | **32 KiB**（2 × 16 KiB），`$8000–$FFFF`，**完全不分頁** | [源] |
| CHR-ROM | **32 KiB**（4 × 8 KiB），整塊切換 | [源] |
| 鏡像 | **垂直**（`$2000 == $2800`、`$2400 == $2C00`） | [源] |
| 電池存檔 | 無 | [源] |
| 板子 | NES-CNROM 系（74xx161 + CNROM 保護二極體，1986 年日製 CNROM 常見） | [源] |
| 中斷 | **沒有掃描線 IRQ**（CNROM 沒有），畫面分割只能靠 sprite 0 命中或週期計時 | [源] |
| 日版容量標示 | 日文維基寫「384 キロビット」= 48 KiB；與 32 + 32 = 64 KiB（512 Kbit）不一致 | [源] |
| 差異解讀 | 日版可能只用 2 條 CHR bank（32 PRG + 16 CHR = 48 KiB = 384 Kbit），美版 ROM 檔則是 4 bank；本專案採 **4 bank 版（Data Crystal / 反組譯所測的美版）** 的行為 | [推論] |

**對本專案的啟示**：初代 Gradius 在「32 KB 程式 + 沒有 IRQ」的條件下做出七關橫捲 + 能量表 + Option，證明我們的 `engine/` + `games/cruiser/` 規模綽綽有餘；真正的限制不是容量，是**每幀 VBlank 預算與每線 8 精靈**。[推論]

### 2-2 畫面結構（兩個光柵帶）

| 帶 | 掃描線 | 捲動 | CHR bank | 標記 |
|---|---|---|---|---|
| A（遊戲區） | **0–211** | `($12, $13)`，`$13` 固定 = **12** | bank 0（地形 + 星空，**沒有 HUD 字型**） | [源/反組譯] |
| B（狀態列） | **212–239** | X = 0（水平重設），**Y 不重設** | bank 1（`SPEED UP / MISSILE / DOUBLE / LASER / OPTION` 字樣、數字、`HI`、`1P`、`GAME OVR`） | [源/反組譯] |

分割細節：

- `$9AA3` 是一個 `LDA $2002 / AND #$40 / BEQ` 的**忙等迴圈**，等 sprite 0 命中；實測會空轉 **1,919–2,186 次**（約 18,358 CPU 週期、161 條掃描線），也就是**半個畫面 CPU 什麼都不做**。[源/反組譯]
- sprite 0 本身固定在 `y=206, tile=$6D, attr=$23, x=248`。命中在掃描線 **207**，寫 `$2005` 的時機落在 **211** 線，所以帶 B 實際從 **212** 開始。[源/反組譯]
- 分割時寫的 `$2005` **Y 值其實無效**（PPU 的垂直捲動只在 pre-render 線複製），所以畫面最下面 12 線（228–239）其實是**捲回名稱表第 0、1 列**。[源/反組譯]
- 這是 CNROM 沒有 IRQ 的必然結果；我們的引擎有 `ppu.split(scanline, {...})`，等價於 MMC3 IRQ，**不需要忙等**，可以把那 18k 週期拿來跑遊戲邏輯。[推論]

### 2-3 精靈與閃爍策略

| 項目 | 內容 | 標記 |
|---|---|---|
| 精靈尺寸 | **8×16** | [源/反組譯] |
| 優先權 | **只看 OAM 索引**（索引小者畫在上面），與 x 座標無關 | [源/反組譯] |
| 每線上限 | 8；第 9、10 顆被 PPU 直接丟掉（**PPU 不會閃爍**） | [源/反組譯] |
| 閃爍 | **由遊戲自己做**：`$8B39` 每幀 `$2F = $2F + $44`（若結果為 0 再 `+4`），把影子 OAM 的寫入基底輪替 | [源/反組譯] |
| 輪替量 | `$44` = 68 位元組 = **17 顆精靈 / 幀** | [推論]（68 ÷ 4 = 17，由 `$44` 直接算出） |
| 影子 OAM | `$0200–$02FF`，NMI 開頭 `STY $4014` 一次 DMA | [源/反組譯] |

**啟示**：Gradius 的做法就是我們 `NES.SH.OAM` 契約裡的「同 prio 之間每幀輪替起點」。差別是 Gradius **整張 OAM 一起轉**（連船都會參與輪替），我們的契約是**分優先權層再輪替**（船 / 選項 / 自機彈永遠 prio 0 不閃）——後者對玩家更友善，也仍然是 NES 可實作的做法（只是遊戲邏輯多一點）。[推論]

### 2-4 捲動方式

| 項目 | 內容 | 標記 |
|---|---|---|
| 相機 | 24-bit：`$3D` = 子像素、`$3E` = 世界 X 低位、`$3F` = 世界 X 高位（= 「頁」） | [源/反組譯] |
| 基礎速度 | 每幀 `$3D += $80`（= **0.5 px/幀**），進位才 `$3E += 1`。4000 幀實測：有跑到的 3207 幀**每幀剛好 +$80**，沒跑到的 789 幀剛好 0 | [源/反組譯] |
| 強制加速 | 關卡結尾的狀態 `st_984F` 改成 `$3E:$3F += 4`（**4 px/幀**），跑到 `$3F >= $11` 為止 | [源/反組譯] |
| 名稱表 | **兩張內容完全相同**（只有第 28、29 列的狀態列不同），所以是一條 256 px 的「跑步機」：`$12` 由 0 跑到 255 再繞回，PPU 自己的 coarse-X 溢位會從另一張名稱表抓右半邊 → 繞回時看不出接縫 | [源/反組譯] |
| 一幀延遲 | 捲動暫存器影子 `$12` 是在**上一幀**由 `$3E` 複製過去的。3206 幀實測 `$12[N] == $3E[N-1]` **3206/3206**；若直接寫當幀相機，有一半的幀會快一格 | [源/反組譯] |
| 地形串流 | 每幀只補新露出的那一欄（block 系統：半頁 = 4 block 欄 × 7 block 列 = 28 block = 128 × 224 px） | [源/反組譯] |

> 我們的 `NES.SH.Scroller` 契約（每幀只寫新露出的那一欄、≤ 45 byte）跟 Gradius 的做法在**精神上完全一致**，只是 Gradius 用兩張同內容名稱表 + PPU 溢位，我們用兩張名稱表交替寫。[推論]

### 2-5 HUD 版面

| 位置 | 內容 | 標記 |
|---|---|---|
| 畫面下方 28 線（212–239） | 分數 / HI / 1P、能量表六格、剩餘船數（生命圖示 `$61` + 十位 + 個位） | [源/反組譯] |
| 重畫時機 | **每 8 個遊戲幀重畫一次**（不是撿到膠囊才畫）：`$8898` 用 `$48 & 3` 輪流送 4 個罐頭 VRAM 封包，能量表 `$89E3` 是其中之一，770 幀內執行 **96 次** | [源/反組譯] |
| 選中游標 | `$8A30`：把已排入佇列的第 `8 - $42` 個位元組改成磚 `$55`；`$42 == 0` 時**完全不畫游標** | [源/反組譯] |
| 「已擁有」字樣 | MISSILE（`$41 != 0`）、DOUBLE（`$44 == 2`）、LASER（`$44 == 1`）、`?`（`$46 != 0`）會換成另一組字串；**OPTION 要 `$45 >= 2` 才換**（只有 1 顆 Option 時仍顯示 OPTION） | [源/反組譯] |
| SPEED UP | **沒有「已擁有」形態**（因為沒有上限），最左邊那格字樣永遠不變 | [源/反組譯] |
| 玩家死亡時 | `$89E3` 直接 RTS，**狀態列什麼都不畫** | [源/反組譯] |

## ③ 能量表系統完整規則

### 3-1 六格順序與效果

| 格 | 標籤 | 對應 RAM | 效果 | 已擁有時 | 標記 |
|---|---|---|---|---|---|
| 1 | **SPEED** | `$40` | `INC $40`（船速 +0.5 px/幀） | **沒有檢查、永遠生效、沒有上限** | [源/反組譯] |
| 2 | **MISSILE** | `$41` | `INC $41`（開啟斜下飛彈） | `$41 != 0` → 直接返回，**膠囊不消耗** | [源/反組譯] |
| 3 | **DOUBLE** | `$44 = 2` | 主武器 → 前方 + 45° 上 | `$44 == 2` → 返回，膠囊保留 | [源/反組譯] |
| 4 | **LASER** | `$44 = 1` | 主武器 → 貫穿短雷射 | `$44 == 1` → 返回，膠囊保留 | [源/反組譯] |
| 5 | **OPTION** | `$45` | `INC $45`，上限 2 | `$45 >= 2` → 返回，膠囊保留 | [源/反組譯] |
| 6 | **?** | `$46 = 5` | 護盾，可吃 5 下 | `$46 != 0` → 返回，膠囊保留 | [源/反組譯] |

幾條**與直覺相反、但實測為真**的規則：

1. **DOUBLE 與 LASER 互斥**，而且是靠同一個位元組 `$44` 做到的：選 DOUBLE 時 `$44 = 2`、選 LASER 時 `$44 = 1`。**選了另一個，原本那個就沒了**（StrategyWiki 的說法「選 Laser 會讓 Double 回到能量表」即是此意）。[源][源/反組譯]
2. **「已經有了」的格子按下去不會浪費膠囊**——`$42` 原地不動，可以繼續等下一次回捲。實測：連按 B 16–20 幀，`$42` 完全不變。[源/反組譯]
3. **B 鍵是「按住」不是「按下瞬間」**（讀 `$07` 而非 `$05`）。實測：按住 B 並每幀強制 `$42 = 1`，`$40` 會**每幀 +1**。[源/反組譯]
4. **撿膠囊與使用強化可以同一幀完成**。每幀順序是 `玩家更新 → 物件更新 → 碰撞（撿膠囊，`INC $42`）→ 套用（`$8974` 讀 `$42`）`，所以按著 B 去撞膠囊，強化在**撞到的那一幀**就生效。[源/反組譯]
5. **第 7 顆膠囊回捲到「1」不是「0」**：`$894B` 的 `CMP #$07 / BCC` 後 `LDA #$01 / STA $42`。也就是回捲後游標直接停在 SPEED，**不會經過「無選取」狀態**。[源/反組譯]

### 3-2 速度上限的真相

| `$40` | 0 | 1 | 2 | 3 | 4 | 5 | 6 | 8 | 10 | 12 | 13 | **14** | 16 | 20 | **254** | **255** |
|---|---|---|---|---|---|---|---|---|---|---|---|---|---|---|---|---|
| px/幀 | 1.0 | 1.5 | 2.0 | 2.5 | 3.0 | 3.5 | 4.0 | 5.0 | 6.0 | 7.0 | 7.5 | **8.0** | 8.0 | 8.0 | **0.0** | **0.5** |

- 公式 `速度 = min(($40 + 2) & $FF, $10) × 128`（單位 1/256 px/幀）= `min($40+2, 16) / 2` px/幀。**16 個 `$40` 值逐一實測，16/16 吻合**。[源/反組譯]
- **飽和點是 `$40 = 14`（8.0 px/幀）**，不是 16。[源/反組譯]
- `ADC #$02` 是 8-bit 且**會溢位**：`$40 = 254` → 原始值 0 → **船完全不動**；`$40 = 255` → 原始值 1 → **0.5 px/幀（半速）**。因為 SPEED UP 沒有上限，這是**玩得到的 bug**。[源/反組譯]
- StrategyWiki 記載「Speed Up 可選 5 次」是**街機**規則；FC 版「可以繼續選但沒有好處，只是取消目前的游標反白」的說法與反組譯不符——FC 版**每選一次都真的加速**，只是 `$40 >= 14` 後看不出差別。[源]（互相矛盾，本專案採反組譯）
- TAS 作者記載「取 13 次 SPEED UP 到最高速、最高速 8 px/幀且無加速度」——與 `$40 = 14` 飽和只差 1，可能是「從 `$40=1` 起算」的差異。[源]

### 3-6 第 7 顆膠囊的隱藏獎勵（分數位數彩蛋）

`$894B` 在 `$42` 要變成 7 的那一幀，會讀**分數的某一位數**：

```
A = ($07E5 + 4 × 玩家index) & $0F      # $07E4..$07E6 是 3 byte BCD 分數
A == 0 → $35 = 4      （自動連射間隔 20 幀 → 4 幀，= RAPID FIRE）
A == 5 → 分數 +10000
其他   → 沒有獎勵
$42 → 1（回捲）
```

- 六組 poke、四種不同結果、含無 poke 對照組，全部實測吻合。[源/反組譯]
- StrategyWiki 的玩家側描述完全一致：「讓 `?` 反白後再撿一顆，千位數是 0 → 連射、是 5 → 10000 分」。[源]
- **RAPID FIRE 死一次就沒了**——不是「被保留」，是死亡流程 `$9B5E` 把 `$35` 硬寫回 `$14`（20）。[源/反組譯]

## ④ Option 跟隨演算法

### 4-1 資料結構

| 位址 | 內容 | 標記 |
|---|---|---|
| `$07A0–$07B7` | **24 筆**過去的 X（整數像素） | [源][源/反組譯] |
| `$07C0–$07D7` | **24 筆**過去的 Y | [源/反組譯] |
| `$0160` | 環形游標 **0..23** | [源/反組譯] |
| 物件槽 | 0 = 本機，**1、2 = 兩顆 Option**（同一組平行陣列） | [源/反組譯] |

> Data Crystal 的 RAM map 把 `$07A0-$07B7` 標成「Vic Viper 的水平位置」、`$07B0-$07C7`（原文如此）標成垂直位置——實際上就是這兩條 24 筆的環形緩衝，兩份資料互相印證。[源]

### 4-2 每幀演算法（逐行）

```
if (任一方向鍵被按住) {                 # ← 關鍵：AND #$0F / BEQ
    cursor = (cursor + 1) % 24
    ringX[cursor] = shipX
    ringY[cursor] = shipY
}
# 下面兩行「無條件」執行，跟有沒有 Option 無關
option1.pos = ring[(cursor - 11 + 24) % 24]
option2.pos = ring[(cursor - 22 + 24) % 24]
```

| 特性 | 說明 | 標記 |
|---|---|---|
| 緩衝長度 | **24** | [源/反組譯] |
| Option 間距 | **11 筆**（Option1 落後 11、Option2 落後 22） | [源/反組譯] |
| 前進條件 | **只有按著方向鍵時**環才前進。玩家放開方向鍵 → 整串 Option **原地凍結**，不會慢慢追上來 | [源/反組譯]（實測：把「每幀都前進」的變體拿去跑，第 362 幀就對不上） |
| 延遲單位 | **是「移動幀」不是「時間幀」**——這是 Gradius 手感的靈魂：貼著船繞小圈 → Option 縮成一團；一路衝刺 → Option 拉成一條長蛇 | [推論]（由上一條直接推得） |
| 無條件維護 | 就算 `$45 == 0`（一顆 Option 都沒有），槽 1、2 的座標**照樣每幀更新**。所以撿到 Option 的瞬間它就已經在正確位置，不會從船身「長」出來 | [源/反組譯] |
| Option 動畫 | 自由跑：`$0121+i = (($0141+i >> 3) & 1) + 4`，**每 8 幀換一張**，兩張交替 | [源/反組譯] |
| 重生時 | 復活時起始座標會**同時寫進槽 0/1/2 與兩條環的全部 24 筆** → Option 不會從上一條命的位置飛過來 | [源/反組譯] |

### 4-3 死亡後 Option 去向

| 遊戲 | 規則 | 標記 |
|---|---|---|
| **Gradius（FC / 街機）** | `$45` 被死亡時的 `$3D–$97` 全區清除一起歸零 → **Option 完全消失**，回檢查點從 0 顆開始 | [源/反組譯] |
| **沙羅曼蛇（街機）** | 死亡時 Option 會**留在原地變成可撿的道具**，下一條命可以撿回來 | [源] |

這是兩作「懲罰哲學」的根本差異，見 §8。

## ⑦ 關卡構成、檢查點 / 復活、rank、循環

### 7-1 關卡的三段式節奏

Gradius 每關固定三段：[源]

1. **空戰段（air battle）** — 純太空背景、簡單編隊。**這段的功能是讓玩家補強化**，不是挑戰。
2. **本關段** — 有主題的地形（洞窟 / 摩艾 / 細胞 / 要塞…）、有地形殺、有砲台。
3. **魔王段** — Big Core（前 5 關）。打完淡出接下一關的導航段。

> 這個「先給資源、再收租、最後結算」的三拍子，是整個 Gradius 手感的骨架，比任何單一數值都重要。[推論]

### 7-3 檢查點制度（FC，反組譯實測）

| 項目 | 內容 | 標記 |
|---|---|---|
| 檢查點公式 | 死亡瞬間 `$24 = min($3F & $0E, 8)`；`$3F` 是世界 X 的**高位（頁碼）**，1 頁 = 256 px | [源/反組譯] |
| 實際意義 | **每關 5 個檢查點，落在頁 0 / 2 / 4 / 6 / 8**，也就是**每 512 px 一個**，超過頁 8 之後一律回頁 8 | [源/反組譯] |
| 驗證 | poke `$3F = 3` → `$24 = 2`；`$3F = 7` → `$24 = 6`；`$3F = 20` → `$24 = 4`（`$14 & $0E = 4`） | [源/反組譯] |
| 復活時 | `$3F`（與地形指標 `$55`）由 `$24` 還原，`$3E`（低位）清 0 → 從那一頁的頭開始 | [源/反組譯] |
| 強化 | 死亡流程 `$9B3E` 用 `LDX #$5A / STA $3D,X` 把 `$3D–$97` 全部清 0，**`$40 / $41 / $44 / $45 / $46` 一併清空**；只有能量表游標 `$42` 從 `$22,X` 還原成 **0 或 1** | [源/反組譯] |
| 死亡代價（時間） | 爆炸後 `$4C = 120` 幀倒數 + 約 26–28 幀的關卡 intro（畫面全黑），實測**共 147 幀 ≈ 2.45 秒** | [源/反組譯] |
| 命數 | 初始 3（`$20`）；死亡 `DEC $20`；`$20` 變負 → GAME OVER | [源/反組譯] |
| 關卡結束 | 第 1 關在 `$3F >= $0C` 結束，即**世界 X ≥ 3072 px = 12 頁 = 12 個畫面寬** | [源/反組譯] |
| 暫停 | START 在 `$15` 設 1，相機凍結，但玩家更新**仍然在跑** | [源/反組譯] |

> **「Gradius 症候群」的量化定義**：死亡 = 失去最多 5 次 SPEED + MISSILE + LASER + 2 Option + 護盾（≈ 11 顆膠囊），而且退回最多 512 px 前。玩家用來重建這些的火力只有「每 20 幀一發的單發彈」。這不是難度設計，是**懲罰複利**。[推論]

### 7-4 rank（動態難度）

**rank 在 FC 版是一個叫 `$17` 的位元組，每幀從零重算：**[源/反組譯]

```
$17 = ($44 != 0 ? 1 : 0)      # 有 LASER 或 DOUBLE
    + $45                      # Option 數（0..2）
    + ($46 != 0 ? 1 : 0)       # 有護盾
    + ($19 != 0 ? 1 : 0)       # 關卡旗標（第 1 關 = 0）
```

| 特性 | 內容 | 標記 |
|---|---|---|
| 範圍 | 第 1 關可達 **0..4**；全遊戲最大 **5**（表格設計到 6） | [源/反組譯] |
| 是 loadout 的函式 | **不是時間、不是分數、不是技術**，純粹看你身上有什麼 | [源/反組譯] |
| 可以下降 | **死亡 → 裝備歸零 → rank 立刻掉到 0** | [源/反組譯] |
| 讀取點 | 全 NMI 可達範圍內有 **23 處讀 `$17`**，19 處是 `LDY $17 / LDA 表,Y` 直接查表 | [源/反組譯] |
| 門檻只有兩個 | `>= 2` 與 `>= 3`，各出現兩次 | [源/反組譯] |
| `>= 2` 的效果 | **敵彈 X、Y 速度各 +25%** | [源/反組譯] |
| `>= 3` 的效果 | **敵人改成「帶隨機提前量的預判射擊」**（rank < 3 是精準瞄現在的位置）；另外（第 2 關起）敵人射擊計時器**一幀扣 2** | [源/反組譯] |
| 查表影響 | 敵人 / 魔王 hp（`05 05 05 05 06 07 08 09 0A`、`02 02 03 04 05 06 07 08 09`）、移動速度、射擊間隔、關卡流程階段長度（`03 03 04 04 05 05 06 06`） | [源/反組譯] |
| **不影響什麼** | **敵人的生成表**。rank 1 與 rank 4 各跑 3600 幀，92 次生成事件**逐位元組相同**；靜態分析五個生成進入點也**沒有任何一條指令讀 `$17`** | [源/反組譯] |
| 街機的差異 | 街機版另外還有「每約 32 秒自然 +1」的時間項；速度提升在街機**不影響 rank** | [源] |

> **給我們的結論**：rank 這種系統最好的形式就是 Gradius 這個——**一個每幀從裝備重算的小整數，只改「敵人怎麼打」不改「敵人是誰」**。錯了只會讓難度偏掉，不會讓關卡結構崩掉。[推論]

## ⑪ 給《星塵巡航艦》的設計建議 10 條

1. **把「無加速度」當成硬規則。** 船的速度切換是瞬間的，沒有慣性、沒有摩擦。這是 Gradius 與所有後來者（R-Type 有蓄力、Thunder Force 有慣性）最根本的分野；一旦加了慣性，玩家就無法在 1 px 的縫隙間做精確操作，整個「能量表選速度」的設計也就失去意義。[源/反組譯]
2. **Option 的環必須「只有移動時才前進」。** 這一行程式碼就是 Gradius 的視覺簽名：小幅擺動 → Option 聚成一團形成集火；一路衝刺 → Option 拉成長蛇覆蓋前方。用時間驅動的延遲跟隨做不出這個效果。[源/反組譯]
3. **膠囊不要用機率，用規則。** 「整隊打完才掉」「紅色的一定掉」是可學習的，玩家第二輪就會開始規劃路線；隨機掉落只會讓死亡變成運氣問題。第 16 顆變清屏也維持這個可預測性。[源/反組譯]
4. **「已經有了的格子不消耗膠囊」一定要做。** 這是原作少數對玩家超級友善的規則，讓玩家敢按 B 試探；反過來，B 鍵建議改成**按下瞬間**觸發（原作是按住，會一口氣吃掉數顆膠囊，是設計瑕疵）。[源/反組譯][推論]
5. **rank 只改「敵人怎麼打」，絕不改「敵人是誰」。** 原作用 3600 幀、92 次生成證明了這條界線。照做的好處是：rank 算錯只會讓難度偏掉，關卡節奏、出怪表、機器人通關測試全都不受影響——這對我們的 `test_stage1.py` 是決定性的。[源/反組譯]
6. **rank 每幀從裝備重算，不要累積。** 一個純函式 `rank = f(武器, Option 數, 護盾)`，沒有累加器就不會漂移，死亡自動歸零，也不需要存檔。用 4 行程式取代一整套動態難度系統。[源/反組譯]
7. **魔王用「每吃一點傷害換一張圖」取代血條。** 原作 Big Core 只有 6 點血，但因為每一點都讓核心多開一格，玩家對「打中了」的回饋清晰到不需要任何 UI。我們的核心要塞應該把外殼 + 核心的總傷害點數壓到 **20–24**，每一點都有視覺變化。[源/反組譯][推論]
8. **死亡懲罰要「重」但「短」。** Gradius 的懲罰（強化全失 + 退回 512 px）是對的，但 147 幀（2.45 秒）的黑畫面在今天太長。建議維持「強化全失 + 回檢查點」，但把停頓壓到 **90 幀**，並補上原作沒有的 **90 幀重生無敵**。[推論]
9. **HUD 用「4 個罐頭封包每 8 幀輪一個」來畫。** 原作在沒有 IRQ、只有 32KB 程式的條件下，靠這招把 VBlank 寫入攤平；我們有 160 byte/幀 的硬預算，這個模式可以直接讓 `budget.over` 永遠是 0。[源/反組譯][推論]
10. **關卡長度抓 3072 px、捲動 0.5 px/幀、檢查點每 512 px。** 這組數字是原作第 1 關的實測值，換算成 102 秒一關、6 個檢查點，節奏上被驗證了 40 年。我們 TASKS 規劃的「12 畫面 = 384 欄」剛好完全吻合，只要把 `CR.stage.speed` 從 1.0 改成 **0.5**，關卡長度就不用動。[源/反組譯][推論]
