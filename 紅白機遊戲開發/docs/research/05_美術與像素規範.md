# 05 美術與像素規範（NES 色彩 / 磁磚經濟 / 精靈 / 動畫 / 掌機差異）

## 摘要（10 行內）

1. NES PPU 輸出 64 種色值（實際可見去重後約 54~56 色），背景與精靈各有 4 組「3 色 + 共用底色」的子調色盤 [源]。
2. 背景配色的最大束縛是屬性表：一個位元組控制 32×32 像素、切成四個 **16×16 像素**區塊，每區塊只能選 4 組子調色盤之一 [源]。
3. 兩張 pattern table 各 256 個磁磚、每磁磚 16 位元組（2 位元平面），CHR bank 切換的粒度由 mapper 決定 [源]。
4. 精靈：OAM 256 位元組 / 64 個精靈，每個 4 位元組（Y、磁磚、屬性、X），屬性含調色盤、背景優先、水平 / 垂直翻轉；**每掃描線只顯示 8 個** [源]。
5. 超過 8 個的對策是 OAM 循環（每幀把索引前進 4 的倍數但非 8 的倍數），把「消失」換成「閃爍」[源]。
6. 狀態列用 sprite 0 hit 做分割捲動；《超級瑪利歐兄弟》把狀態列金幣的下兩列像素複製進 0 號精靈 [源]。一幀只能有一次 sprite 0 hit [源]。
7. 動畫幀數慣例：NES 走路多為 3 幀（1→2→1→3 的循環），2 幀也很常見；SMB3 / SMW 等級約 15fps [源]。
8. 大角色由多個 8×8 或 8×16 精靈組成（metasprite）；24×24 的洛克人＝9 個 8×8 磁磚 [源/算術]。
9. 掌機：GB 160×144 / 4 階灰 / 40 精靈 / 每線 10 個；GBC 8 組 BG 調色盤 ×4 色 / RGB555 / 同屏最多 56 色；GBA 240×160 / 15 bit 色 / 128 精靈（32 個可仿射）[源]。
10. 文末給出「一套建議的原創美術規格」與 30 條檢查表 [推論]。

## ① NES 色彩系統實務

### 1.1 色彩總數

| 項目 | 事實 | 標記 |
|---|---|---|
| PPU 色值 | 調色盤記憶體中的 6 bit 值對應 64 種輸出之一 | [源] NESdev |
| 實際不重複色 | $0E / $0F 是 $1D（黑）的鏡像，$1E / $1F 等亦為黑，去重後常被引用為 54~56 色 | [源] NESdev + Lospec |
| Lospec 收錄 | 「Nintendo Entertainment System」調色盤收 55 色；另一版「NES (Aseprite)」收 56 色 | [源] Lospec |
| 色相結構 | 色相 $0 為淺灰，$1~$C 由藍 → 紅 → 綠 → 青，$D 為深灰，$E~$F 為黑的鏡像 | [源] NESdev |
| 亮度 | 高 2 bit 為亮度層（$0x 最暗 / $3x 最亮） | [源] NESdev |
| 禁用色 | $0D 會產生「比黑更黑」的訊號，可能讓某些電視出問題 | [源] NESdev |
| 色彩強調（emphasis） | PPUMASK（$2001）的強調位元可整體偏紅 / 綠 / 藍，NES 全套 56 色是把 8 種強調設定都算進去的說法 | [源] NESdev |

> [推論] 實務結論：**把 $0D 視為禁用色，把 $0E / $0F / $1E / $1F / $2E…等當成 $1D 的同義黑**，實際可用的「有意義色」約 52~54 色。

### 1.2 調色盤記憶體配置

| 位址 | 內容 | 備註 |
|---|---|---|
| $3F00 | 底色（backdrop） | 背景與精靈都透明時顯示這一色 [源] |
| $3F01~$3F03 | 背景子調色盤 0 的 3 色 | |
| $3F05~$3F07 | 背景子調色盤 1 | $3F04 為鏡像 / 未用 |
| $3F09~$3F0B | 背景子調色盤 2 | |
| $3F0D~$3F0F | 背景子調色盤 3 | |
| $3F11~$3F13 | 精靈子調色盤 0 | $3F10 鏡像到 $3F00 [源] |
| $3F15~$3F17 | 精靈子調色盤 1 | |
| $3F19~$3F1B | 精靈子調色盤 2 | |
| $3F1D~$3F1F | 精靈子調色盤 3 | |

事實：每層（背景 / 精靈）各有 4 組子調色盤、每組 4 色；每組的第 0 項與底色共用；整段 $3F00–$3F1F 在 $3F00–$3FFF 內重複鏡像 [源]。

> 因此螢幕上**最多同時 25 色**：底色 1 + 背景 4×3 + 精靈 4×3 = 25 [推論，由上述事實計算]。

### 1.3 16×16 屬性區塊的限制與繞法

事實：屬性表是每個 nametable 末端的 64 位元組陣列（$23C0 / $27C0 / $2BC0 / $2FC0）；一個位元組控制 32×32 像素（4×4 磁磚），再切成四個 16×16 像素（2×2 磁磚）的區塊，各佔 2 bit [源]。位元排列為 `值 = (右下<<6) | (左下<<4) | (右上<<2) | (左上<<0)` [源]。

| 繞法 | 做法 | 代價 |
|---|---|---|
| **對齊設計** | 所有裝飾元素以 16×16 為單位擺放，不跨區塊 | 構圖自由度下降，但零成本，最推薦 [推論] |
| **共用暗色** | 讓 4 組子調色盤共用同 1~2 個暗色（輪廓 / 陰影），跨區塊時邊界不明顯 | 色彩變化減少 [推論] |
| **用精靈補色** | 需要第 4、5 色的小物件改用精靈疊在背景上 | 吃精靈預算與每線 8 個限制 [推論] |
| **屬性邊界藏在暗處** | 讓屬性切換發生在黑色 / 陰影區 | 需要美術與關卡編輯器配合 [推論] |
| **每列換調色盤** | 用 mapper IRQ 在畫面中途改調色盤 | 需要 MMC3 等，且一幀只能做有限次 [推論] |

### 1.4 調色盤配置範例（原創遊戲用）

[推論] 以「夜間電子都會」主題為例的一組配置（NES 色碼）：

| 組 | 用途 | 色 0（底色） | 色 1 | 色 2 | 色 3 |
|---|---|---|---|---|---|
| BG0 | 主地形 | $0F 黑 | $01 深藍 | $11 中藍 | $21 亮藍 |
| BG1 | 遠景建築 | $0F 黑 | $00 深灰 | $10 中灰 | $20 白 |
| BG2 | 霓虹裝飾 | $0F 黑 | $04 深紫 | $14 洋紅 | $24 粉 |
| BG3 | UI / 狀態列 | $0F 黑 | $0F 黑 | $30 白 | $28 黃 |
| SP0 | 主角 | — | $0F 黑（輪廓） | $16 紅 | $30 白 |
| SP1 | 敵人 A | — | $0F 黑 | $19 綠 | $29 亮綠 |
| SP2 | 敵人 B / 子彈 | — | $0F 黑 | $28 黃 | $30 白 |
| SP3 | 特效 / 爆炸 | — | $0F 黑 | $27 橘 | $30 白 |

設計守則 [推論]：
1. 每組都把「色 1」設為同一個暗色（此例 $0F），讓所有物件的輪廓一致、跨區塊時不突兀。
2. 精靈的「色 3」盡量都用 $30（白）當高光，讓角色在任何背景上都能被看見。
3. 狀態列自用一組（BG3），這樣改狀態列配色不會影響場景。
4. 同一關的 4 組背景調色盤要有共同的色溫，否則畫面會散。

## ② 磁磚經濟

### 2.1 256 個磁磚怎麼分配

事實：pattern table 分成兩段各 **256 個磁磚**（$0000–$0FFF 與 $1000–$1FFF），每個磁磚 16 位元組、用兩個位元平面編碼 4 種色索引 [源]。一般把其中一張給背景、另一張給精靈 [源]。

[推論] 背景 256 磁磚的建議預算：

| 用途 | 磁磚數 | 說明 |
|---|---|---|
| 地形實體（地板 / 牆 / 平台） | 48 | 含各種邊角、內角、頂面 |
| 地形變體（破損 / 苔蘚 / 不同材質） | 32 | 用於視覺變化 |
| 裝飾物件（管線、招牌、窗） | 40 | 以 16×16 元磁磚為單位設計 |
| 背景遠景 | 24 | 天空、建築剪影 |
| 動畫磁磚（水 / 火 / 霓虹） | 16 | 保留給 CHR bank 切換 |
| 字型（大寫 + 數字 + 標點） | 48 | 見 04 文件 ⑦-4 |
| UI 框線 / 圖示 | 24 | 9 格邊框 + 心 + 圖示 |
| 空白 / 純色 | 4 | 全透明、全黑、全白 |
| 預留 | 20 | 除錯與後期追加 |
| **合計** | **256** | |

[推論] 精靈 256 磁磚的建議預算：

| 用途 | 磁磚數 | 說明 |
|---|---|---|
| 主角全動作 | 72 | 見 §3.2 |
| 敵人 A~F（6 種原型） | 96 | 每種 16 個磁磚 |
| 魔王（單關載入） | 32 | 靠 CHR bank 換 |
| 子彈 / 投射物 | 12 | |
| 特效（爆炸、煙、火花） | 20 | |
| 道具 | 12 | |
| 0 號精靈 / 游標 / 其他 | 12 | |
| **合計** | **256** | |

### 2.2 重用與翻轉

| 技巧 | 節省量 | 注意 |
|---|---|---|
| 水平翻轉（OAM 屬性 bit 6） | 面向左右只需畫一邊，省 50% [源] | 角色不能有不對稱特徵（單邊配件）[推論] |
| 垂直翻轉（bit 7） | 上下對稱物件省 50% [源] | 背景磁磚**無法**用 OAM 翻轉；NES 背景沒有翻轉位元 [推論] |
| 對稱磁磚 | 圓形、球、輪子只畫 1/4 | [推論] |
| 共用部件 | 走路循環中頭部不變，只換腿 | [源] NESdev 指出 8×8 精靈可讓走路循環共用頭部磁磚 |
| 純色磁磚重用 | 大片天空 / 地面只需 1~2 個磁磚 | [推論] |
| 邊框 9 格法 | 任意大小視窗只需 9 個磁磚 | [推論] |

> 重要限制 [推論]：NES 的**背景磁磚沒有翻轉旗標**（不像 GB/GBC/GBA），所以左右對稱的背景圖案必須存兩份磁磚。這是 NES 背景磁磚消耗特別快的主因之一，設計時要把「非對稱但可平鋪」的紋理列為優先。

### 2.3 元磁磚（Metatile）

事實：關卡資料若以 16×16 的元磁磚（4 個 8×8 磁磚）為單位存放，資料量可大幅下降；甚至可做階層式元磁磚（256×256 / 128×128 / 64×64 / 32×32 / 16×16）；《洛克人》系列把地圖切成 32×32 的「超級元磁磚」，每個由四個 16×16 元磁磚組成 [源]。

[推論] 為什麼 16×16 是甜蜜點：
1. 正好對應屬性表的一個色彩區塊 → 每個元磁磚可帶一個調色盤編號，配色自動合法。
2. 一個元磁磚可以只用 1 個位元組索引（256 種），關卡資料變成 16×15 的小陣列。
3. 碰撞資訊可以掛在元磁磚上（實心 / 平台 / 傷害 / 梯子），不必逐 8×8 標註。

元磁磚資料結構建議 [推論]：

```
Metatile 定義（每個 5 bytes）:
  byte 0: 左上 8x8 磁磚索引
  byte 1: 右上
  byte 2: 左下
  byte 3: 右下
  byte 4: bit 0-1 調色盤編號, bit 2-4 碰撞型別, bit 5-7 旗標（傷害/水/冰）
```

### 2.4 CHR bank 切換動畫

事實：mapper 能力的重點之一就是「切換 pattern table 的粒度有多細」[源]。很多遊戲把某幾個磁磚槽保留給瀑布、蠟燭等固定循環動畫，用 CHR bank 切換做出動畫 [源]。調色盤循環（color cycling）也常用來做水流 / 熔岩：不換圖，只換調色盤的顏色順序 [源]。

| 手法 | 成本 | 效果 | 適用 |
|---|---|---|---|
| CHR bank 切換 | 需要有 bank 切換能力的 mapper（如 MMC3 的 1KB 粒度） | 真正的形狀變化 | 瀑布、齒輪、旗幟 [推論] |
| 調色盤循環 | 每幀寫 3~4 個位元組，幾乎零成本 | 只有顏色流動 | 水、熔岩、霓虹燈 [源] |
| 兩者併用 | 中 | 最佳 | 大型瀑布 [推論] |
| 整組調色盤瞬間改白 | 極低 | 閃電 / 受擊閃白 | [源] |

[推論] 動畫磁磚的更新節奏：8 幀（約 7.5Hz）更新一次對水流最自然；超過 15Hz 會閃到刺眼。

## ③ 精靈規範

### 3.1 8×8 與 8×16

事實：OAM 共 256 位元組，容納 64 個精靈，每個 4 位元組 [源]：

| 位元組 | 內容 |
|---|---|
| 0 | Y 座標（有 1 條掃描線延遲；$EF–$FF 會把精靈藏起來） |
| 1 | 磁磚索引（8×8 模式由 PPUCTRL bit 3 選 bank；8×16 模式用本位元組 bit 0 選 bank） |
| 2 | 屬性：調色盤（4~7）、優先權位元（置於背景之後）、水平翻轉、垂直翻轉 |
| 3 | X 座標 |

8×8 與 8×16 的取捨 [源]：

| 項目 | 8×8 | 8×16 |
|---|---|---|
| pattern table 使用 | 一次只能用一張 | 可同時用兩張（可與背景共用磁磚） |
| OAM 項目數（32×16 角色） | 32 筆 | 16 筆 → 省 CPU |
| 進出畫面 | 較平順（減少 pop-on，PAL 上更明顯） | 較容易一次跳出一大塊 |
| 小物件（子彈、煙） | 適合，不浪費空間 | 浪費 |
| 動畫磁磚重用 | 佳（走路循環可共用頭部） | 較差 |
| MMC3 掃描線計數器 | 正常 | 同時取兩張 pattern table 會產生多餘的 PA12 上升，干擾計數器 |

[推論] 建議：主角與敵人用 **8×16**（省 OAM 與 CPU），子彈、特效、UI 游標用 **8×8**。但若使用 MMC3 的 IRQ 分割，要注意 8×16 跨 bank 的干擾。

### 3.2 角色由幾個精靈組成

| 角色尺寸 | 8×8 精靈數 | 8×16 精靈數 | 例 |
|---|---|---|---|
| 8×16 | 2 | 1 | 小型敵人 |
| 16×16 | 4 | 2 | 小瑪利歐級 |
| 16×24 | 6 | 3（需一個 8×8 補） | 典型主角 |
| 16×32 | 8 | 4 | 大型主角 |
| 24×24 | 9 | — | 洛克人（24×24 → 9 個 8×8 磁磚）[源/算術] |
| 32×32 | 16 | 8 | 中型魔王 |

主角的磁磚預算試算 [推論]：16×24 角色 = 6 個 8×8 磁磚 / 幀；若共用頭部（2 磁磚），每幀新增 4 磁磚。
- 待機 2 幀 = 6 + 4 = 10
- 走路 3 幀 = 12
- 跳躍 2 幀 = 8
- 下落 1 幀 = 4
- 攻擊 3 幀 = 12
- 受傷 1 幀 = 4
- 蹲下 1 幀 = 6
- 死亡 2 幀 = 8
- 爬梯 2 幀 = 8
- **合計約 72 磁磚**（與 §2.1 的預算相符）

### 3.3 每掃描線 8 精靈的閃爍策略

事實：PPU 每掃描線最多算 8 個精靈，超過的直接不畫；OAM 中位址較低者優先顯示 [源]。常見對策是 **OAM 循環（OAM cycling）**：每幀重新排列精靈順序，等於隨機化優先權，讓被丟掉的精靈每幀不同——視覺上變成閃爍而不是整個消失 [源]。具體做法之一是每次寫入 OAM 緩衝時，把起始索引前進「4 的倍數但不是 8 的倍數」（4、12、20、28…）；另一種更簡單的是把變數初始化為 4，每次 VBlank 加或減 8 [源]。PPU 有精靈溢位旗標，但它一幀只設一次（不知道是哪些精靈出問題），而且該旗標的邏輯有 bug 會誤報 [源]。

[推論] 分級策略（依重要性決定是否參與循環）：

| 優先級 | 內容 | 處理 |
|---|---|---|
| 固定最前（不循環） | 0 號精靈（sprite 0 hit 用）、主角 | 永遠放在 OAM 最前面 |
| 高 | 魔王、對玩家有威脅的彈幕 | 固定在次前段 |
| 中 | 一般敵人 | 參與循環 |
| 低 | 特效、粒子、可收集物 | 參與循環，必要時直接不畫 |

美術端的對策 [推論]：
1. **把角色設計得「瘦」**：16 px 寬的角色只佔 2 個精靈欄位，同一行能站 4 個角色。
2. **敵人不要與主角同高**：飛行敵人設在不同高度帶，自然避開同一掃描線。
3. **爆炸特效用背景磁磚**：把爆炸畫在背景層（若該處不需捲動）可完全避開精靈預算。

### 3.4 大魔王用背景層

[推論] 當魔王大於 64×64 時，用精靈組合在 NES 上幾乎不可行（8×8 精靈需要 64 個，正好用光全部 OAM，且每列都會爆掉 8 個上限）。標準作法：

| 手法 | 說明 | 代價 |
|---|---|---|
| 魔王畫在背景層 | 魔王本體用 nametable 磁磚，移動時重寫 nametable | 只能以 8 px（或 16 px）為單位移動；VBlank 時間有限，每幀只能改有限磁磚 [推論] |
| 背景 + 精靈混合 | 身體用背景、會動的部位（手、眼、嘴）用精靈 | 最常見，兼顧成本與動態 [推論] |
| 魔王靜止、競技場動 | 魔王固定在畫面中央，背景捲動製造移動感 | 省極多資源 [推論] |
| CHR bank 換整套 | 魔王專用一整組 CHR bank，進魔王房才切換 | 需要 mapper 支援 [推論] |

### 3.5 精靈優先權

| 機制 | 規則 | 用途 |
|---|---|---|
| 精靈間 | OAM 索引小者在前 [源] | 決定角色與敵人誰蓋誰 |
| 精靈 vs 背景 | 屬性位元組的優先權位元可讓精靈顯示在背景「之後」[源] | 角色走進草叢 / 管線後方、0 號精靈藏在狀態列後 |
| 透明 | 每組精靈調色盤的色 0 為透明 | 只有 3 個實色可用 [源] |

[推論] 常用技巧：讓角色的「輪廓」與「內部」用兩組不同調色盤的精靈疊起來，可讓一個角色看起來有 5~6 色（輪廓 3 色 + 內部 3 色，共用透明）。NESdev 討論中也提到洛克人的輪廓可能與身體其餘部分分屬不同磁磚，因為每個 8×8 精靈可用不同調色盤，排列得當就會看起來顏色更多 [源]。

## ④ 動畫幀數慣例

### 4.1 基準表

事實：NESdev 論壇的共識是經典 NES 平台遊戲多用 **3 幀走路循環**，播放順序為 `1→2→1→3→1→2→1…`（《超級瑪利歐兄弟》1 與 3、《超級瑪利歐世界》皆是此型）；2 幀交替的更簡單版本也很常見且「有其魅力」；動畫師建議至少做到 SMB3 / SMW 的水準，約 15fps；許多遊戲只有 4~8fps 並靠延遲操作掩飾 [源]。《卡比之星》的動畫流暢但每個動作的幀數不多，並且很會重用 CHR 磁磚，用「快速循環」的任天堂手法 [源]。

[推論] 建議幀數表（60fps 為基準）：

| 動作 | 幀數 | 每幀持續 | 等效 fps | 備註 |
|---|---|---|---|---|
| 待機 | 1~2 | 30~40 幀 | 1.5~2 | 呼吸起伏 1 px |
| 待機眨眼 | +1 | 4~6 幀 | — | 每 3~6 秒觸發一次，可隨機 |
| 走路 | 3（1-2-1-3） | 6~8 幀 | 7~10 | 最經典 |
| 走路（流暢版） | 4 | 4 幀 | 15 | SMB3 / SMW 等級 [源] |
| 奔跑 | 4 | 3 幀 | 20 | 加動態線 |
| 跳躍上升 | 1 | — | — | 單一姿勢即可 |
| 跳躍頂點 | 1 | — | — | 可省略 |
| 下落 | 1 | — | — | 通常與上升不同 |
| 落地 | 1 | 4~6 幀 | — | 壓縮（squash）1~2 px，效果極佳 |
| 攻擊 | 2~3 | 預備 6 / 命中 3 / 收招 6 | — | 預備幀要清楚 |
| 受傷 | 1 | 12 幀 | — | 搭配閃爍 |
| 死亡 | 2~4 | 8 幀 | — | 可用旋轉 / 消散 |
| 爬梯 | 2 | 8 幀 | — | 只在移動時播放 |
| 蹲下 | 1 | — | — | |

### 4.2 實作慣例對照

| 遊戲 | 角色走路幀數 | 特徵 | 標記 |
|---|---|---|---|
| 《超級瑪利歐兄弟》 | 3 幀（1-2-1-3 循環） | 以極少幀製造節奏感 | [源] NESdev 論壇 |
| 《超級瑪利歐兄弟 3》 | 3~4 幀，約 15fps | 增加了轉身 / 煞車幀 | [源] |
| 《洛克人》 | 3 幀跑步 + 獨立跳躍姿勢 | 跳躍姿勢單一（被論壇形容為「有點怪」） | [源] |
| 《卡比之星》 | 幀數不多但重用極佳 + 快速循環 | 大量狀態（吸入、飛行、能力）擠在有限 CHR 裡 | [源] |

### 4.3 幀數 vs. 磁磚成本

[推論] 16×24 角色（6 磁磚 / 幀，頭部可共用 2 磁磚）：

| 幀數 | 新增磁磚 | 累計 | 評價 |
|---|---|---|---|
| 2 幀走路 | 8 | 8 | 最省，看起來像機器人 |
| 3 幀走路 | 12 | 12 | 甜蜜點（1-2-1-3 可得 4 拍） |
| 4 幀走路 | 16 | 16 | 流暢，SMB3 等級 |
| 6 幀走路 | 24 | 24 | 超出 8 位元常態，不建議 |

> [推論] 決策法則：**與其把磁磚花在「走路第 4 幀」，不如花在「落地壓縮幀」與「攻擊預備幀」**——後兩者對手感的貢獻遠大於前者。

### 4.4 子像素動畫（Subpixel animation）

[推論，概念見 saint11 教學清單中的 "subpixel" 項目 [源]] 8 位元精靈只能整數像素移動，但可以用「輪替的 1 px 位移 + 內部細節變化」模擬更細緻的運動：
- 待機呼吸：每 30 幀把上半身整體上移 1 px。
- 慢速漂浮：位置每 3 幀動 1 px（等效 0.33 px/frame）。
- 眼睛移動：眼珠像素往左右各挪 1 px，看起來像視線轉動。

## ⑤ 背景層次與假視差

### 5.1 狀態列分割

事實：0 號精靈的不透明像素與背景不透明像素重疊時，PPU 狀態暫存器 bit 6 會被設起；程式偵測到後即可修改捲動值，使後續掃描線用不同捲動量 [源]。《超級瑪利歐兄弟》把狀態列閃爍金幣的下方兩列像素複製到 0 號精靈，並讓 0 號精靈顯示在背景之後 [源]。一幀只能有一次 sprite 0 hit；若要多條分割線就得用 mapper IRQ（如 MMC3）或 DPCM 分割 [源]。

[推論] 美術端要配合的事：
1. 0 號精靈必須疊在**一定會有不透明背景像素**的位置——狀態列裡永遠不會變成全透明的圖案（數字外框、圖示實心部位）。
2. 這個位置的圖案不可以在某些狀態下消失（例如「金幣數為 0 時不畫金幣」會讓分割失效）。
3. 分割線附近 1~2 列像素可能出現雜訊，美術上要放深色或邊框。

### 5.2 捲動速率與假視差

| 手法 | 原理 | 成本 | 效果 |
|---|---|---|---|
| 單層捲動 | 只有一層背景 | 零 | 標準 |
| 分割捲動（水平帶） | 用 IRQ 在不同 Y 區間設不同捲動值 | 需 mapper IRQ | 天空 / 地面不同速，最像視差 [源: 論壇討論多層分割] |
| 精靈當前景 | 用精靈畫近景物件（欄杆、樹） | 吃精靈預算 | 真正的前景視差 [推論] |
| 調色盤深度 | 遠景用低對比 / 偏藍色 | 零 | 心理視差（大氣透視）[推論] |
| 磁磚動畫 | 遠景雲朵用 CHR 動畫緩慢變化 | 低 | 偽移動 [推論] |
| 靜止遠景 | 遠景完全不動 | 零 | 最便宜的「無限遠」暗示 [推論] |

[推論] 沒有 mapper IRQ 時的最佳組合：**靜止遠景 + 大氣透視配色 + 精靈前景**，視覺上已經很接近三層視差。

### 5.3 色彩循環（Color cycling）

事實：色彩循環（又稱 palette shifting / palette animation）是改變調色盤內容來製造動畫感的技術，早期遊戲廣泛使用，因為「存一張圖 + 改調色盤」比存多幀動畫省記憶體與運算 [源]。NES 上常見於瀑布、河流、熔岩：指定一組專屬調色盤給這塊區域，然後輪轉它的顏色 [源]。

[推論] 具體參數：

| 效果 | 循環色數 | 更新間隔 | 方向 |
|---|---|---|---|
| 瀑布 | 3 | 6~8 幀 | 向下 |
| 河流 | 3 | 10~12 幀 | 水平 |
| 熔岩 | 3 | 12~16 幀 | 隨機感（用非等距順序） |
| 霓虹招牌 | 2 | 20~30 幀 | 閃爍 |
| 傳送門 | 3 | 4 幀 | 快速旋轉 |

### 5.4 閃電與畫面閃白

[推論] 實作：在 VBlank 期間把整組背景調色盤寫成「白 / 亮灰」，維持 2~4 幀後還原。

| 事件 | 幀序 |
|---|---|
| 閃電 | 白 2 幀 → 原色 3 幀 → 白 4 幀 → 原色（雙閃最自然） |
| 玩家受傷 | 全畫面偏紅 3 幀（把底色改成 $06） |
| 魔王死亡 | 白 1 幀 / 原色 1 幀，交替 8 次，再全黑淡出 |
| 撿到大道具 | 底色循環 4 種亮色，持續 30 幀 |

> 這類效果在 NES 上成本極低（VBlank 內寫 16 個位元組），是「投資報酬率最高的特效」[推論]。

## ⑥ 像素藝術原則

### 6.1 輪廓（Outline）

| 型式 | 說明 | 適用 |
|---|---|---|
| 全黑硬輪廓 | 整圈 1 px 純黑 | 精靈（在任何背景上都看得見）[推論] |
| 選擇性輪廓（selout） | 輪廓顏色隨受光方向變化（背光處深、受光處用物件本色的暗階） | 高階作法，NES 上因只有 3 色難以實作 [推論] |
| 無輪廓 | 靠色塊對比區分 | 背景磁磚（省色）[推論] |
| 內輪廓 | 物件內部分界線 | 大型物件 [推論] |

[推論] NES 的 3 色限制下，最務實的是「全黑硬輪廓 + 2 個實色（暗面 / 亮面）」——這正是大多數 NES 角色的樣子。

### 6.2 抗鋸齒（Anti-aliasing）

Pedro Medeiros（saint11，《Celeste》《TowerFall》的美術）把手動抗鋸齒描述為較複雜的主題：用中間色調模擬「半個像素」，柔化邊緣 [源]。

[推論] NES 上的取捨：
- 只有 3 色時，抗鋸齒會直接吃掉一個實色，通常**不值得**。
- 例外：角色的臉部曲線、UI 的圓角，可用第 2 色當一次性的過渡。
- 大原則：**先把剪影做對，再考慮抗鋸齒**；抗鋸齒不能救一個讀不出來的形狀。

### 6.3 選色

[推論] 在 NES 的 3 色限制下的選色公式：

| 槽位 | 角色 | 建議 |
|---|---|---|
| 色 1 | 輪廓 / 最暗面 | 全作品統一（如 $0F 黑） |
| 色 2 | 主體色（中間調） | 決定角色辨識度，選飽和度高的 |
| 色 3 | 亮面 / 高光 | 亮度差要夠大（NES 的 $3x 層） |

色相偏移（hue shifting）：暗面往藍 / 紫偏、亮面往黃 / 橘偏，會比單純降低亮度更有生氣 [推論]。但 NES 的固定調色盤能做的偏移有限，例如 $16（紅）→ $27（橘）→ $37（淺橘）是可用的一條。

### 6.4 讀性（Readability）與剪影（Silhouette）

[推論] 檢驗法：
1. **黑影測試**：把角色全塗成黑色，若仍能分辨「這是誰、面向哪邊、在做什麼」，剪影就合格。
2. **縮小測試**：縮到 50% 仍能辨識。
3. **背景測試**：把角色放在最複雜、最同色的背景上仍能看出來。
4. **同框測試**：主角、敵人、道具、裝飾四者同時出現時，優先序要一眼清楚。

讀性排序守則 [推論]：**玩家 > 威脅 > 可互動物件 > 地形 > 裝飾**。做法是把「對比度預算」按這個順序分配——裝飾用低對比（相鄰亮階），威脅用高對比（黑 + 高飽和）。

### 6.5 常見錯誤

| 錯誤 | 症狀 | 修正 |
|---|---|---|
| 抖動（dither）過度 | 在 NES 低解析度下變成噪點 | 只用在大面積漸層，且限 50% 棋盤 [推論] |
| 亮階太接近 | 立體感消失 | 至少跨 1 個 NES 亮度層（$1x → $3x）[推論] |
| 像素大小不一致 | 縮放過的圖混入手繪圖 | 一律用整數倍縮放 [推論] |
| 孤立像素（jaggies） | 曲線上出現 1 px 突起 | 線段長度依序遞減（4-3-2-1），不要 3-1-3 [推論] |
| 輪廓斷裂 | 角色在深色背景中消失 | 輪廓改用亮色或加一圈暗色描邊 [推論] |
| 動畫「抖」 | 幀與幀之間整體位移 1 px | 固定一個錨點（腳底 / 腰部）[推論] |

## ⑦ 掌機差異

### 7.1 Game Boy（DMG）

| 項目 | 規格 | 標記 |
|---|---|---|
| 解析度 | 160×144（20×18 磁磚） | [源] Pan Docs |
| 更新率 | 約 59.7 fps | [源] |
| 色彩 | 4 階灰 | [源] |
| 精靈總數 | 40 個 | [源] |
| 每掃描線精靈 | 10 個 | [源] |
| 精靈尺寸 | 8×8 或 8×16 | [源] |
| VRAM | 8 KB | [源] |
| Work RAM | 8 KB | [源] |
| CPU | Sharp LR35902，4.194304 MHz | [源] |

[推論] 對美術的影響：
- 只有 4 階灰 → **剪影與對比就是一切**；不能靠顏色區分敵我，必須靠形狀。
- 精靈調色盤只有 3 個可見階（色 0 透明）→ 角色實質只有 3 階。
- 每掃描線 10 個精靈（比 NES 的 8 寬鬆）→ 同屏角色可以稍多。
- 160×144 比 NES 的 256×240 小很多 → 角色要更小（建議 12×16 或 16×16），或者鏡頭要更近。

### 7.2 Game Boy Color

| 項目 | 規格 | 標記 |
|---|---|---|
| 色彩空間 | RGB555，共 32768 色 | [源] Pan Docs |
| 背景調色盤 | 8 組（含 Window） | [源] |
| 物件調色盤 | 8 組 | [源] |
| 每組色數 | 4 色 | [源] |
| 同屏最大色數 | 56 色 | [源] |
| 解析度 | 同 DMG（160×144） | [源] |
| 背景磁磚屬性 | 可指定調色盤、bank、水平 / 垂直翻轉、優先權 | [推論，GBC 背景屬性表的標準功能] |

[推論] 與 NES 的關鍵差異：
1. **調色盤可掛在每個磁磚上**（不是 16×16 區塊），配色自由度遠高於 NES，屬性區塊的煩惱消失。
2. **背景磁磚有翻轉旗標**，對稱圖案省一半磁磚。
3. 同屏 56 色（背景 8×4 = 32 + 精靈 8×4 = 32，扣掉透明）看起來比 NES 的 25 色豐富得多。
4. 因此 GBC 的畫面常呈現「柔和、低飽和、多層次」的風格，與 NES 的「高飽和、高對比」形成鮮明對比。

### 7.3 Game Boy Advance

| 項目 | 規格 | 標記 |
|---|---|---|
| CPU | ARM7TDMI，16.78 MHz（ARM 32 bit / Thumb 16 bit 雙指令集） | [源] Tonc |
| 解析度 | 240×160 | [源] |
| 色彩 | 15 bit（32768 色） | [源] |
| VRAM | 96 KB | [源] |
| 調色盤 | 背景 256 項 + 精靈 256 項（各 15 bit 色） | [源] |
| 精靈數 | 128 個（模式 0~2）；bitmap 模式 3~5 只有 64 個 | [源] |
| 仿射（affine） | 2 個背景 + 32 個物件可做旋轉 / 縮放 / 剪切 | [源] |
| 視訊模式 | 3 個磁磚模式（0~2）+ 3 個 bitmap 模式（3~5） | [源] |

[推論] 對美術的影響：
- 256 色模式（8bpp）讓像素藝術幾乎沒有配色限制；但 16 色 ×16 組的模式（4bpp）更省 VRAM，仍是實務主流。
- 仿射精靈讓「旋轉的魔王 / 縮放的特效」變得可行，這在 NES / GB 上要靠大量預繪幀。
- 240×160 的長寬比（3:2）比 NES 的 256×240（≈ 16:15）寬很多 → **同樣的角色尺寸，GBA 的垂直視野更窄**，垂直向的平台遊戲要特別注意。

### 7.4 螢幕尺寸對構圖的影響

| 機種 | 解析度 | 磁磚數（8×8） | 建議角色高度 | 可見的垂直磁磚 |
|---|---|---|---|---|
| NES | 256×240（實際安全區約 256×224） | 32×30 | 16~32 px | 28（安全區） |
| GB / GBC | 160×144 | 20×18 | 12~16 px | 18 |
| GBA | 240×160 | 30×20 | 16~24 px | 20 |

[推論] 結論：
- 若要一份美術同時能用於 NES 與 GB，**角色高度取 16 px**是唯一安全的共同值。
- GB 的 18 磁磚高度扣掉 2 列狀態列只剩 16 列 → 平台遊戲的跳躍高度不能超過 4 磁磚，否則角色會跳出畫面。
- NES 的下方 8~16 列常被電視 overscan 切掉，重要 UI 不要放在最底部 [推論]。

## ⑨ 原創美術風格建議（避免侵權的具體做法）

### 9.1 法律紅線（絕對不做）

| 禁止 | 說明 |
|---|---|
| 使用任何商業 ROM 抽出的 CHR / 精靈圖 | 即使只是「參考用」也不要放進專案資料夾 [專案原則] |
| 描圖（trace）既有角色 | 逐像素描摹會被視為重製 [推論] |
| 使用受商標保護的角色名稱、外型特徵組合 | 例如紅帽 + 吊帶褲 + 八字鬍 + 大鼻子 的整組特徵 [推論] |
| 使用官方字型磁磚 | 8×8 字型也有著作權 [推論] |
| 直接照抄關卡布局 | 例如 1:1 重現 World 1-1 [推論] |

### 9.2 安全區（可以做）

| 可做 | 說明 |
|---|---|
| 使用硬體調色盤本身 | NES 的 64 色是硬體規格，不是創作 [推論] |
| 使用通用技法 | 屬性區塊對齊、OAM 循環、sprite 0 hit、色彩循環都是技術 [推論] |
| 參考「設計模式」 | 起承轉合、弱點鏈、可變跳躍是想法，不是表達 [推論] |
| 使用開放授權調色盤 | Lospec 上標示可自由使用的調色盤 [推論，使用前仍需看各調色盤標示] |
| 自行重新詮釋類型慣例 | 「會跳的水管工」不能抄，但「平台跳躍動作遊戲」的類型本身是公共財 [推論] |

### 9.3 建立原創視覺識別的具體做法

[推論] 主題方向：**電子音樂 × 夜間都會 × 幾何生物**

| 設計決策 | 具體做法 | 為何不像既有作品 |
|---|---|---|
| 主角造型 | 用「幾何體 + 單一發光特徵」而非人形（如：一個會走路的多面體，眼睛是發光線條） | 避開所有人形角色的比例特徵 |
| 色彩語言 | 全作限用「深藍底 + 洋紅 / 青 高光」的雙色霓虹 | NES 經典作多用紅 / 藍 / 棕，此配色反差明顯 |
| 輪廓風格 | 不用黑輪廓，改用「比主體暗兩階的同色系輪廓」 | 多數 NES 角色都是黑輪廓 |
| 動畫語彙 | 動作用「拉伸 / 壓縮 + 殘影」而非寫實步行 | 幾何角色不需走路循環，省磁磚也更獨特 |
| 背景語彙 | 用等距（isometric）暗示的建築剪影 + 掃描線光暈 | 與側視平鋪的磚牆風格區隔 |
| 特效語彙 | 所有特效都是「同心多邊形擴散」 | 統一的視覺簽名 |
| UI 語彙 | 用波形 / 頻譜條當生命值，呼應電子音樂主題 | 不是心形也不是橫條 |
| 字型 | 自繪 5×7 幾何無襯線，數字用七段顯示器造型 | 完全原創 |

### 9.4 自我檢查問句

[推論] 每完成一個素材就問：
1. 如果把它跟某個經典角色並排，一般玩家會不會認錯？（會 → 重做）
2. 它有沒有任何一個特徵是「只在某款特定商業作品出現過」的？（有 → 換掉）
3. 我能不能寫出一句話說明「我為什麼這樣畫」，而答案不是「因為某某遊戲是這樣」？（不能 → 重新設計）
4. 這個素材的來源檔案是不是 100% 由本專案產出？（不是 → 刪除）

## 附錄：建議的一套原創美術規格

[推論，綜合以上全部事實]

| 項目 | 規格 | 理由 |
|---|---|---|
| 邏輯解析度 | **256×240**（安全區 256×224） | NES 原生；縮放到 GBA 只需裁切 |
| 顯示倍率 | 整數倍（×2 / ×3 / ×4） | 避免像素模糊 |
| 磁磚尺寸 | 8×8，關卡以 16×16 元磁磚建構 | 對齊屬性區塊 |
| 色彩來源 | NES 硬體 64 色，實用 52 色（禁用 $0D 與各黑色鏡像） | [源] |
| 調色盤數 | 背景 4 組 ×3 色 + 精靈 4 組 ×3 色 + 1 底色 = 同屏 25 色 | [源] 硬體上限 |
| 統一輪廓色 | 所有子調色盤的色 1 統一為同一暗色 | 跨區塊不突兀 |
| 主角尺寸 | **16×24**（8×16 精靈 ×3 + 8×8 ×0，或 8×8 ×6） | 同屏可站 4 人不爆掃描線 |
| 一般敵人 | 16×16 | |
| 小型敵人 / 投射物 | 8×8 | |
| 中魔王 | 32×32（精靈） | |
| 大魔王 | 64×64 以上（背景層 + 精靈部位） | |
| 走路幀數 | **3 幀**（1-2-1-3，每幀 7 遊戲幀） | [源] NES 慣例 |
| 待機幀數 | 2 幀 + 眨眼 1 幀 | |
| 跳躍 | 上升 1 + 頂點 1 + 下落 1 + 落地 1 | |
| 攻擊 | 3 幀（預備 6 幀 / 命中 3 幀 / 收招 6 幀） | |
| 受傷 / 死亡 | 1 幀 / 3 幀 | |
| 主角磁磚預算 | ≤ 72 個 8×8 | |
| 目標幀率 | 60 fps（邏輯與繪製同步） | |
| 狀態列 | 上方 2 磁磚列（16 px），專屬調色盤 | |
| 字型 | 8×8 磁磚，有效字面 5×7，數字等寬 | |
| 掌機移植預留 | 角色高度 ≤ 24 px；重要 UI 不放畫面最底 16 px | GB 只有 18 磁磚高、NES 有 overscan |
