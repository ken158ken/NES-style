# 01 — 紅白機（Famicom / NES）硬體規格與限制

> 研究 agent：**hw** ｜ 日期：2026-09-12 ｜ 全文繁體中文，數字皆附來源。
> 標記規則：`[源]` = 有明確來源佐證；`[推論]` = 作者依事實推導的判斷或建議，非原始資料。

## 摘要（10 行內）

1. Famicom 1983-07-15 於日本上市、NES 1985-10-18 於北美上市，兩者主機板幾乎相同，差在卡匣腳位（60 vs 72 pin）、鎖定晶片 10NES、手把可否拆卸、以及**卡帶擴充音源只有 Famicom 能用**。`[源]`
2. CPU 是 Ricoh 2A03（6502 相容，**BCD 十進位模式被切斷**），NTSC 下約 1.789773 MHz，主機板上只有 **2 KB** 工作 RAM。`[源]`
3. 一個 NTSC 影格約 **29780.5 個 CPU cycle**、60.0988 Hz；其中只有 VBlank 的 20 條掃描線（約 **2273 cycle**）能安全寫 PPU。`[源]`
4. PPU 輸出 256×240，但 CRT 實際只看得到中央約 **256×224**；圖形由 8×8 磁磚組成，圖樣表共 8 KB＝2×256 磁磚。`[源]`
5. 色彩最嚴苛：系統調色盤 **64 格（56 色獨立）**，畫面同時只有 4 組背景 + 4 組精靈調色盤，每組 3 色 + 1 個共用背景色；背景配色以 **16×16 像素屬性區塊**為單位。`[源]`
6. 精靈上限 **64 個 / 影格、8 個 / 掃描線**，超過就不畫 → 產生 8 位元世代著名的「閃爍」。`[源]`
7. APU 五聲道：2 方波（12.5/25/50/75% 占空比、掃頻、包絡）、1 三角波（無音量控制）、1 雜訊、1 DPCM 取樣；混音是**非線性**的。`[源]`
8. 主機位址空間只有 32 KB 給卡帶 ROM，所有大作都靠 **mapper** 做 bank switching；MMC3 的掃描線 IRQ 是 1988 年後遊戲品質躍升的關鍵。`[源]`
9. 卡帶容量從 NROM 的 40 KB 成長到 Kirby's Adventure 的 768 KB、Metal Slader Glory 的 1 MB。`[源]`
10. 以上限制直接決定了磁磚重用、調色盤配置、大魔王用背景畫、狀態列分割、密碼存檔等所有 8 位元遊戲設計語彙。`[推論]`

## 1. 主機概觀

### 1.1 Famicom 與 NES 的差異

| 項目 | Family Computer（日本） | Nintendo Entertainment System（北美 / 歐洲） |
|---|---|---|
| 上市 | 1983-07-15 `[源]` | 1985-10-18 紐約試賣；1986-09-27 全美 `[源]` |
| 卡匣接腳 | 60 pin | 72 pin `[源]` |
| 卡匣插槽 | 上掀式 | 前插式（模仿 VCR 錄影機）`[源]` |
| 手把 | **固定接線**在主機上（二號手把有麥克風，無 Start/Select） | **可拆卸** 7-pin 接頭 `[源]` |
| 鎖定晶片 | 無 | **10NES** 認證晶片（常見的閃爍、無法開機多半是它老化）`[源]` |
| 擴充音源 | **卡匣腳位支援**（VRC6 / VRC7 / FDS / Sunsoft 5B / Namco 163 / MMC5）`[源]` | 未接出，NES 卡帶聽不到擴充音源 `[源]` |
| 視訊 | NTSC（2C02 PPU / 2A03 CPU） | 北美 NTSC；歐澳為 PAL（2C07 PPU / 2A07 CPU）`[源]` |
| 擴充埠 | 底部 15-pin 擴充埠（Zapper、Family BASIC 鍵盤等） | 無，周邊改走手把埠 `[源]` |
| 全球銷量 | Famicom + NES 合計 **6191 萬台** `[源]` | 同左（Nintendo 合併計算）`[源]` |

> `[推論]` 對開發者的實務意義：如果你要做「真 ROM」並希望在真機跑，**預設目標應該是 NTSC NES（無擴充音源）**；想用 VRC6 之類的額外音源，就等於宣告「Famicom / 模擬器 / 特製卡帶」限定。

### 1.2 Famicom Disk System（FDS，磁碟機）

| 項目 | 內容 |
|---|---|
| 上市 | 1986-02-21（日本）`[源]` |
| 媒體 | Quick Disk 改良的「Disk Card」，雙面共約 **112 KB** `[源]` |
| 額外音源 | Ricoh **2C33** 內含 1 聲道**波表合成（wavetable）** `[源]` |
| 遊戲數 | 約 194 款 `[源]` |
| 優點 | 容量大於當時卡帶、可寫入＝可存檔、可到店家用 Disk Writer 重寫（便宜）`[源]` |
| 衰退原因 | 磁片脆弱怕灰塵指紋、讀取慢、盜版猖獗、第三方不滿 Nintendo 要求共有一半著作權；1989 年後卡帶更便宜大容量而被淘汰 `[源]` |
| 代表作 | 《薩爾達傳說》《林克的冒險》《銀河戰士》《光神話 帕爾提娜之鏡》《惡魔城》《Super Mario Bros. 2（日版）》`[源]` |

> `[推論]` FDS 是「可存檔」與「開放世界探索」在紅白機上第一次大規模成立的技術前提：初代《薩爾達傳說》的磁碟存檔在卡帶版改成電池 SRAM，兩者都證明「持續進度」需要硬體支援，不是軟體能自己變出來的。

### 1.3 主要周邊

| 周邊 | 年份 | 技術原理 / 規格 | 代表作 |
|---|---|---|---|
| **Zapper 光線槍** | 日本 1984-02-18（光線槍系列）；北美 1985-10-18 隨 NES 同捆 `[源]` | 扣扳機時遊戲把整個畫面塗黑 **1 個影格**，下一個影格把所有有效標靶畫成**白色方塊**；槍口光感測器依「第幾個影格偵測到亮」判定打中哪個目標 `[源]` | 《Duck Hunt》《Wild Gunman》《Hogan's Alley》《Gumshoe》`[源]` |
| **Power Pad（日本：Family Trainer）** | Bandai 1986 日本；Nintendo 1988 北美 `[源]` | 兩層塑膠間夾 **12 個壓力感測器**；A 面 8 鈕、B 面 12 鈕；北美銷量 50 萬 `[源]` | 《World Class Track Meet》《Dance Aerobics》《Athletic World》`[源]` |
| **Family BASIC** | 1984-06-21；V3 版 1985-02-21 `[源]` | Nintendo × Hudson Soft × Sharp；鍵盤 + 卡帶，內含 HuBASIC 方言，支援精靈、背景、音樂、手把；**只支援整數**、用**錄音帶**存檔、不支援 FDS `[源]` | 使用者自製小遊戲（非商業）`[源]` |
| **R.O.B. 機器人** | 1985 隨 NES 同捆 `[源]` | 用畫面閃光下指令的光學玩具，實質是打進玩具通路的行銷道具 `[推論]` | 《Gyromite》《Stack-Up》`[源]` |

> `[推論]` Zapper 的原理解釋了為什麼它**在 LCD / 電漿電視上完全失效**：現代面板有顯示延遲且不是逐線掃描，感測器抓不到那一瞬間的亮度事件（來源也明說「只能用 CRT」）`[源]`。若要在瀏覽器重現光線槍玩法，必須改成純軟體命中判定，不能模仿原理。

## 2. CPU：Ricoh 2A03

### 2.1 核心規格

| 項目 | NTSC（2A03） | PAL（2A07） |
|---|---|---|
| 核心 | MOS 6502 相容，8 位元資料匯流排 / 16 位元位址匯流排（64 KB 定址）`[源]` | 同左 |
| 主時脈（master clock） | 21.477272 MHz ± 40 Hz `[源]` | 26.601712 MHz ± 50 Hz `[源]` |
| CPU 除頻 | ÷12 `[源]` | ÷16 `[源]` |
| **CPU 頻率** | **≈1.789773 MHz**（約 559 ns / cycle）`[源]` | ≈1.662607 MHz `[源]` |
| 暫存器 | A（累加器）、X、Y（索引）、S（堆疊指標）、P（旗標）、PC `[源]` |
| 定址模式 | 13 種，對 zero page 特別最佳化 `[源]` |
| **重大差異** | **十進位（BCD）模式被 Ricoh 切斷**，`SED` 無效；一般認為是為了規避 MOS 的 BCD 專利授權金 `[源]` |
| 整合 | **APU 內建於 CPU 晶片內**（Nintendo 藉此提高被仿冒的難度）；OAM DMA 與 DMC DMA 電路也在裡面 `[源]` |
| 工作 RAM | 主機板 **2 KB**（$0000–$07FF）`[源]` |

> `[推論]` 「無 BCD」的實務後果：**分數、金錢、HP 全部要自己做十進位轉換**。8 位元時代常見做法是把分數直接存成「每個 byte 一位數」的十進位陣列（Super Mario Bros. 的分數就是這種做法），避免每次顯示都做除以 10。若你在瀏覽器重製，這條限制可以無視，但「分數以 10 為單位、末位永遠是 0」這種**外觀慣例**建議保留，才像紅白機。

### 2.2 記憶體映射表（CPU 位址空間）

| 位址範圍 | 大小 | 用途 |
|---|---|---|
| `$0000–$00FF` | 256 B | **Zero page**（存取最快、指令最短，放最熱的變數）`[源]` |
| `$0100–$01FF` | 256 B | **堆疊**（6502 硬體固定）`[源]` |
| `$0200–$07FF` | 1.5 KB | 一般工作 RAM；慣例上 `$0200–$02FF` 拿來當 **OAM shadow buffer** `[源]`/`[推論]` |
| `$0800–$1FFF` | — | $0000–$07FF 的鏡像（每 2 KB 重複 3 次）`[源]` |
| `$2000–$2007` | 8 B | **PPU 暫存器** `[源]` |
| `$2008–$3FFF` | 8184 B | PPU 暫存器鏡像（每 8 byte 重複）`[源]` |
| `$4000–$4017` | 24 B | **APU 與 I/O 暫存器**（含 $4014 OAM DMA、$4016/$4017 手把）`[源]` |
| `$4018–$401F` | 8 B | APU/IO 測試模式（正常停用）`[源]` |
| `$4020–$5FFF` | — | 卡帶擴充區（多數 mapper 未用；MMC5、VRC 等會用）`[源]` |
| `$6000–$7FFF` | 8 KB | **卡帶 RAM**（工作 RAM / 電池備份存檔 SRAM）`[源]` |
| `$8000–$FFFF` | 32 KB | **卡帶 PRG-ROM 與 mapper 暫存器**（寫入這裡＝下 mapper 指令）`[源]` |
| `$FFFA–$FFFB` | 2 B | **NMI 向量** `[源]` |
| `$FFFC–$FFFD` | 2 B | **RESET 向量** `[源]` |
| `$FFFE–$FFFF` | 2 B | **IRQ / BRK 向量** `[源]` |

> `[推論]` 這張表最關鍵的一行是 `$8000–$FFFF` 只有 32 KB。整個紅白機的卡帶工程學（mapper）就是為了突破這 32 KB 而生。

### 2.3 中斷：NMI / IRQ / RESET

| 中斷 | 觸發來源 | 典型用途 |
|---|---|---|
| **NMI** | PPU 在**掃描線 241 的第 2 個 tick** 進入 VBlank 時觸發（需 PPUCTRL bit7 開啟）`[源]` | 主遊戲迴圈的心跳：OAM DMA、更新捲動、更新名稱表、跑音樂驅動程式 `[推論]` |
| **IRQ** | mapper 提供（MMC3 掃描線計數、VRC 的 cycle 計數、MMC5）、APU frame counter、DMC 取樣結束 `[源]` | **畫面中途分割**（狀態列、視差、分割捲動）`[推論]` |
| **RESET** | 開機 / 按 Reset 鍵 | 初始化；注意開機時需等待兩次 VBlank，PPU 才穩定 `[推論]` |

### 2.4 每影格 cycle 預算的意義

| 項目 | NTSC | PAL |
|---|---|---|
| 每掃描線 CPU cycle | 113⅔ `[源]` | 106 9/16 `[源]` |
| 每影格掃描線 | 262 `[源]` | 312 `[源]` |
| **每影格 CPU cycle** | **29,780.5** `[源]` | 33,247.5 `[源]` |
| 影格率 | **60.0988 Hz** `[源]` | 50.0070 Hz `[源]` |
| VBlank 長度 | 20 條掃描線 ≈ **2,273 cycle** `[源]` | 70 條掃描線 ≈ 7,459 cycle `[源]` |

怎麼讀這個預算（皆為 NTSC）：

| 消耗項 | cycle | 佔一影格比例 |
|---|---:|---:|
| **OAM DMA（$4014 搬 256 bytes）** | **513（奇數 cycle 時 514）** `[源]` | 約 1.7% |
| 扣掉進出 NMI handler 的開銷後，VBlank 可用 | 約 2,250 `[源]` | 7.6% |
| 展開（unrolled）的 VRAM 寫入約 8 cycle / byte，故 VBlank 約可寫 **160–200 bytes** `[源]` | — | — |
| 剩下給遊戲邏輯（畫面繪製中） | 約 27,000 | 91% |

實務換算（常用「粗略成本」，`[推論]`）：

| 工作 | 約略 cycle | 一影格可做幾次 |
|---|---:|---:|
| 一次 8 位元加法（zero page） | 3 | ~9,000 |
| 一次 16 位元加法（含進位） | ~10 | ~2,700 |
| 一次 8×8 → 16 位元乘法（軟體迴圈） | 100–200 | ~150–270 |
| 一個敵人的「移動 + 重力 + 動畫 + 邊界判定」 | 150–400 | 約 **60–170 隻** |
| 一次 metatile 解壓 + 寫一欄名稱表（30 bytes） | 300–600（含 VBlank 寫入） | 每影格 1 欄剛好 |
| 音樂驅動程式（FamiTone2 等級） | 約 1,500–2,500 | 每影格 1 次（約佔 5–8%） |

> `[源]` 上表中「OAM DMA 513/514 cycle」「VBlank 2273 cycle」「VBlank 可寫約 160 bytes ＋ OAM」有原始出處；其餘成本估算為 `[推論]`。
>
> `[推論]` **最重要的一條心法**：紅白機的瓶頸不是 CPU 算力，而是 **VBlank 這 2273 個 cycle 的頻寬**。所以正確寫法永遠是「畫面期間先把要寫的東西算好、排進 RAM 裡的 update buffer，VBlank 一到就無腦複製」。NESdev 論壇原話：「不要在 VBlank 裡計算，先在主 RAM 準備好緩衝區再複製。」`[源]`

## 3. PPU：圖像處理器

### 3.1 畫面與可視範圍

| 項目 | 數值 |
|---|---|
| 輸出解析度 | **256 × 240**，逐行掃描（240p，非交錯）`[源]` |
| 每掃描線 PPU dot | 341（1 dot = 1 像素，1 CPU cycle = 3 dot）`[源]` |
| 掃描線編排 | 預渲染線 261(-1)、**可見 0–239**、後渲染線 240、**VBlank 241–260** `[源]` |
| NTSC 電視實際可見 | 「極少 NTSC 電視顯示中央 **256×224** 以外的內容」`[源]` |
| Nintendo 官方安全區 | **Action safe 256×224；Title safe 224×192**（設計紙上上下各留 24 線、左右各留 16 像素給 overscan）`[源]` |
| PAL 差異 | 312 掃描線、50 Hz、像素長寬比 1.386:1（NTSC 為 1.143:1）、色相相差約 15 度 `[源]` |

> `[推論]` 設計準則：**HUD、血條、分數一律放進 224 線的中央區**，且距離左右邊緣至少 16 像素。可見區之外的上下各 8 線（240 vs 224）通常拿來當「捲動時的緩衝列」——正在載入新磁磚的那一欄/列藏在螢幕外，玩家看不到接縫。

### 3.2 磁磚與圖樣表（Pattern Table）

| 項目 | 數值 |
|---|---|
| 磁磚尺寸 | **8 × 8** 像素 `[源]` |
| 每磁磚位元深度 | **2 bit / 像素**（4 色：1 透明 + 3 色）`[源]` |
| 每磁磚大小 | **16 bytes**（兩個 bitplane，各 8 bytes）`[源]` |
| 圖樣表 | 共 **8 KB CHR**，分成 **2 個 4 KB 表，各 256 個磁磚**（$0000 與 $1000）`[源]` |
| 慣例 | 一表給背景、一表給精靈（可由 PPUCTRL 切換）`[源]` |

> `[推論]` **這是紅白機美術的根本限制**：畫面上同一瞬間最多只有 256 個背景磁磚圖案 + 256 個精靈磁磚圖案可選。一個 16×16 的敵人＝4 個磁磚、一個 32×32 的中魔王＝16 個磁磚。若不做 CHR bank switching，一整個關卡的所有地形 + 所有敵人 + 字型都必須塞進這 512 格裡。**磁磚重用（tile reuse）不是風格，是數學。**

### 3.3 名稱表與屬性表（Nametable / Attribute Table）

| 項目 | 數值 |
|---|---|
| 一個名稱表 | **1024 bytes**：960 bytes（30 列 × 32 行磁磚 = 256×240 像素）+ 64 bytes 屬性表 `[源]` |
| 位址 | $2000（左上）、$2400（右上）、$2800（左下）、$2C00（右下）`[源]` |
| **主機只有 2 KB VRAM** | 只夠 2 個名稱表，第 3、4 個靠鏡像或卡帶自帶 VRAM `[源]` |
| 屬性表 | 每 byte 管 **32×32 像素**，內分 4 個 **16×16 像素**象限，每象限 2 bit 選 4 組背景調色盤之一 `[源]` |

**鏡像模式（由卡帶接線 / mapper 決定）：**

| 模式 | 行為 | 適合 |
|---|---|---|
| **垂直鏡像**（左右兩張不同） | $2000/$2800 相同、$2400/$2C00 相同 | **水平捲動**卷軸（Super Mario Bros.）`[源]`/`[推論]` |
| **水平鏡像**（上下兩張不同） | $2000/$2400 相同、$2800/$2C00 相同 | **垂直捲動**（Ice Climber、Kid Icarus）`[推論]` |
| **單畫面（single-screen）** | 四張全指向同一張 | 不捲動或整頁翻頁（MMC1 支援）`[源]` |
| **四畫面（four-screen）** | 卡帶額外提供 2 KB VRAM，四張獨立 | **全向捲動**（Gauntlet、Rad Racer II）`[源]`/`[推論]` |

> `[推論]` 這解釋了為什麼**《薩爾達傳說》是「一畫面一畫面翻頁」而不是自由捲動**：只有 2 KB VRAM、垂直與水平鏡像二選一，要做順暢的四向捲動就得付四畫面 VRAM 的錢。也解釋了為什麼《銀河戰士》房間切換時會有一個明顯的捲動轉場——它在切換鏡像模式。

### 3.4 調色盤

### 3.5 精靈（Sprite / OAM）

| 項目 | 數值 |
|---|---|
| OAM 大小 | **256 bytes，最多 64 個精靈** `[源]` |
| 每精靈 4 bytes | Byte0 = Y（實際位置需 −1，$EF–$FF 會隱藏）、Byte1 = 磁磚編號、Byte2 = 屬性（調色盤 / 優先度 / 翻轉）、Byte3 = X `[源]` |
| **每掃描線上限** | PPU 的 secondary OAM 只有 **32 bytes（8 個精靈）** → **每條掃描線最多 8 個精靈** `[源]` |
| 超過時 | 設定 sprite overflow 旗標（但該旗標**有硬體 bug**：剛好 8 個時行為錯誤，「沒有遊戲依賴這個 bug 的行為」）`[源]` |
| 尺寸模式 | **8×8** 或 **8×16**（全域，不能逐精靈設定）`[源]` |
| 8×16 模式 | 磁磚編號 bit0 決定用哪張圖樣表，下半自動用下一個磁磚 `[源]` |
| 顏色 | 每精靈 4 組精靈盤擇一，**3 色 + 透明** `[源]` |
| DMA | 寫 $4014 → 從 CPU RAM 搬 256 bytes 到 OAM，**513（+1）cycle，期間 CPU 暫停** `[源]` |

**8×8 vs 8×16 取捨** `[源]`

| | 8×8 | 8×16 |
|---|---|---|
| 適合 | 小子彈、煙霧、拼圖塊；動畫可只換局部磁磚（例如只換腳）；進出畫面邊緣的「跳出感」較輕 | 大物件覆蓋面積大、OAM 條目省一半、CPU 管理成本低；**可同時取用兩張圖樣表** |
| 缺點 | 大角色要用掉很多 OAM 條目 | 小物件浪費圖樣表空間；額外的 PA12 變化**會干擾 MMC3 的掃描線計數器** |
| 代表作 | Super Mario Bros.、Mega Man | **SMB2、SMB3、Zelda II、TMNT**、Crystal Mines、Alfred Chicken |

**精靈 0 命中（Sprite 0 Hit）** `[源]`
- 條件：精靈 #0 的**不透明像素**與背景的**不透明像素**重疊時，PPUSTATUS bit6 置 1。
- 必要條件：背景與精靈都在渲染中、不在左邊 8 像素裁切區（x ≠ 0–7）、兩者 CHR index 皆 ≠ %00。
- 每影格只會觸發第一次；在預渲染線清除。
- **與精靈優先度無關**——即使精靈 0 被背景遮住也算命中。

> `[推論]` 典型用法：把精靈 0 放在狀態列與遊戲畫面的分界線上（常常是 HUD 裡某個一定不透明的圖示角落），主程式在畫面期間輪詢 $2002 等 bit6 變 1，命中的瞬間立刻改寫 $2005/$2000，讓下半畫面用另一組捲動值 → **固定狀態列 + 捲動關卡**。代價是輪詢期間 CPU 被綁死，算不了別的東西；這也是為什麼 MMC3 的掃描線 IRQ 一出現，1988 年後的遊戲畫面立刻變複雜。

### 3.6 捲動與畫面分割

| 概念 | 說明 |
|---|---|
| 捲動暫存器 | $2005（PPUSCROLL，寫兩次：X 然後 Y）、$2000 bit0–1 選基底名稱表 `[源]` |
| 內部暫存器 | **v**（15 bit，目前 VRAM 位址）、**t**（暫存位址，VBlank 結束時 t→v）、**x**（3 bit fine X）、**w**（寫入切換旗標）`[源]` |
| 編碼 | `yyy NN YYYYY XXXXX` = fine Y / 名稱表選擇 / coarse Y / coarse X `[源]` |
| 生效時機 | 寫進 PPUSCROLL 的捲動值「在 VBlank 結束、渲染開始前才套用」`[源]` |
| 畫面中途只改 X | 第一次寫 $2005 立即更新 fine X，coarse X 在掃描線結束的 dot 257 才更新 `[源]` |
| 畫面中途改 X+Y | 需要 4 次寫入，順序 **$2006, $2005, $2005, $2006**，且「最後兩次必須在 hblank（cycle 256 之後）內完成」才不會出現雜訊 `[源]` |

> `[推論]` 三種分割畫面的手段，由簡到難：
> 1. **精靈 0 命中**（免 mapper，但只能分割一次、位置受精靈 0 位置限制、要燒 CPU 輪詢）——SMB、SMB3 的狀態列。
> 2. **MMC3 掃描線 IRQ**（可在任意掃描線切、可多次）——SMB3 的地圖、Kirby's Adventure 的多層效果。
> 3. **每掃描線都切（IRQ 或 cycle-timed code）**＝假視差、水面波紋、Mode-7 風格拉伸——極耗 CPU，通常只在演出畫面用。

### 3.7 VBlank 能更新多少資料

| 項目 | 數值 |
|---|---|
| VBlank 長度 | 20 掃描線 = 20 × 341 ÷ 3 ≈ **2,273 CPU cycle** `[源]` |
| 扣除 NMI 進出開銷後可用 | 約 2,250 cycle `[源]` |
| 實務吞吐 | 「適度展開的 VRAM 寫入程式，NTSC 的 VBlank 大約可以複製 **160 bytes**，外加 OAM 顯示清單」`[源]` |
| 極限最佳化 | 有開發者達到約 **200 bytes / 影格**（約 8 cycle / byte）`[源]` |
| 換算 | 160 bytes ≈ **10 個 CHR 磁磚**，或 **8 個磁磚 + 一列名稱表 / 一欄名稱表 / 整組調色盤** `[源]` |

> `[推論]` 這條數字是「為什麼紅白機遊戲的關卡是這樣長的」的直接原因。水平捲動時，每前進 8 像素就需要寫入**一欄 30 個磁磚 + 8 bytes 屬性**（約 38 bytes），剛好塞得進 VBlank。所以**捲動速度上限大約是每影格 8 像素**（更快就要一次寫兩欄，VBlank 會爆）。SMB 的最快捲動速度就落在這個量級。

## 4. APU：音訊處理器

### 4.1 五聲道總覽

| 聲道 | 暫存器 | 音量控制 | 音高解析度 | 特徵 | 典型用途 |
|---|---|---|---|---|---|
| **方波 1** | $4000–$4003 | 4 bit（固定音量或包絡衰減）`[源]` | 11 bit timer `[源]` | 4 種占空比 + **掃頻（sweep）** | 主旋律 |
| **方波 2** | $4004–$4007 | 同上 | 同上 | 同上 | 和聲 / 對位 |
| **三角波** | $4008–$400B | **無音量控制**，固定 **4 bit 輸出、32 階梯波形** `[源]` | 11 bit（可比方波低一個八度）`[推論]` | 有 length counter + 7 bit linear counter；「靜音只是停止，會維持最後的輸出值而非歸零」`[源]` | 貝斯線、大鼓 |
| **雜訊** | $400C–$400F | 4 bit（同包絡）`[源]` | **16 種週期** 查表 `[源]` | 15 bit LFSR；mode bit 切長 / 短模式 | 打擊樂、爆炸、風聲 |
| **DMC / DPCM** | $4010–$4013 | 7 bit 輸出位準（可直接寫 $4011）`[源]` | **16 種取樣率** `[源]` | 1 bit 差分編碼 | 鼓組取樣、人聲、低音 |
| 控制 | $4015（聲道啟用 / 狀態）、$4017（frame counter，4 或 5 步模式，驅動包絡 / 掃頻 / length counter）`[源]` |

### 4.2 方波細節

**占空比表** `[源]`

| duty 值 | 百分比 | 序列 | 音色印象 |
|---|---|---|---|
| 0 | **12.5%** | `0 1 0 0 0 0 0 0` | 細、尖、鼻音（常用於副旋律）`[推論]` |
| 1 | **25%** | `0 1 1 0 0 0 0 0` | 8 位元最經典的「主旋律音色」`[推論]` |
| 2 | **50%** | `0 1 1 1 1 0 0 0` | 圓潤、像單簧管，音量感最飽滿 `[推論]` |
| 3 | **25% 反相** | `1 0 0 1 1 1 1 1` | 聽感等同 75%，與 duty 1 同音色但相位相反 `[源]` |

- 頻率公式：`f = f_CPU / (16 × (t + 1))`，t 為 11 bit timer；NTSC 下 f_CPU = 1.789773 MHz。`[源]`
- **t < 8 時該方波會被靜音** `[源]` → 這是高音區的硬上限。
- 掃頻單元（$4001 / $4005，bitfield `EPPP.NSSS`）可自動連續改變音高 `[源]`；典型用途是雷射音、跳躍音 `[推論]`。

### 4.3 雜訊細節

- 15 bit LFSR，回授 = bit0 XOR（mode=1 時 bit6，否則 bit1），右移後填入 bit14。`[源]`
- **長模式（mode=0）**：偽隨機序列 **32767 步** → 聽起來像「沙沙」的白雜訊。`[源]`
- **短模式（mode=1）**：序列只有 **93 或 31 步** → 聽起來是金屬感的「嗡嗡 / 機械音」。`[源]`
- **16 種週期表（NTSC，單位 CPU cycle）**：4, 8, 16, 32, 64, 96, 128, 160, 202, 254, 380, 508, 762, 1016, 2034, 4068 `[源]`
- PAL 的表不同：4, 8, 14, 30, 60, 88, 118, 148, 188, 236, 354, 472, 708, 944, 1890, 3778 `[源]`

> `[推論]` 鼓組配置慣例：**短週期（index 0–3）＝ hi-hat / 沙鈴；中週期＝小鼓；長週期 + 快速包絡＝大鼓或爆炸**。短模式則拿來做電子感的音效。

### 4.4 DPCM / DMC 細節

| 項目 | 數值 |
|---|---|
| 編碼 | **1 bit 差分（delta）**：bit=1 輸出計數器 +2、bit=0 −2，超出 7 bit 範圍時**夾住不溢位** `[源]` |
| 輸出 | 7 bit 位準（0–127），持續輸出給混音器 `[源]` |
| 取樣率 | **16 種**；NTSC 從 **54 Hz 到 33,143.9 Hz**；PAL 50 Hz–33,252.1 Hz `[源]` |
| 樣本位置 | **必須放在 $C000–$FFFF** `[源]` |
| 樣本長度 | 最長 **4,097 bytes**（長度暫存器 = $FF 時）`[源]` |
| 代價 | 自動播放時 **CPU 每讀一個樣本 byte 會被 stall 1–4 cycle** `[源]` |
| 已知 bug | DMC DMA 與手把讀取衝突，會「吃掉回報中的一個 bit，並在 Right 的位置多出一個 1」→ **幽靈右鍵** `[源]` |

> `[推論]` DPCM 是紅白機最貴的聲道：吃 ROM（4 KB 只夠一段很短的鼓聲）、吃 $C000–$FFFF 的黃金位址空間、還會偷 CPU cycle 並弄壞手把輸入。所以典型用法是**只放 3–5 個短鼓組樣本**（大鼓、小鼓、tom），把三角波釋放出來專職做貝斯——《超級瑪利歐兄弟 3》《洛克人 3》之後的音樂厚度就是這樣來的。用來做人聲（如《忍者龍劍傳》的少數語音）則是奢侈品。

### 4.5 混音特性（非線性）

**精確公式** `[源]`：
```
pulse_out = 95.88 / ((8128 / (pulse1 + pulse2)) + 100)
tnd_out   = 159.79 / ((1 / ((triangle/8227) + (noise/12241) + (dmc/22638))) + 100)
output    = pulse_out + tnd_out            // 範圍 0.0 – 1.0
```
（任一組全為 0 時，該組結果視為 0，避免除以 0。`[源]`）

**線性近似** `[源]`：
```
pulse_out = 0.00752 × (pulse1 + pulse2)
tnd_out   = 0.00851 × triangle + 0.00494 × noise + 0.00335 × dmc
```

> `[推論]` 非線性的聽感後果：**兩個方波同時放到最大音量時，總和「小於」兩倍**（有壓縮感）；而且三角/雜訊/DMC 共用一個 DAC，**DMC 播放時會把三角波和雜訊壓下去**。這就是為什麼真機上鼓一打、貝斯就有種被「側鏈壓縮」的律動感。若要在 Web Audio 重現紅白機味道，**照抄非線性公式比調 EQ 有效得多**。

### 4.6 音樂驅動程式（sound driver）概念

| 概念 | 說明 |
|---|---|
| 為什麼需要 driver | APU 本身只有暫存器，沒有「音符」「樂器」的概念；必須有一段每影格（60 Hz）跑一次的程式去寫暫存器 `[推論]` |
| **NSF 的陷阱** | FamiTracker 匯出的 NSF 內含的 replayer「能處理所有 tracker 功能，但**不是為遊戲最佳化的**：吃很多 ROM、RAM、CPU 時間，而且無法處理音效」`[源]` |
| 遊戲用 driver | **FamiTone2 / FamiTone4 / FamiTone5**（Shiru / nesdoug）、**GGSound**（NESmaker 採用）、**Pently**、**FamiStudio sound engine**（改自 FamiTone2）`[源]` |
| 工作流程 | FamiTracker 或 FamiStudio 作曲 → 文字匯出 → 轉換腳本（如 GGSound 的 `ft_txt_to_asm.py`）→ 組譯進 ROM `[源]` |
| 常見架構 | 每影格：更新 tempo 計數 → 讀 pattern 取得音符 / 效果 → 套用樂器包絡（音量、琶音、音高、占空比四條包絡）→ 寫 $4000–$4013；音效以優先度搶佔某一聲道 `[推論]` |

## 5. 卡帶與 mapper

### 5.1 為什麼需要 mapper

CPU 只留 $8000–$FFFF **32 KB** 給卡帶 ROM、PPU 只有 8 KB CHR 空間與 2 KB VRAM。`[源]`
Mapper 是卡帶上的晶片，負責：**(1) bank switching 換頁**、**(2) 控制鏡像模式**、**(3) 提供額外 RAM / 電池存檔**、**(4) 產生 IRQ**、**(5) 少數還提供擴充音源**。`[源]`

### 5.2 主要 mapper 對照表

| iNES # | 名稱 | PRG 上限 | CHR | 換頁粒度 | IRQ | 額外 | 代表遊戲 |
|---|---|---|---|---|---|---|---|
| **000** | **NROM** | 16 KB（NROM-128）/ 32 KB（NROM-256）`[源]` | 8 KB ROM 固定 | 無 | 無 | 鏡像由焊點決定 `[源]` | Super Mario Bros.、Donkey Kong、Mario Bros.、Galaxian、Balloon Fight `[源]` |
| **001** | **MMC1** | 256 KB（部分板子 512 KB）`[源]` | 128 KB，8 KB 或 2×4 KB `[源]` | PRG 16 KB / CHR 4 KB | 無 | **序列式寫入（連寫 5 次才生效）**、支援**單畫面鏡像**、電池 PRG-RAM 最大 32 KB `[源]` | The Legend of Zelda、Metroid、Dr. Mario、Mega Man 2、Final Fantasy `[源]` |

### 5.3 CHR ROM vs CHR RAM

| | **CHR ROM** | **CHR RAM** |
|---|---|---|
| 本質 | 卡帶上獨立的圖形 ROM 晶片 `[源]` | 卡帶上的 SRAM，開機後由 CPU 從 PRG ROM 複製進去 `[源]` |
| 換磁磚 | 「**很快、不需要 VBlank 時間、可以在畫面中途做**」`[源]` | 必須在 **VBlank 用 CPU 搬**，約 **10 個磁磚 / 影格** `[源]` |
| 圖形總量 | 受 CHR ROM 容量 + mapper banking 限制（MMC3 可到 256 KB）`[源]` | 只有 8 KB 「視窗」，但可存**壓縮資料**在 PRG，需要時解壓 `[源]` |
| 彈性 | 動畫需要「每個影格一個 bank」`[源]` | 可以逐磁磚小幅替換、做比例字型、動態合成圖像 `[源]` |
| 成本 | 需燒錄額外 ROM 晶片 `[源]` | 只需一顆改接線的 SRAM，且**剩餘空間可加電池當存檔用** `[源]` |
| 代表作 | Super Mario Bros. 3、Jurassic Park、Cosmic Epsilon `[源]` | Hatris、Cocoron、**Battletoads**、Elite、Final Fantasy（角色 / 道具種類多）`[源]` |

> `[推論]` 選擇準則：**平台動作 / 卷軸射擊 → CHR ROM + MMC3**（能無成本做磁磚動畫，如 SMB3 的問號磚、水面）；**RPG / 文字多 / 需要動態拼字 → CHR RAM**（字型與圖像可壓縮，剩下的 SRAM 還能拿來存檔）。

### 5.4 電池備份 SRAM 與存檔

| 方式 | 硬體需求 | 例子 |
|---|---|---|
| **電池備份 SRAM** | $6000–$7FFF 的 SRAM + 一顆鈕扣電池 + 少量被動元件 | 《The Legend of Zelda》《Final Fantasy》`[源]` |
| **只有 WRAM（無電池）** | 同樣的 SRAM，**沒接電池** | 《Metroid》的 PCB 與 Zelda 幾乎相同，**差別就只在有沒有電池**與相關元件 `[源]` |
| **密碼（password）** | **零成本** | 《Metroid》用 **64 字元、區分大小寫**的密碼；《Mega Man 2》用點陣式密碼盤重建遊戲狀態 `[源]` |
| **成本現實** | 「SRAM 一直都很貴」，早期簡單遊戲不划算，所以很多複雜遊戲改用密碼 `[源]` |

> `[推論]` 密碼系統本質是「把遊戲狀態壓縮成人類抄得動的字串 + 校驗碼」。設計上的關鍵是**校驗碼**（避免亂輸入產生非法狀態）與**狀態量**（Mega Man 2 只需要記 8 個 boss 是否擊破 + 道具 → 點陣盤剛好夠；Metroid 要記地圖旗標 + 道具 + 飛彈數 → 需要 64 字元）。

## 6. 限制如何塑造遊戲設計

| 硬體限制 | 設計後果 | 代表遊戲與具體做法 |
|---|---|---|
| **圖樣表只有 256 + 256 個磁磚** `[源]` | **磁磚重用 / metatile 系統**：關卡不是畫出來的，是用 16×16 的「大磚」拼出來，再用「畫面 = 大磚 ID 陣列」壓縮 | 《Super Mario Bros.》整個世界由極少的地面 / 磚塊 / 問號 / 管子 / 雲 = 山（同一組磁磚換調色盤！）組成；雲與草叢用**同一組磁磚**，只差調色盤 `[推論，經典公認案例]` |
| **屬性表以 16×16 像素為單位配色** `[源]` | 美術必須「**以 16×16 為色塊格線**」構圖，角色與背景的顏色邊界會被迫對齊格線；否則出現「色彩滲漏」 | 《Mega Man》的背景多為大面積規則磚塊；《Castlevania》的牆面紋理刻意以 2×2 磁磚為週期 `[推論]` |
| **4 組背景盤 + 4 組精靈盤，各 3 色 + 共用底色** `[源]` | **調色盤分工策略**：背景 = 地形 / 裝飾 / 特殊 / HUD；精靈 = 主角 / 敵 A / 敵 B / 特效。同一張圖換調色盤 = 免費的「新敵人」 | 《Super Mario Bros.》的紅 / 綠慢慢龜、地上 / 地下 / 水下關卡用**同一批磁磚換色**；《Mega Man》每個 Robot Master 關卡換一套調色盤產生截然不同的氛圍 `[推論]` |
| **每掃描線 8 精靈** `[源]` | **閃爍（flicker）**：每影格輪替 OAM 順序，讓超出的精靈輪流被畫出來，人眼看成半透明；或用「mask sprite」策略性遮蔽 | 《Mega Man》系列的招牌閃爍；《Castlevania II》《Ninja Gaiden》使用**在 OAM 前段塞空白精靈、以相同 Y 座標蓋掉該掃描線其他精靈**的遮蔽技巧 `[源]` |
| 同上 | **大魔王用「背景」畫，不用精靈** | 因為背景不受 8 精靈限制，只有 16×16 配色格線限制。Mother Brain（《Metroid》）、多數 8 位元大型 boss 的身體是背景層，只有會動的手 / 眼睛 / 彈幕是精靈 `[推論]` |
| **2 KB VRAM，只有 2 個名稱表** `[源]` | **多方向捲動很難**：四向自由捲動需要「四畫面 VRAM」或極高頻寬的動態更新 | 《薩爾達傳說》採**一畫面一畫面翻頁 + 轉場捲動**；《銀河戰士》以房間為單位、切換鏡像模式；真正做四向捲動的《Gauntlet》《Rad Racer II》使用四畫面卡帶 `[源]`/`[推論]` |
| **VBlank 只能寫 ~160 bytes** `[源]` | **捲動速度上限約 8 px / 影格**；關卡設計成「橫向長條」而非開闊區域；捲動時只更新螢幕外的一欄 | 《Super Mario Bros.》**單向水平捲動不能往回走**（省下反向更新的邏輯與頻寬）；《Contra》的橫向關卡也是單向 `[推論]` |
| **無硬體圖層 / 無視差** | **假視差**：用調色盤循環、CHR bank 動畫、或每掃描線改捲動值假裝有第二層 | 《Super Mario Bros. 3》的雲與草；《忍者龍劍傳》演出畫面；水面波紋以逐線捲動實現 `[推論]` |
| **沒有硬體狀態列** | **狀態列 = 畫面分割**：精靈 0 命中（免 mapper）或 MMC3 掃描線 IRQ | 《SMB》《SMB3》用精靈 0；《Kirby's Adventure》用 MMC3 IRQ 做多重分割 `[源]`/`[推論]` |
| **APU 只有 5 聲道且三角波無音量** `[源]` | **聲部分配的鐵律**：方波 1 = 主旋律、方波 2 = 和聲 / 對位、三角波 = 貝斯（偶爾兼大鼓）、雜訊 = 鼓組、DMC = 取樣鼓或省略 | 幾乎所有 NES 名曲皆遵守；近藤浩治《SMB》地上 BGM 就是「2 方波 + 三角貝斯 + 雜訊鼓」的教科書 `[推論]` |
| 同上 | **音效會「吃掉」音樂聲部**：跳躍音搶走方波 2，音樂當下就少一個和聲 | 這是 8 位元音樂「聽起來會抖一下」的原因；driver 需做優先度搶佔 `[推論]` |
| **DPCM 吃 ROM、偷 CPU、弄壞手把** `[源]` | 取樣只用在 3–5 個短鼓聲；很多遊戲乾脆不用 DPCM | 《Mega Man 3》之後用 DPCM 讓鼓變厚；《忍者龍劍傳》的少量語音 `[推論]` |
| **SRAM 昂貴** `[源]` | **密碼系統**成為 8 位元 RPG / 動作遊戲的標準配備 | 《Metroid》64 字元密碼、《Mega Man 2》點陣密碼；《薩爾達傳說》《FF》因銷售預期高而付得起電池 `[源]` |
| **NMI 是唯一穩定心跳** | 遊戲邏輯天然是「**每影格一次**」的固定時間步；物理用定點數（8.8）而非浮點 | 這造就了 8 位元手感的「乾脆、可預測」；也讓 PAL 版整體慢 17% `[推論]` |
| **無硬體碰撞偵測、無乘除法** `[源]` | 碰撞一律 AABB 矩形；地形碰撞查 metatile 屬性表；避免任何需要乘除的運算 | 全平台通用做法 `[推論]` |

## 7. 模擬器準確度與常見坑

### 7.1 主要模擬器比較

| 模擬器 | 定位 | 測試 ROM 通過率（RetroArch core 比較） | 備註 |
|---|---|---|---|
| **Mesen / Mesen2** | 最準確，內建強大除錯器（PPU viewer、event viewer、trace logger、Lua） | **156/156（100%）** `[源]` | 原為 NES 專用，Mesen2 改寫為多主機平台；開發活躍 `[源]` |
| **puNES** | 高準確度 | 153/156（98.08%）`[源]` | |
| **Nestopia UE** | 自稱「cycle-accurate NES & Famicom emulator」 | 148/156（94.87%）`[源]` | CPU / mapper / PPU 表現佳 `[源]` |
| **FCEUX / FCEUmm** | 工具導向：錄影（TAS）、Lua 腳本、除錯 | FCEUmm 約 84/156（53.85%）`[源]` | TASVideos 長年以它為基準；開發重心在錄影 / 腳本而非時序精度，主線自 2023 年後沉寂 `[源]` |

> `[推論]` 開發建議：**用 Mesen 當「真理」**（它的 PPU viewer 能即時看名稱表、CHR、調色盤、OAM，是做 NES 遊戲最有生產力的工具），用 FCEUX 做 Lua 自動化測試，最後務必在 Nestopia 或真機交叉驗證一次。

### 7.2 常見坑（開發者角度）

| 坑 | 說明 |
|---|---|
| **PAL / NTSC 幀率** | NTSC 60.0988 Hz vs PAL 50.0070 Hz `[源]`；PAL 每影格 33,247.5 cycle、VBlank 長達 7,459 cycle `[源]`。**直接把 NTSC 遊戲丟去 PAL，遊戲整體慢約 17%、音樂降速降 pitch** `[源]` |
| PAL 的音訊表不同 | 雜訊週期表、DMC 取樣率表 PAL 版都不一樣 `[源]`；沒重算就會走音 `[推論]` |
| **色彩差異** | 2C02 輸出 NTSC 複合訊號，**沒有唯一 RGB 真值**；PAL 的色相相差約 **15 度** `[源]`。不同模擬器預設調色盤（Mesen NTSC 濾鏡 / FCEUX / Nestopia YIQ）目視差異明顯 `[推論]` |
| **音訊混音差異** | 真機混音是非線性 `[源]`；用線性近似的模擬器在多聲道齊奏時會偏亮、偏吵 `[推論]` |
| $0D「blacker than black」 | 模擬器照畫，真機 / 擷取卡可能出問題 → **永遠用 $0F 當黑** `[源]` |
| **sprite overflow 旗標的 bug** | 剛好 8 個精靈時行為錯誤，「沒有遊戲依賴這個 bug」`[源]` → 不要拿這個旗標當邏輯依據 `[推論]` |
| **DMC 與手把衝突** | 使用 DPCM 時手把會出現幽靈「右」鍵 `[源]`；解法是連讀兩次比對，或避開 DMC 播放期間讀手把 `[推論]` |
| **MMC3 IRQ 與 8×16 精靈** | 8×16 精靈會取用兩張圖樣表，「額外的 PA12 上升會混亂 MMC3 的掃描線計數器」`[源]` |
| **bus conflict** | UxROM / CNROM 原版板子有 bus conflict，寫 mapper 暫存器時值會與該位址的 ROM 內容 AND `[源]`；模擬器有的模擬、有的不模擬 → **程式一定要寫成 bus-conflict-safe**（寫入位址的 ROM 內容剛好等於要寫的值）`[推論]` |
| **開機時序** | PPU 開機後需要等待兩次 VBlank 才穩定；沒等就寫 PPU，模擬器能跑、真機黑畫面 `[推論]` |
| **VBlank 超時** | 在 NMI 裡多寫幾十個 byte 就會超過 2,273 cycle，導致渲染開啟太晚，畫面頂端出現雜線 `[源]`/`[推論]` |
| **iNES vs NES 2.0 header** | 舊 iNES header 無法表達大容量、submapper、PAL/NTSC 等資訊；新專案應輸出 NES 2.0 `[推論]` |

| **容量** | 最大授權 NES 遊戲 | Kirby's Adventure **768 KB** |
| | 最大授權 Famicom 遊戲 | Metal Slader Glory **1024 KB** |
| **PAL 對照** | CPU / 影格率 / cycle / VBlank | 1.662607 MHz / 50.0070 Hz / 33,247.5 / 7,459 cycle（70 線） |
