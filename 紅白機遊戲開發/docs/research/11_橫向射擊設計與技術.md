# 11 橫向射擊（橫捲 STG）設計與技術 — NES 實作指南

> 本文是 R2《星塵巡航艦》的規格來源。技術段落以 NESdev Wiki / NESdev Forums 的一手資料為準，設計段落以 shmups.system11.org 社群、Shmups Wiki、開發者訪談與遊戲資料庫為準。
> 所有結論標 `[源]`（有網址佐證）或 `[推論]`（本文的推導 / 建議）。**遊戲內容一律原創，本文只借鑑機制與數字。**

## 摘要（10 行內）

1. NES 的橫向射擊被三個硬上限決定：OAM **64 個精靈**（256 byte，每個 4 byte）、**每掃描線 8 個**、VBlank 只能寫約 **160 byte** 名稱表 [源]。
2. 超過 8 個就會「消失」而非「閃爍」；閃爍是**軟體**做出來的——每幀輪替 OAM 槽位順序（OAM cycling），讓被丟掉的對象輪流換人 [源]。
3. 《宇宙巡航艦》（Gradius NES）與《Parodius》是 NES 上閃爍最兇的代表；Gradius NES 用 **CNROM（mapper 3）**，沒有 IRQ，狀態列只能靠 sprite 0 命中 [源]。
4. Konami 最後一款 FC 射擊《Crisis Force》改用自家 **VRC4e**，才換到四向捲動 + 大型魔王 [源]；《Gun-Nac》甚至給玩家「減少閃爍」的開關 [源]。
5. 瞄準射擊不要用三角函數：把角度切成 256 份查 SIN/COS 表，atan2 用「反射到第一卦限 + 斜率查表」，NES 實測約 **400 cycle**（< 4 條掃描線）[源]。
6. 自機碰撞框**必須**遠小於精靈——連 1985 年的 Gradius 都已經這麼做；業界常見是 1~4 px 的中心點 [源]。
7. 復活制度是橫捲 STG 的分水嶺：Gradius / R-Type = **檢查點 + 全裝備清空**（催生「Gradius 症候群」）；沙羅曼蛇 / Life Force = **原地復活**，並保留部分強化 [源]。
8. rank（動態難度）在 Gradius 是「難度設定 + 關卡 / 循環 + 已啟用強化 + 特殊項」的加總，III 的範圍是 0~31，初代封頂 15 [源]。
9. 大型魔王的標準解法是「背景磚做本體 + 精靈只做會動的部位」，因為背景不吃每線 8 精靈的限制，代價是一幀只能換約 32 塊磚 [源]。
10. 文末給《星塵巡航艦》**8 種敵人原型 / 3 種魔王原型 / 關卡 1 逐欄節奏表 / HUD 版面草案**，可直接當 ship / stage / audio agent 的實作輸入 [推論]。

## ① 三個硬上限與本專案的對應

| 限制 | 硬體數字 | 來源 | 對橫向射擊的意義 | 本專案（engine/shmup.js）對應 |
|---|---|---|---|---|
| OAM 容量 | **64 個精靈 × 4 byte = 256 byte** | [源] NESdev PPU OAM | 船 + 選項 + 自機彈 + 敵 + 敵彈 + 爆炸全部擠在 64 格 | `NES.SH.OAM` 收集 → 排序 → 寫 0..63，超過計 `dropped` |
| 每掃描線 | **8 個**（secondary OAM 只有 32 byte = 8 × 4） | [源] NESdev PPU OAM / PPU sprite evaluation | 一排編隊敵人只要同 y 就會少人 | 同 prio 每幀輪替起點（軟體 sprite cycling） |
| OAM DMA | `$4014` 一次 **513 CPU cycle**（奇數週期 +1） | [源] NESdev PPU OAM | 一幀只能整批傳一次 OAM | `ppu.sprite()` 走獨立 `oam` 預算通道（256 byte） |
| 名稱表寫入 | NTSC VBlank 實務 **約 160 byte**（保守 64、理論上限約 4 欄 + 屬性） | [源] NESdev forums / The frame and NMIs | 每幀最多補「一欄磚 + 屬性」；換場景不能一次重畫 | `NES.SH.Scroller` 每幀 ≤ 45 byte（30 磚 + 15 屬性），`budget.over` 必須為 0 |
| 精靈優先權 | OAM 位址小的**蓋在**位址大的上面；sprite 0 最高、63 最低 | [源] NESdev PPU OAM | 「誰會被丟掉」＝「誰的 OAM index 大」 | `add({prio})`，0 = 船 / 選項 / 自機彈 … 4 = 爆炸 |
| 精靈溢位旗標 | `$2002` bit 5，**硬體實作有 bug**，會去查錯的 OAM index | [源] NESdev PPU sprite evaluation | 不能拿來當「這線超過 8 個」的可靠偵測 | 本專案用軟體統計（`ppu.stats` / `nes_lint`） |
| 隱藏精靈 | y = `$EF`~`$FF`（239~255）即不顯示 | [源] NESdev PPU OAM | 「刪除」物件 = 把 y 寫 255，不用真的搬 OAM | `OAM.add` 對 y ≥ 240 自動略過 |

- [推論] 對《星塵巡航艦》的直接結論：**畫面上「會動的東西」總量請以 40~48 個精靈為設計目標，留 16~24 格給爆炸與魔王**。超過 48 就開始出現肉眼可辨的成片閃爍。
- [推論] 本專案遊戲區只有 **0..207 掃描線**（HUD 佔 208..239），等於 **26 條 8px 精靈列**；每列最多 8 個 ⇒ 理論同屏 208 個，實務被 OAM 64 卡死。瓶頸永遠是 OAM 而不是掃描線，除非敵人排成一直線。

## ② OAM 64 精靈的分配與優先權

### 2.1 優先權 = OAM index，這是唯一的規則

NESdev 講得很清楚：**「OAM 位址較低的精靈會蓋住位址較高的精靈」**，而且「如果任一掃描線上超過 8 個，只有優先權最高的 8 個會被畫出來」[源]。屬性位元組 bit 5 的 priority 只決定「在背景前 / 後」，**不影響精靈彼此的先後**[源]。

⇒ 所以「精靈排序」與「誰被丟掉」是同一件事，不能分開設計。

### 2.2 橫向射擊的建議分配表

| prio | 物件 | 建議槽數 | 理由 |
|---|---|---|---|
| 0 | 自機（16×8 = 2 顆） | 2 | 自機絕不可閃爍，玩家靠它定位 [推論] |
| 0 | 選項 / Option（每顆 1 顆精靈） | 2 | 與自機同級；它代表火力位置 [推論] |
| 1 | 自機彈 / 雷射段 / 飛彈 | 6 | 打不到東西比看不到敵人更讓人抓狂 [推論] |
| 2 | 敵彈 | 12 | **敵彈閃爍 = 不公平**，優先權必須高於敵機本體 [源+推論] |
| 3 | 敵機本體 | 28 | 最先被犧牲的一層；玩家仍能從敵彈推測位置 |
| 4 | 爆炸 / 特效 / 掉落膠囊 | 14 | 純表演，掉了不影響判定（膠囊可用磚做提示）[推論] |
| — | 保留（sprite 0 / HUD 指標） | 0~1 | 本專案用掃描線分割，不需要真 sprite 0 |
| 合計 | | 64 | |

> [推論] 「敵彈優先權高於敵機」是橫捲 STG 的鐵則，跟平台動作遊戲的直覺相反。平台遊戲把敵人本體放前面沒問題，射擊遊戲把敵彈丟掉會直接造成「不明死亡」。

### 2.3 兩種 OAM 寫入策略

| 策略 | 做法 | 優點 | 缺點 |
|---|---|---|---|
| **固定分區** | 槽 0-3 給自機、4-9 給自機彈、10-21 給敵彈…各區固定 | 實作最簡單、除錯容易 | 區內滿了不能借用別區，浪費 |
| **依 prio 排序後緊縮**（本專案） | 每幀收集 → 依 prio 穩定排序 → 依序寫 0..63 | 不浪費一格；閃爍層級可控 | 每幀要排序（64 筆，成本可忽略） |
| **隨機洗牌** | 每幀 Fisher-Yates 打亂 0..63 | 閃爍最均勻，N 個物件每個的消失機率 = (N−8)/N | 優先權失控，自機也會閃 [源] |

- [源] NESdev 討論串提到「隨機洗牌能保證閃爍均勻分布，但計算較貴、視覺較佳」；同串也提到「Tokumaru 的做法是打亂**物件**的繪製順序，但保留物件**內部**各精靈的層次」。
- [推論] 本專案採第二種 + 「同 prio 內每幀輪替起點」，等於在保留分層的前提下做局部洗牌，是成本與品質的平衡點。

## ③ 每線 8 精靈：閃爍與輪替策略

### 3.1 為什麼要「製造」閃爍

硬體行為是**消失（dropout）**，不是閃爍。NESdev 的說法：「在 NES 上唯一能把 dropout 變成 flicker 的方法，就是每幀旋轉 OAM 本身，讓精靈每幀都落在新的 OAM 槽，於是輪流被丟掉、看起來就是閃爍」[源]。

| 現象 | 玩家感受 | 可接受度 |
|---|---|---|
| Dropout（固定同一批消失） | 「這隻敵人根本沒畫出來」→ 不明死亡 | ✗ 不可接受 |
| Flicker（輪流消失） | 「畫面很忙但我看得到大概位置」 | ✓ NES 時代的共識 |
| Slowdown（幀率掉） | 「變慢了但看得清楚」 | ✓ 街機 STG 甚至刻意保留 |

### 3.2 四種實作手法

| 手法 | 具體做法 | 成本 | 代表 |
|---|---|---|---|
| **固定步進旋轉** | 每幀把 OAM 寫入指標的起點 +4（或 +8） | 幾乎為 0 | 最通用 |
| **質數步進（+9×4）** | 「每加一個精靈就把指標 +9×4 = +36」，繞回時剛好填滿 64 格 | 極低 | [源] NESdev「stupid easy way」 |
| **$34 偏移法** | 清 OAM 時 `Offset += $34; CurrIndex = Offset`，每配一顆 `CurrIndex -= $0C` | 低 | [源] Dwedit 於 NESdev 論壇 |
| **完全洗牌** | 每幀 Fisher-Yates 打亂 0..63 對照表 | 中（64 次交換 + 亂數） | [源] Bregalad 於 NESdev 論壇 |
| **條件式閃爍** | 先統計每條掃描線的精靈數，只有 > 8 的那幾條參與輪替 | 高（要掃 240 線） | [源] NESdev「Implementing Conditional Sprite Flickering」 |

- [推論] 「質數步進」之所以有效，是因為 9 與 16（64 ÷ 4）互質，指標會走遍所有 4-byte 對齊位置後才回到原點；換成 +8×4 就只會踩 8 個位置，輪替效果差一半。
- [源] NESdev 也提到**設計層面**的兩招：①「把精靈換成背景磚」（SMB 的 `?` 磚與磚塊就是這樣省下來的）②「刻意讓精靈互相重疊」，這樣掉一顆遮住的內容比較少。

### 3.3 三款 FC 射擊各用什麼

| 作品 | 閃爍狀況 | 佐證 | [推論] 推測策略 |
|---|---|---|---|
| **宇宙巡航艦（Gradius, FC 1986）** | 嚴重；NESdev 直接點名「Gradius 系列與史上閃爍 + 降速最慘的 Parodius 就是這樣」[源] | NESdev 論壇；Gradius NES 用 mapper 3 CNROM，無 IRQ、無額外 RAM [源] | 簡單的固定步進輪替；同時**大砍規格**（選項從 4 顆減到 2 顆、雷射不再貫穿整個畫面）來降低同屏精靈數 [源] |
| **沙羅曼蛇 / Life Force（FC 1987）** | 仍有閃爍，但編隊規模比街機小 | 移植時刪掉 Meteorite Space / Asteroid Hell 兩關、選項上限 2 顆（街機 3 顆）[源] | 用「減少同屏物件」而非「更好的輪替」來解問題 [推論] |
| **超惑星戰記（Blaster Master, FC 1988）** | **不是橫向射擊**（載具 / 步行混合的探索動作），本文只把它當復活制度的對照 | Wikipedia [源] | — |
| **Crisis Force（FC 1991，Konami 最後一款 FC 射擊）** | Famitsu 評論仍批評「物件多時會閃」[源] | TCRF 指出用 **VRC4e** | 有 mapper IRQ 可做多段分割，把「大型魔王」改用背景層畫，把精靈省給彈幕 [推論] |
| **Gun-Nac（FC 1990，Compile）** | **內建「減少閃爍」選項**讓玩家自選 flicker / slowdown [源] | Destructoid 比較文 | 提供兩套策略切換：輪替（閃）vs 降速（不閃）[推論] |

> [推論] 給本專案的結論：我們是「現代程式還原」，可以直接做**最好的那一種**——同 prio 內每幀輪替起點 + 分層優先權。這比 1986 年的 Gradius 好，但仍嚴守「每線 8 個」的視覺結果，所以看起來仍是 NES。

### 3.4 驗收標準

| 檢查項 | 判定 | 工具 |
|---|---|---|
| 任一掃描線同幀 > 8 個精靈被畫出 | ✗ 不合格 | `engine/nes_lint.js` 執行期 |
| 同一物件連續 3 幀都被丟掉 | ✗ 輪替沒生效 | `test_shmup.py`：連號 16 個同線精靈，兩幀聯集應為 16 |
| 自機 / 選項 / 敵彈曾被丟掉 | ✗ 優先權設錯 | `OAM.dropped` 只允許 prio ≥ 3 |
| `dropped > 0` 的幀數比例 | > 20% 表示編隊設計過密 | stage agent 調整出怪表 |

## ④ 子彈池與物件上限

### 4.1 為什麼一定要「池」而不是動態配置

NES 沒有堆積（heap），所有物件都是**固定大小的陣列 + alive 旗標**。這帶來一個 NES 特有的設計語彙：

> **「池滿了就不生成」**——不排隊、不擠掉舊的、不擴充。射一發沒子彈就是沒射出去。

- [推論] 這其實是**手感的一部分**：Gradius 的「自機彈同時最多 2 發」讓玩家必須貼近開火（近距離 = 子彈回收快 = DPS 高），是刻意的風險回報設計，不是偷工減料。
- 本專案 `NES.SH.Pool(n, factory)` 的 `alloc()` 失敗回 `null`，正是這個語彙的實作。

### 4.2 建議池大小表（《星塵巡航艦》）

| 池 | 建議上限 | 每個佔 OAM | 最壞 OAM 佔用 | 理由 |
|---|---|---|---|---|
| 自機彈（一般 / 雙向） | **4**（同時在畫面上，含斜上彈） | 1 | 4 | Gradius 是 2 發；我們有雙向，實質等價 [推論] |
| 雷射段 | **4 段**（一條雷射，每段 1 顆精靈） | 1 | 4 | 與一般彈互斥，不疊加 |
| 飛彈 | **2** | 1 | 2 | 沿地面滾動，壽命長，要限量 |
| 敵人 | **12** | 1~4 | 約 20 | 編隊 5 隻 + 砲台 3 + 散兵 4 |
| 敵彈 | **16** | 1 | 16 | 超過 16 在 NES 上一定閃到看不見 [推論] |
| 膠囊 | **4** | 1 | 4 | 同時 4 顆已經很多 |
| 爆炸 | **8**（4 幀動畫） | 1 | 8 | 最先被犧牲 |
| 魔王部位 | **1 隻 × 最多 12 顆精靈** | — | 12 | 本體盡量用背景磚 |
| **合計最壞** | | | **約 70** | 超過 64 ⇒ 靠 prio 丟爆炸與敵機，符合預期 |

### 4.3 池的記憶體與遍歷

| 項 | 做法 | 備註 |
|---|---|---|
| 配置 | 開機時一次建好 n 個物件，之後只切換 `alive` | 零 GC；本專案要求「無 GC」 |
| 遍歷 | `each(fn)` 只走 `alive` 的；**不要**用 `filter` / `map`（會配置新陣列） | 現代 JS 陷阱 |
| 釋放 | `free(obj)` 只設 `alive = false`，不搬移 | 保持索引穩定，測試好寫 |
| 出界回收 | 每幀檢查 `x < -16 || x > 272 || y < -16 || y > 224` | 敵彈忘記回收是最常見的「池滿了」bug [推論] |

## ⑤ 瞄準射擊：角度查表

### 5.1 為什麼不用 `Math.atan2`

- 在真機上根本沒有浮點數與三角函數。為了「原汁原味」，本專案規定用 `NES.SH.atan2` 查表。
- [源] NESdev 上有實測：《Thwaite》用「部分查表式的 atan2」——**把向量反射到第一卦限 → 算斜率（1 次除法）→ 查斜率表 → 反射回去**，整趟約 **400 cycle，不到 4 條掃描線**。
- [源] 另一派更省的做法是**時間式瞄準**：`velocity = (target − position) / 64`，讓子彈在固定 64 幀內抵達目標當時的位置，完全不需要三角函數，也不需要正規化速度。

### 5.2 三種瞄準精度的取捨

| 方案 | 角度數 | 實作 | 手感 | 適用 |
|---|---|---|---|---|
| **8 方向** | 8 | 比較 dx / dy 的符號與大小 | 明顯「格子感」，玩家容易預判 | 雜兵、低階砲台 [推論] |
| **16 方向** | 16 | 8 方向 + 22.5° 中間值（斜率門檻 tan22.5 ≈ 0.414、tan67.5 ≈ 2.414） | 夠圓滑，仍可預判 | **本專案建議的預設** [推論] |
| **256 方向（一圈 = 256）** | 256 | `SIN[256]` / `COS[256]`，8.8 定點（256 = 1.0） | 完全平滑，與街機同級 | 魔王環形彈、追蹤彈 [推論] |

> [源] Contra（NES）反組譯專案的 `Aim Documentation.md` 顯示：白色 blob 敵人用一個 `#$00`~`#$16`（= 23 個值）的瞄準方向變數，`#$00` 是正右方（3 點鐘），順時針遞增。這是「**有限方向表**」在真實 NES 商業遊戲裡的實例。

### 5.3 8.8 定點的角度表規格（本專案）

| 項 | 規格 | 說明 |
|---|---|---|
| 角度單位 | `0..255` = 一整圈（每單位 1.40625°） | 用 `& 255` 就能環繞，不用取模 |
| `SIN[a]` / `COS[a]` | `Int16Array`，值域 `−256..256`（256 = 1.0） | `COS[a] === SIN[(a + 64) & 255]` |
| `aim(sx, sy, tx, ty, speed88)` | 回 `{vx, vy}`，單位 = px/幀 × 256 | `vx = (COS[a] * speed88) >> 8` |
| 誤差要求 | 每個值與 `round(256 * sin(2πa/256))` 誤差 0 | 建表時直接四捨五入，測試逐項比對 |
| `atan2` 八方驗證 | 正右 = 0、右上 = 224、正上 = 192、左上 = 160、正左 = 128 … 允許 ±1 | 注意 **y 軸向下**，所以「上」是角度遞減方向 |

### 5.4 常見彈幕形狀的產生式

| 形狀 | 公式（角度 `a0` = 瞄準角，`n` = 彈數） | 用途 |
|---|---|---|
| 單發瞄準 | `a0` | 砲台基本攻擊 |
| 扇形（spread） | `a0 + (i − (n−1)/2) * step`，`step` 建議 8~16（≈ 11°~22°） | 中階敵人 |
| 環形（ring） | `i * 256 / n` | 魔王爆開型 |
| 螺旋（spiral） | 每 k 幀發一發，角度 `+= step`（step 與 256 互質才不會重疊） | 魔王第二階段 |
| 交錯環（offset ring） | 第 m 波的角度加上 `128 / n` | 讓兩波之間留出「安全縫」[推論] |
| 牆型（wall） | 同角度、不同初始 y，速度略有差 | 逼玩家往固定缺口跑 |

> [推論] NES 的可讀性要求：**同時在畫面上的敵彈 ≤ 16 顆**，而且相鄰兩顆的間距至少 12 px（自機碰撞框 12×6 才過得去）。環形彈 8 顆就已經很滿。

## ⑥ 名稱表欄串流與 VBlank 預算

### 6.1 預算數字

| 數字 | 值 | 來源 |
|---|---|---|
| NTSC VBlank 實務可寫名稱表 / 調色盤 | **約 160 byte**（中度展開迴圈） | [源] NESdev 論壇 |
| 保守常見值 | 多數遊戲每個 NMI **不超過 64 byte** | [源] NESdev 論壇 |
| 理論上限（4 cycle LDA/STA 估算） | 約 284 byte | [源] NESdev 論壇 |
| 用最快緩衝法的實務上限 | **約 4 欄（或 4 列）名稱表 + 對應屬性** | [源] NESdev 論壇 |
| 另外的 OAM DMA | 256 byte / 513 cycle，**不佔上面那 160** | [源] NESdev PPU OAM |
| 捲動 32 px 需要 | 略多於 128 byte / VBlank（「完全在合理範圍內」） | [源] NESdev 論壇 |

- 本專案 `engine/cpu_timing.js` 已把 **160 byte** 設成硬預算，並且 OAM 走獨立通道（256 byte）。R1 的 demo 實測單幀尖峰 51 byte。

### 6.2 一欄要寫多少

| 項目 | byte 數 | 說明 |
|---|---|---|
| 一整欄磚（30 列可見 + 邊界） | **30** | 名稱表 32×30 |
| 對應屬性（每 16×16 一格，一欄 16px 寬 ⇒ 每兩欄才換一次屬性欄） | **8**（15 列 ÷ 2 向上取整）；實務每兩欄寫一次 | 屬性表 8×8 |
| 合計 | **約 38**（尖峰），平均約 34 | 遠低於 160 ✓ |

⇒ [推論] **本專案每幀寫一欄綽綽有餘，甚至支援捲動速度 2 px/幀 以上**（2 px/幀 時每 4 幀寫一欄）。真正的限制是：`camX` 每前進 8 px 就必須補好一欄，否則右緣會出現殘影。

### 6.3 欄串流的實作要點

| 要點 | 做法 | 陷阱 |
|---|---|---|
| 雙名稱表 | 水平捲動用 **垂直鏡像**（左右兩張 NT 並排 512 px 寬） | 鏡像設錯會變成上下接 |
| 寫哪一欄 | `col = (camX >> 3) + 32`（右緣外一欄）；`nt = (col >> 5) & 1`；`ntCol = col & 31` | 一定要「**先寫、後捲**」，否則玩家會看到空欄 |
| 觸發條件 | `(camX & 7) === 0` 且 camX 有前進 | 用 `lastCol` 比對比用餘數安全（速度 > 8 px/幀 時要補多欄） |
| 屬性 | 每 `(col & 1) === 0` 時寫一次該屬性欄（8 byte） | 屬性欄 16px 寬，晚寫一格會出現色塊錯位 |
| 初始化 | rendering 關閉時一次補滿兩張 NT（1920 byte），**不計預算** | 遊戲中途換場景要分攤到多幀（R1 的教訓） |
| 倒退 | 本專案是強制捲動，`camX` 單調遞增 ⇒ 不處理倒退 | 若未來要做「被魔王逼退」，需要寫左緣欄 |

### 6.4 一幀的順序（VBlank 預算的分配）

```
NMI（VBlank 開始）
 ├─ ① OAM DMA（$4014）           256 byte / 513 cycle  ← 獨立通道
 ├─ ② 名稱表欄緩衝 flush          ≤ 38 byte
 ├─ ③ 屬性緩衝 flush              ≤ 8 byte（每兩欄一次）
 ├─ ④ HUD 數字更新（分數 / 能量表） ≤ 24 byte（只寫變動的格）
 ├─ ⑤ 調色盤更新（閃白 / 淡入）     ≤ 32 byte（只在特效幀）
 └─ ⑥ 設定捲動 $2005 / $2006
VBlank 結束 → 可見畫面
 └─ 掃描線 208：分割，捲動歸零、切 HUD 用的名稱表區
```

- [推論] 上表最壞情況 = 38 + 8 + 24 + 32 = **102 byte**，留 58 byte 餘裕給魔王背景磚動畫。這是本專案「魔王本體用背景磚」可行的關鍵預算依據。

## ⑦ 以捲動位置為鍵的出怪表

### 7.1 為什麼用「位置」而不是「時間」

| 鍵 | 優點 | 缺點 | 適用 |
|---|---|---|---|
| **捲動位置（欄 / px）** | 關卡是「空間」，編輯器所見即所得；地形與敵人永遠對齊；玩家可記憶 | 捲動停下來（魔王戰）時要另一套機制 | **橫捲 STG 的標準** [源] |
| 幀數（時間） | 停止捲動時仍能運作；節奏好控 | 一旦有降速就全歪掉 | 魔王戰、過場 |
| 混合 | 主表用位置，魔王段切成幀表 | 兩套邏輯 | **本專案採用** [推論] |

- [源] 社群的實作共識：「觸發出怪的就是關卡的捲動；攻擊編隊在特定捲動位置被觸發，然後才插進『活動物件表』，所以任何時刻只需要處理一小部分敵人。」
- [源] 另一個常見技巧：「敵人**依出現順序排序**，於是每幀只需要檢查一個元素就知道要不要生成。」

### 7.2 資料格式建議（本專案 `NES.SH.Spawner`）

```js
// stage1.js：以「欄」為鍵，遞增排序，單次觸發
CR.SPAWN_TABLE = [
  { col:  24, fn: (s) => s.wave('bee', { y:  64, n: 5, drops: true }) },
  { col:  32, fn: (s) => s.turret({ y: 'floor', x: 256 }) },
  { col:  40, fn: (s) => s.wave('bee', { y: 120, n: 5, drops: true }) },
  // ...
  { col: 352, fn: (s) => s.boss('core') },
];
```

| 欄位 | 型別 | 說明 |
|---|---|---|
| `col` | 整數，**必須遞增** | 關卡欄座標（1 欄 = 8 px）；`camCol = camX >> 3` |
| `fn(ctx)` | 函式 | 呼叫 stage 的生成器；**不可**假設池一定有空位（`alloc()` 可能回 null） |
| 觸發規則 | `camCol >= col` 且尚未觸發過 | 倒退不重觸發（本專案 camX 單調遞增，僅檢查點重置時 `reset()`） |
| 指標 | 只保留一個 `next` 索引 | 每幀 O(1)，不掃全表 |

### 7.3 編隊（wave）的參數化

| 參數 | 說明 | 建議值 |
|---|---|---|
| `n` | 隻數 | 3 / 5 / 8 |
| `gap` | 前後間隔幀 | 6~10（太密會同線 > 8） |
| `y` | 入場高度 | 距地板 / 天花板至少 24 px |
| `path` | 路徑 ID（直線 / 蛇行 / U 轉 / 繞圈） | 一個 wave 只用一種 |
| `drops` | 全滅是否掉膠囊 | Gradius 規則：**整隊全滅**才掉一顆 [源] |
| `pal` | 用精靈調色盤 2 或 3 | 「會掉膠囊的那隊」用不同色 = 視覺告知 [源] |

> [源] Gradius 的規則明確：「摧毀特定敵人（以**不同顏色**標示）或敵人編隊時會掉落 Power Capsule。」顏色是給玩家的合約，本專案必須遵守。

### 7.4 檢查點與出怪表的互動

| 情境 | 處理 |
|---|---|
| 玩家死亡 → 回檢查點 | `Spawner.reset()` 後把 `next` 指標二分搜到 `camCol` 之後的第一筆 |
| 已生成但未被殺的敵人 | 全部 `free()`，畫面清空 |
| 檢查點在編隊中間 | ✗ 禁止；檢查點必須放在**編隊之間的空隙**，否則玩家一復活就被包 [推論] |
| 復活救濟 | Gradius 的做法：死亡後生成「一大群橘色敵人」讓玩家撿膠囊回復 [源]。本專案建議照做 |

## ⑧ 碰撞框縮小原則

### 8.1 業界事實

| 事實 | 來源 |
|---|---|
| 「連 Gradius 的碰撞框都比精靈小，而且這不是彈幕遊戲專屬——90 年代中期以後幾乎每款知名作品（含 Psikyo、Seibu 等非彈幕廠）都是精靈大、判定小。」 | [源] shmups.system11.org |
| 「判定通常只有 1~4 px，遠小於自機精靈，這就是密集彈幕還能活下來的訣竅。」 | [源] Dinogame 彈幕定義文 |
| 「玩家判定應該是放在精靈**質心**的一個小圓，而且要在**所有動畫幀**保持在同一位置。」 | [源] shmups.system11.org |
| 「玩家子彈與敵人精靈的判定要**寬鬆**，讓瞄準感覺準確又公平；敵彈的判定要**緊**，讓密集彈幕可以精準閃避。」 | [源] SLYNYRD Pixelblog 63 |

### 8.2 本專案的判定框規格（TASKS 契約 + 本文補充理由）

| 對象 | 精靈尺寸 | 判定框 | 比例 | 理由 |
|---|---|---|---|---|
| 自機 | 16×8 | **12×6**（置中，左右各縮 2、上下各縮 1） | 56% 面積 | 保留「擦彈」的餘裕，但不至於讓玩家覺得穿模 [推論] |
| 自機 vs **敵彈** | — | 建議進一步縮到 **6×4**（核心） | 19% | 彈幕段落的公平性；可用「兩個框」：對地形用 12×6、對敵彈用 6×4 [推論] |
| 自機彈 | 8×8 | **4×4** ×（對敵人放寬到 8×8） | — | 打擊感優先 |
| 敵機 | 16×16 | **12×12** | 56% | 讓玩家「看起來擦到」也能打中 |
| 敵彈 | 8×8 | **4×4** | 25% | 緊 |
| 膠囊 | 8×8 | **12×12**（比精靈**大**） | 225% | 撿道具要好撿；這是唯一應該放大的框 [推論] |
| 地形 | 磚 8×8 | 用 `solidAt(x, y)` 查磚，取自機框 4 角 | — | 4 角取樣足夠；不要逐像素 |

### 8.3 兩段式判定（建議）

```
自機 hitbox
┌──────────────┐  ← 12×6：對地形、對敵機本體（撞到 = 死）
│  ┌──────┐    │
│  │ 6×4  │    │  ← 核心：對敵彈（擦彈不死）
│  └──────┘    │
└──────────────┘
```

- [推論] 這讓「貼著地板飛」變得刺激但可控，同時彈幕段落不會因為船身長 16 px 而變成不可能。
- [推論] 護盾（Force Field）啟動時，把**對敵彈**的框直接關掉 N 次命中，而不是放大框——放大框在 NES 的整數座標下會有奇怪的邊界行為。

### 8.4 判定順序（每幀）

| 順序 | 檢查 | 結果 |
|---|---|---|
| 1 | 自機彈 × 敵人 | `enemy.hit(dmg)`；子彈 `free()`（雷射不消失） |
| 2 | 自機彈 × 魔王部位 | 只有「露出的弱點」可被打中 |
| 3 | 自機 × 膠囊 | `gauge++`，膠囊 `free()` |
| 4 | 自機 × 敵彈 | 有護盾 → 扣護盾；無 → `die()` |
| 5 | 自機 × 敵人 | `die()`（並讓敵人也爆） |
| 6 | 自機 × 地形 | `die()` |
| — | 無敵幀 | `invul > 0` 時跳過 4/5/6，建議 **90 幀**（1.5 秒） |

> [推論] 順序很重要：**先撿膠囊再判死**。同一幀同時撿到膠囊又撞到彈，玩家會覺得「我明明撿到了」——先給獎勵比較不會被罵。

## ⑨ 雷射與長型子彈的精靈拼法

### 9.1 問題

NES 的精靈是 8×8（或 8×16），一條橫貫畫面的雷射需要 32 顆精靈 —— **一定會爆掉每線 8 個的限制**（同一條掃描線上排 32 顆）。

- [源] 這正是 Gradius FC 版的妥協：「雷射在 NES 版沒那麼好用了，因為它不再貫穿整個畫面。」

### 9.2 五種拼法

| 拼法 | 描述 | 每線精靈數 | 成本 | 適用 |
|---|---|---|---|---|
| **A. 短雷射（段數上限）** | 只畫 3~4 段（24~32 px），隨自機前進 | 4 | 4 顆 OAM | **本專案採用**（契約：最長 4 段） |
| **B. 粗雷射（8×16 疊兩層）** | 用 8×16 精靈模式，一段只要 1 顆就有 16 px 高 | 4 | 4 顆 | 想要「厚重」感時 |
| **C. 背景磚雷射** | 雷射畫在背景層，寫名稱表 | **0** | 每幀 ~8 byte | 位置只能 8px 對齊，動起來很卡 [推論] |
| **D. 閃爍雷射** | 段落之間刻意留空隙，每幀交錯（像虛線） | 2~4 | 少 | 復古味濃，但可讀性差 |
| **E. 掃描線分段** | 雷射每段 y 稍微錯開 1~2 px，讓它們不在同一條掃描線 | ≤ 8 | 多 | 只適合斜向雷射 |

### 9.3 本專案雷射規格（建議給 ship agent）

| 項 | 規格 | 理由 |
|---|---|---|
| 段長 | 每段 8×8 精靈，最長 **4 段 = 32 px** | 契約已定；4 顆 OAM 可接受 |
| 生成 | 按住 B 蓄力？→ **不**。按一下就發射完整 4 段 | NES Gradius 是「按住可延長」，但我們的自機彈上限是 2，簡化為固定長度 [推論] |
| 前進 | 整條以 **6 px/幀** 前進（比一般彈 4 px/幀 快） | 雷射要有「快」的感覺 |
| 貫穿 | 命中敵人**不消失**，但同一隻敵人每 8 幀只吃一次傷害 | 避免一幀打 4 次 |
| 傷害 | 每次 2（一般彈 1） | 讓「選雷射」有意義 |
| 磚 | 頭段 / 中段 / 尾段 三種磚（`S_LASER_H` / `_M` / `_T`） | 中段可重複用，省 CHR |
| 互斥 | 與 DOUBLE 互斥（Gradius 規則 [源]） | 逼玩家做選擇 |

### 9.4 其他長型物件

| 物件 | 拼法 | 精靈數 |
|---|---|---|
| 敵人雷射掃射（魔王第三階段） | 3 條各 3 段 = 9 顆，但**三條 y 錯開 ≥ 16 px** | 9（每線 ≤ 3） |
| 觸手 / 鎖鏈 | 每節 8×8，最多 6 節；節與節間隔 8px 且**呈斜線** | 6（每線 1~2） |
| 大型敵機（32×16） | 8 顆 8×8，或 4 顆 8×16 | 4（8×16 較省） |
| 地形凸起上的砲管 | 背景磚畫底座，只有砲管頭是精靈 | 1 |

> [推論] **通則：任何「長」的東西都要盡量走斜的或走背景**。橫平豎直 + 精靈 = 每線 8 個的地雷。

## ⑩ 大型魔王：背景磚 + 精靈混合

### 10.1 為什麼要用背景

| 事實 | 來源 |
|---|---|
| 「掃描線限制與同屏精靈限制讓大量用精靈很困難，所以很多遊戲**用背景層做魔王**。」 | [源] MegaCat Studios |
| 「聰明的設計者用**動畫背景磚**做出大型敵人，完全沒有精靈閃爍問題。」 | [源] MegaCat Studios |
| 「動畫背景魔王很麻煩，因為**一次只能換約 32 塊磚**。解法是在幀之間做『混合』，重用上一幀的部分磚，減少需要新換的磚數。」 | [源] MegaCat Studios |
| 「背景是一整片磚格，**只能整塊一起移動**。所以像《洛克人 6》那種大魔王出現時背景通常是空的——你沒辦法只移動魔王。」 | [源] NESdev 論壇 |
| 實例：洛克人系列的巨型魔王、《忍者蛙》Snake Pit 的蛇、《Bucky O'Hare》的背景敵人 + 視差 + 丟石頭 | [源] NESdev 論壇 |

### 10.2 三層混合方案（本專案建議）

| 層 | 內容 | 更新成本 | 可動性 |
|---|---|---|---|
| **背景磚** | 魔王本體外殼、要塞牆面、不動的裝甲板 | 每幀 ≤ 32 byte（改磚 index） | 只能 8px 對齊，或整體跟著捲動 |
| **CHR bank 動畫** | 外殼的「發光 / 破損」動畫：**不換磚 index，換磚的圖樣內容** | 若是現代還原，直接改 CHR 資料（真機需要 CHR-RAM 或 bank 切換） | 原地動畫，成本最低 [推論] |
| **精靈** | 會移動的部位：核心、砲管、觸手、開合的裝甲門 | OAM 12 顆以內 | 完全自由 |

> [推論] 本專案《星塵巡航艦》的魔王在契約上是 48×48。若全用精靈 = 6×6 = **36 顆 8×8 精靈**，且每條掃描線 6 顆 —— 加上敵彈立刻爆線。**建議改成：背景磚畫 48×48 的要塞本體（36 塊磚），精靈只畫「4 片會開合的外殼板」+「核心」+「砲口閃光」= 約 10~12 顆。**

### 10.3 魔王進場的預算分攤

| 幀 | 動作 | 名稱表 byte |
|---|---|---|
| 0 | 停止捲動（`stage.speed = 0`），播 boss 曲 | 0 |
| 1~12 | 每幀寫 3 塊磚，把 36 塊魔王磚逐步「浮現」（配合閃白調色盤） | 3/幀 |
| 13 | 屬性表寫 9 byte（3×3 個 16×16 區塊） | 9 |
| 14~20 | 精靈部位淡入（OAM，不佔名稱表） | 0 |
| 21 | 戰鬥開始 | — |

- [推論] 這比「一幀寫 36 byte」更安全，而且「逐步浮現」本身就是很有戲的登場演出。

### 10.4 魔王受擊表現

| 表現 | 實作 | 成本 |
|---|---|---|
| 閃白 | 換背景調色盤（`$30` 白）2 幀 | 3~4 byte |
| 裝甲破損 | 把該區磚換成「裂痕」版本（9 塊） | 9 byte |
| 部位脫落 | 精靈消失 + 生成爆炸 | 0（OAM） |
| 核心露出 | 外殼磚換成「開口」版本 + 核心精靈開始畫 | 12 byte |
| 死亡大爆炸 | 8 個爆炸精靈依序在魔王範圍隨機位置生成，每 6 幀一個，共 48 幀 | OAM 8 |
| 死亡後清除 | 分 12 幀把 36 塊磚換回背景 | 3/幀 |

## ⑪ 狀態列分割：sprite 0 vs IRQ

### 11.1 兩種做法

| 做法 | 原理 | 優點 | 缺點 | 來源 |
|---|---|---|---|---|
| **sprite 0 命中** | 在狀態列邊界放一顆不透明精靈，與不透明背景重疊 → `$2002` bit 6 置位；CPU 忙迴圈輪詢 | 不需要特殊 mapper（Gradius NES 的 CNROM 只能這樣） | **浪費大量 CPU 等待時間**；一幀只能一次；x = 0~7（左裁切開啟時）與 x = 255 不觸發 | [源] NESdev PPU OAM / nesdoug |
| **mapper 掃描線 IRQ**（MMC3 / VRC4） | 卡帶計數 A12 翻轉，到指定掃描線發 IRQ | 不用輪詢、**一幀可多次分割**、時序穩 | 需要 mapper | [源] NESdev 論壇 |
| 混合 | 用 IRQ 在 sprite 0 命中前一點觸發，減少輪詢時間 | 兩者之長 | 複雜 | [源] NESdev 論壇 |

### 11.2 本專案的選擇

- R1 的 `ppu.split(scanline)` 在效果上等價於 MMC3 IRQ（QA 報告 P2-3 已確認），**R2 直接沿用**。
- 本專案 HUD 在**下方**（掃描線 208..239），屬於「底部狀態列」：

| 掃描線 | 內容 | 捲動設定 |
|---|---|---|
| 0..207 | 遊戲區 | `scrollX = camX & 255`，`nt = (camX >> 8) & 1` |
| **208**（split） | 分割點 | `scrollX = 0`，`nt = 0`，並把 PPU 位址指到 HUD 用的名稱表列 |
| 208..239 | HUD（4 列磚） | 固定 |

- [推論] 底部狀態列比頂部好處理：頂部狀態列需要在畫面**開始**時就是固定的、然後中途切成捲動；底部則是「先捲動、後固定」，只需要一次分割，而且 VBlank 的設定順序更自然。
- [推論] 注意：分割發生在可見區間，**分割那一刻不能寫名稱表**（PPU 正在讀）。所有名稱表寫入都必須在 VBlank 完成。

### 11.3 HUD 更新的省 byte 技巧

| 技巧 | 說明 | 省下 |
|---|---|---|
| 只寫變動的位數 | 分數 7 位，實際每幀通常只有 1~2 位變 | 5~6 byte |
| 能量表用**屬性表**反白 | 不換磚，只改 16×16 區塊的調色盤（1 byte 改 4 個磚的顏色） | 每次切換省 ~6 byte |
| 剩餘船數用「重複同一塊磚」 | 寫 n 塊「船圖示」磚 + 空白磚 | 3 byte |
| 分數只在變動時寫 | 加分時設 dirty 旗標 | 大多數幀 0 byte |

### 12.2 制度的設計後果

| 學習方式 | **記憶 + 路線規劃**（memorizer） | 反射 + 應變 |
| 挫折點 | 「復活地獄」：裸機面對為全裝設計的段落 | 幾乎沒有，但可能變成「用命換推進」 |
| 單次遊玩長度 | 短（死了要重打一段） | 長 |
| 適合的關卡 | 有明確「段落」的（通過閘門 / 打完中王） | 連續流動的 |

| 社群評價 | 「Gradius 症候群」是負面詞 [源] | 沙羅曼蛇被視為系列的體貼分支 [源] |

### 12.3 本專案建議

> [推論] **《星塵巡航艦》採「檢查點 + 三層救濟」**，理由：我們是 Gradius 風格致敬，檢查點是這個類型的識別特徵；但要用救濟避開純粹的懲罰。

| 層 | 機制 | 數值建議 |
|---|---|---|
| ① | 檢查點密集（每 ~64 欄一個，關卡 384 欄 ⇒ 6 個） | 每段約 40~60 秒 |
| ② | **復活救濟編隊**：死後 90 幀內生成一隊「必掉膠囊」的橘色敵人（Gradius 原作就有 [源]） | 保證掉 3 顆膠囊 |
| ③ | **速度不歸零**：死亡後 SPEED 保留 1 級（不回到 1 級） | 唯一保留的強化；速度 1 級太慢會連鎖死亡 [推論] |
| ④ | 無敵幀 90 幀 + 閃爍 | 復活瞬間不會被既有敵彈殺 |
| ⑤ | 死亡時**清空所有敵彈** | NES 時代常見的體貼；避免「復活即死」[推論] |

- [推論] ③ 是本專案對 Gradius 的**刻意改良**。玩家測試若覺得太寬鬆，把它改成「保留但只在本關有效」。
- [推論] 檢查點位置的硬規則：**檢查點前後 16 欄內不可有敵人、不可有地形收窄**。這是唯一能避免復活地獄的結構性保證。

## ⑬ 動態難度 rank

### 13.1 Gradius 系列的 rank

| 作品 | rank 公式 / 因子 | 範圍 | 來源 |
|---|---|---|---|
| **Gradius（初代 AC）** | 難度設定 + 關卡 / 循環 + 已啟用的強化 | 封頂 **15**（Nemesis 版另計存活幀、關卡數、強化、選項數、難度） | [源] shmups.system11 / Shmups Wiki |
| **Gradius III（AC）** | 難度設定 + 循環 / 關卡 + 強化 + 特殊項 = rank | **0~31**；高段的每一級差距比低段大（21→22 比 5→6 明顯得多） | [源] shmups.system11 |
| **Gradius IV** | **動態 rank 計數器**（類似《Battle Garegga》），上升速率由當前強化決定；**每次死亡會降 rank** | — | [源] shmups.system11 |
| **Zanac（Compile, 1986/NES）** | **ALC（Automatic Level of Difficulty Control）**：依開火頻率、目前特殊武器、掉命頻率、擊落藍色偵察機的數量調整敵人生成 | MSX 版畫面上會顯示一個 16 進位的 ALC 值 | [源] Wikipedia / HG101 |

### 13.2 rank 的原始目的

> [源] 社群的共識說法：「初代 Gradius 的 rank 會上升，好讓你**全副武裝時仍有挑戰**；當你的船裸機時 rank 會下降，給你一個能推進的機會。」

- [推論] 也就是說 rank 的本質是**「難度跟著火力走」的自動平衡器**，不是懲罰高手。它會壞掉，是因為「死亡清空火力」與「rank 不同步下降」這兩件事撞在一起 —— Gradius IV 加上「死亡降 rank」就修好了大半。

### 13.3 rank 可以調整什麼

| 可調項 | 低 rank | 高 rank | 對 NES 的成本 |
|---|---|---|---|
| 敵彈速度 | 1.5 px/幀 | 3.0 px/幀 | 0（同一個 speed88） |
| 砲台開火間隔 | 90 幀 | 40 幀 | 0 |
| 一次發幾發 | 1（瞄準） | 3（扇形） | 0 |
| 敵人 hp | ×1 | ×1.5 | 0 |
| 編隊隻數 | n | n + 2 | 池要夠 |
| 敵人移動速度 | ×1 | ×1.25 | 0 |
| 是否生成額外散兵 | 否 | 是 | 池要夠 |

> [推論] rank 調「敵彈速度」與「開火間隔」的**體感回饋最明顯、實作成本最低**，是首選兩項。調敵人 hp 會讓玩家覺得「我的槍變弱了」，反而傷手感。

### 13.4 本專案的 rank 設計（建議）

```
rank = clamp(0, 15,
      floor(camCol / 48)          // 進度：關卡 384 欄 ⇒ 0..8
    + speed - 1                   // 速度等級：0..4
    + (double ? 1 : 0)
    + (laser ? 2 : 0)
    + options                     // 0..2
    - deaths * 3                  // 每死一次降 3，最低 0
)
```

| rank 區間 | 名稱 | 敵彈速度 | 砲台間隔 | 額外散兵 |
|---|---|---|---|---|
| 0~3 | 寬鬆 | 1.5 px/f | 100 幀 | 無 |
| 4~7 | 標準 | 2.0 px/f | 75 幀 | 無 |
| 8~11 | 緊 | 2.5 px/f | 55 幀 | 每 96 欄 1 隻 |
| 12~15 | 高壓 | 3.0 px/f | 40 幀 | 每 64 欄 1 隻 |

- [推論] `- deaths * 3` 是採納 Gradius IV 的修正；`deaths` 在過關時歸零。
- [推論] **rank 必須可在 debug 面板看到**（`state().rank`），否則 QA 沒辦法複現問題。

## ⑭ 膠囊與強化經濟

### 14.1 Gradius 能量表（Power Meter）的經濟學

| 事實 | 內容 | 來源 |
|---|---|---|
| 取得 | 摧毀**特定顏色**的敵人或**整個編隊**會掉 Power Capsule | [源] Shmups Wiki / Gradius Wiki |
| 累積 | 每撿一顆，能量表的反白格往右移一格 | [源] |
| 兌現 | 按按鈕啟用當前反白格的能力；**能量表歸零重來** | [源] |
| 格位順序（初代） | Speed Up → Missile → Double → Laser → Option → ?（護盾） | [源] Shmups Wiki |
| 沙羅曼蛇 FC 版格位 | Speedup → Missile → **Ripple** → Laser → Option → **Force**（Force Field：耐打次數較少但**包覆整艘船**） | [源] Gradius Wiki |
| 速度上限 | Speed Up 最多買 **5 次** | [源] Shmups Wiki |
| 選項上限 | 街機 4 顆，**部分移植只有 2 顆**（FC 版 2 顆） | [源] Shmups Wiki / Gradius Wiki |
| 互斥 | Laser 與 Double 互斥 | [源] Shmups Wiki |

### 14.2 為什麼這套經濟好玩

> [源]「這種進程本身就有風險回報：你會想**留著膠囊等更好的選項**，但有些升級根本是活下去的必需品。為了一個更強的能力而不兌現較弱的那個，往往很危險。」

- [推論] 精髓在於「膠囊是**通用貨幣**，而能量表是**一條單向的價目表**」。你不能跳格買，只能一路往右走；走過頭就繞回第一格。這讓「什麼時候按 B」變成每一局最重要的決策。
- [推論] 對比之下，《Gun-Nac》把強化直接撒給玩家（甚至有商店可買 [源]），《Zanac》用特殊武器槽位切換 —— 兩者都更「爽」，但決策深度不如 Gradius。

### 14.3 本專案的能量表（沿用契約 + 數值建議）

| 格 | 名稱 | 效果 | 可重複 | 建議數值 |
|---|---|---|---|---|
| 1 | **SPEED** | 移動速度 +1 級 | 是，上限 5 | 1級 1.5 / 2級 2.0 / 3級 2.5 / 4級 3.0 / 5級 3.5 px/幀 |
| 2 | **MISSILE** | 按射擊時同時斜下發射飛彈，落地後沿地面滾 | 否（有 / 無） | 飛彈速度 2 px/幀 下墜 + 3 px/幀 前進；滾動 3 px/幀；傷害 2 |
| 3 | **DOUBLE** | 前方 + 斜上 45° 各一發（與 LASER 互斥） | 否 | 各 4 px/幀，傷害各 1 |
| 4 | **LASER** | 4 段貫穿雷射（與 DOUBLE 互斥） | 否 | 6 px/幀，傷害 2，貫穿 |
| 5 | **OPTION** | 增加一顆選項（複製自機全部火力） | 是，上限 2 | 延遲 16 幀 / 顆，歷史緩衝 64 筆 |
| 6 | **?（SHIELD）** | 護盾，可擋 3 次 | 是（補滿） | 覆蓋全船；被打破時閃爍 30 幀 |

### 14.4 膠囊掉落率設計

| 來源 | 掉落 | 頻率 |
|---|---|---|
| 編隊全滅（5 隻） | **必掉 1 顆** | 關卡 1 安排 8 隊 ⇒ 8 顆 |
| 特殊色敵人（單隻） | 必掉 1 顆 | 4 隻 |
| 砲台 | 不掉 | — |
| 硬殼敵（hp 3） | 25% | 4 隻 ⇒ 期望 1 顆 |
| 復活救濟編隊 | 必掉 3 顆 | 死亡時 |
| **關卡 1 總供給** | **約 13 顆** | 足夠買到 SPEED×2 + MISSILE + DOUBLE + OPTION×1（= 5+2+3+... 依路徑）[推論] |

- [推論] 膠囊總供給要「**剛好不夠全買**」。Gradius 的張力來自稀缺；如果玩家關卡 1 就能滿裝，rank 會爆掉而且後面沒東西追求。
- [推論] 膠囊要有**壽命**（約 300 幀後閃爍、360 幀消失），否則玩家會在畫面上囤積，OAM 被吃光。

## ⑮ 魔王模式設計

### 15.1 原則

| 原則 | 說明 | 來源 |
|---|---|---|
| 節奏是魔王的本質 | 「魔王戰應該有好的節奏——隨時間**堆疊與釋放**張力與難度。」 | [源] Game Developer |
| 魔王是關卡的標點符號 | 「知道魔王要來了，就是把接連幾關的強度往上堆的好藉口。」 | [源] Game Developer |
| 最終魔王 = 總複習 | 「最終魔王該讓人覺得是到目前為止所學的總結。」 | [源] Game Developer |
| 中王的位置 | 「大約在關卡中段、玩家理解了這個機制的時候，是放中王的正確時機，作為獎勵掌握的高潮。」 | [源] Game Developer |
| 出場即休息 | 「戲劇化的魔王登場讓玩家有機會伸展與心理準備。」 | [源] Game Developer |

### 15.2 魔王階段的標準三段式

| 階段 | 觸發 | 玩家在學什麼 | 彈幕密度 | 弱點 |
|---|---|---|---|---|
| **① 外殼 / 探索** | 進場 | 認識形狀、找哪裡可以打 | 低（瞄準單發） | 外部裝甲（多個，各自 hp 低） |
| **② 露出 / 施壓** | 外殼全破 | 在既有攻擊下維持輸出 | 中（扇形 + 直線牆） | 核心（hp 高） |
| **③ 絕命 / 解放** | 核心 hp < 40% | 用上所有走位技巧 | 高（環形 + 掃射雷射） | 核心（不變） |

- [推論] 每階段之間必須有 **30~60 幀的「靜止 / 轉場」**，讓玩家看到變化、也給一個呼吸點。沒有轉場的階段切換會讓玩家覺得被偷襲。
- [推論] 三個階段的**攻擊要可疊加但不可同時滿載**：階段 3 = 階段 1 的攻擊（降頻）+ 新攻擊，而不是全部一起來。

### 15.3 弱點露出的三種表現

| 方式 | 視覺 | 實作 | NES 可行性 |
|---|---|---|---|
| **裝甲板脫落** | 4 片板子逐一爆掉，露出中間 | 精靈消失 + 背景磚換成「開口」 | ✓ 最省 |
| **開合窗口** | 砲口週期開合，只有開的時候能打 | 精靈換磚 + `vulnerable` 旗標 | ✓；要有 ≥ 20 幀的預警 |
| **發光核心** | 核心變色（調色盤循環）表示可打 | 換 1 個調色盤 byte | ✓ 最省 byte |

> [推論] 一定要有**明確的「打不中」回饋**：打到裝甲時子彈彈開 + 短促「鏘」音效，不能只是子彈消失。否則玩家不知道自己有沒有在輸出。

### 15.4 彈幕型態庫（NES 可行版）

| 型態 | 彈數 | 週期 | 難度 | 說明 |
|---|---|---|---|---|
| 瞄準單發 | 1 | 60 幀 | ★ | 教學用；玩家只要動一下就躲掉 |
| 三連瞄準 | 3 | 每 8 幀一發，共 3 發後歇 60 幀 | ★★ | 逼玩家持續移動 |
| 扇形 5 發 | 5 | 90 幀 | ★★ | step = 12（約 17°） |
| 環形 8 發 | 8 | 120 幀 | ★★★ | 相鄰間距 45°，必留缺口 |
| 交錯雙環 | 8 + 8 | 兩波隔 30 幀，第二波偏移 22.5° | ★★★★ | 逼玩家在第一波的縫裡就定位 |
| 牆型 6 發 | 6 | 100 幀 | ★★★ | 垂直排列留 1~2 個缺口，缺口隨機 |
| 雷射掃射 | 3 條 | 蓄力 45 幀 + 掃射 90 幀 | ★★★★ | 三條 y 錯開 ≥ 16 px；蓄力時有明顯充能光 |

### 15.5 魔王的公平性檢查表

| ☐ | 項目 |
|---|---|
| ☐ | 每種攻擊都有 ≥ 20 幀的預警動作（充能光 / 砲口張開 / 身體後仰） |
| ☐ | 任一時刻都存在至少一條「不需要像素級精度」的安全路徑 |
| ☐ | 魔王本體的碰撞框不會突然伸到玩家所在位置（衝撞攻擊要有預警） |

| ☐ | 有「超時」處理：180 秒未打完，魔王自爆或撤退（避免卡關） |

## ⑯ 關卡節奏曲線

### 16.1 理論

| 原則 | 來源 |
|---|---|
| 「持續的高強度加上重度堆疊會消耗玩家，**製造強度的起伏**反而能讓高潮更突出。」 | [源] Game Developer |
| 「在最終階段，設計者應該放慢、為最終魔王蓄勢，給玩家時間休息與準備。」 | [源] Game Developer |
| 「視覺上很強烈但機制上較簡單的段落，可以在中王之前提供休息。」 | [源] Game Developer |
| 難度曲線應為**鋸齒狀**（緊張—放鬆交替）而非直線（心流通道） | [源] 本研究 `04_遊戲設計模式.md` §⑤ |

### 16.2 橫捲 STG 的五段式（本文提出）

| 段 | 佔比 | 強度 | 內容 | 目的 |
|---|---|---|---|---|
| **① 開場（establishing）** | 0~10% | 2/10 | 稀疏的單向敵人、第一隊必掉膠囊 | 讓玩家取得第一批強化；建立視覺主題 |
| **② 教學（teaching）** | 10~30% | 4/10 | 一次引入一種新敵人 / 一種地形危險 | 每個新元素第一次出現時**只有它** |
| **③ 組合（combining）** | 30~55% | 6/10 | 兩種元素疊加（砲台 + 編隊、狹道 + 之字敵） | 考驗剛學會的東西 |
| **④ 高潮（peak）** | 55~75% | 8/10 | 最密的一段；狹窄地形 + 三面砲台 | 本關的真正考驗 |
| **⑤ 呼吸 + 魔王（breath & boss）** | 75~100% | 3 → 9/10 | **一段幾乎沒有敵人的開闊區**，然後魔王登場 | 讓玩家調整位置、看能量表、心理準備 |

- [推論] 第 ⑤ 段的「呼吸」極其重要：Gradius 每關魔王前都有一段相對空曠。沒有它，玩家會帶著上一段的殘血與慌亂進魔王戰，感覺是被連坐而不是被挑戰。
- [推論] 節奏曲線用**「每 16 欄的敵人威脅值」**量化：威脅值 = Σ(敵人危險度)，畫成折線圖應該看得到鋸齒與一個明顯的峰。

## ⑰ 初見殺與記憶型設計

### 17.1 兩種學習模型

| 模型 | 定義 | 代表 | 玩家的成長曲線 |
|---|---|---|---|
| **反應型（reaction）** | 資訊在畫面上，靠反射與判斷即時應對 | 彈幕系、《沙羅曼蛇》大部分段落 | 平滑上升 |
| **記憶型（memorizer）** | 必須知道「下一個會發生什麼」才活得下來 | **R-Type**（「memorizer shooter 的第一與終極範例」[源]） | 階梯狀（每學會一段跳一級） |

- [源] R-Type 的說明：「死亡極度懲罰——你會被丟回檢查點，沒有武器、沒有 Force Pod、沒有 Bits、沒有加速。因此玩家通常被鼓勵不惜一切避免死亡，並且打得非常保守。」
- [源] 另一個角度：「早期的橫捲遊戲（如 R-Type）把注意力大量放在**環境危害**上。閃避子彈是次要的，主要是撿強化與**記住關卡配置**，免得自己撞上去。」

### 17.2 初見殺（instant death on first encounter）的分級

| 等級 | 描述 | 可接受？ |
|---|---|---|
| **A. 完全無預警** | 沒有任何線索，第一次一定死（例如畫面外突然射出的高速彈） | ✗ **禁止** |
| **B. 有線索但需要辨識** | 地形紋理不同、敵人顏色不同、有 20 幀的預警動畫 | ✓ 這是「學習」 |
| **C. 有預警且可即時反應** | 預警 ≥ 40 幀、且安全區明顯 | ✓ 最佳 |
| **D. 需要事前佈局** | 必須在 3 秒前就選對路徑（R-Type 式） | △ 只在最終關使用 [推論] |

### 17.3 本專案的規則

> [推論] 《星塵巡航艦》定位是「致敬 Gradius 的可玩原創作」，不是苦行。規則：
> 1. **關卡 1 全部只用 C 級**。
> 2. 任何從畫面外（x > 256）出現的敵人，出現後 **至少 30 幀內不得開火**。
> 3. 高速敵彈（≥ 3 px/幀）**只能從畫面內的敵人**射出，且射出前砲口要閃 2 幀。
> 4. 地形的致命凸起在進入前 48 px（約 1 秒）就要完全可見。
> 5. 沒有任何「必須先知道才能過」的段落。

### 17.4 給記憶留空間，而不是強迫記憶

| 手法 | 說明 |
|---|---|
| 可選的高風險路徑 | 記住的人可以走上方狹道拿額外膠囊；不記得的人走安全下路 |
| 提前資訊 | 大型敵人進場前先有一小隊同色的斥候 |
| 重複的動機 | 同一種編隊模式在關卡中出現 3 次（第 3 次疊加變化）——玩家自然記住 |
| 節奏可預測 | 砲台開火間隔固定，玩家可以數拍子 |

## ⑱ 速度等級的取捨

### 18.1 問題

Gradius 的 SPEED 可以買 5 次 [源]。但速度是**雙面刃**：

| 速度 | 優點 | 缺點 |
|---|---|---|
| 慢（1~2 級） | 好微調、狹道安全 | 追不上膠囊、躲不掉快彈、被地形夾死 |
| 中（3 級） | 平衡 | — |
| 快（4~5 級） | 撿膠囊快、能大幅換位 | **過衝**（overshoot）撞牆；在狹道等於自殺 |

- [推論] Gradius 老手的共識是「速度 3 級最好用」；很多人刻意不買到 5 級。這代表這條升級線**做對了**——它創造了一個真實的取捨，而不是單調的變強。

### 18.2 本專案的速度表

| 等級 | px/幀 | 8.8 定點 | 橫越 240px 需要 | 適合 |
|---|---|---|---|---|
| 1 | 1.5 | 384 | 160 幀（2.7 秒） | 太慢，起始值 |
| 2 | 2.0 | 512 | 120 幀（2.0 秒） | 舒適下限 |
| **3** | **2.5** | **640** | **96 幀（1.6 秒）** | **甜蜜點** [推論] |
| 4 | 3.0 | 768 | 80 幀（1.3 秒） | 開闊區好用 |
| 5 | 3.5 | 896 | 69 幀（1.1 秒） | 狹道危險 |

- [推論] 斜向移動要不要正規化？**不要**。NES 遊戲普遍是「上 + 右 = 各自全速」，斜向實際速度 ×1.414。這是那個時代的手感，而且斜衝更快本身就是一種技巧。
- [推論] **無慣性**。SLYNYRD 說得直接：「不要加慣性……在 shmup 裡玩法至上。」[源] 自機的加速度應為無限大（按下即全速、放開即停）。

### 18.3 速度與其他系統的互動

| 互動 | 設計 |
|---|---|
| 速度 vs 地形 | 狹道段落的縫隙高度應 ≥ 32 px（4 格），讓 5 級速度也能通過 |
| 速度 vs 選項延遲 | 延遲 16 幀固定 ⇒ 速度越快，選項拖得越遠（5 級時落後 56 px）。這是**正確的**——高速時選項像尾巴甩出去，是招牌視覺 [推論] |
| 速度 vs 膠囊壽命 | 1 級速度要能在膠囊消失前撿到 ⇒ 膠囊壽命 ≥ 300 幀 |
| 死亡後 | 保留 1 級（見 §⑫）；否則 1 級速度 + 高 rank = 復活地獄 |

### 19.3 從對照表學到的三件事

1. [推論] **「能量表 + 檢查點」是一組**：延遲兌現的樂趣建立在「我攢的東西很寶貴」之上，而檢查點制度讓它真的寶貴。如果改成原地復活，能量表的張力會下降一半——所以沙羅曼蛇 FC 版即使有能量表，體驗也偏向「爽」。
2. [推論] **選項（Option）是這個類型的招牌視覺**。它同時是火力、是拖尾特效、是玩家操作的延伸。技術上只要一個環形歷史緩衝就能做到，CP 值極高。
3. [推論] **FC 上的技術天花板是 mapper**。Gradius 用 CNROM 就已經很吃力；Crisis Force 用 VRC4e 才做到四向捲動 + 大魔王。我們是軟體還原，不受此限，但**要自我約束在「一張水平鏡像的雙名稱表 + 一次分割」的範圍內**，才像 1986 年的 Konami 而不是 1991 年的。

## ⑳ 音樂技法（射擊遊戲特化）

> 通用的 2A03 技法見 `docs/research/06_音樂音效_2A03與chiptune.md`（§1.6 聲道優先與音效搶聲道、§2.1 琶音、§2.2 回音）。本節只補**橫向射擊特有**的部分。

### 20.1 引用 06 的既有結論

`06_音樂音效_2A03與chiptune.md` 已確立（不重複論證，直接沿用）：實務編制 = 旋律（方波 1）+ 和聲／回音（方波 2）+ 低音（三角波）+ 鼓（雜訊）+ DPCM，**音效必須搶其中一軌**（摘要 §3）；核心技法 = 琶音模擬和弦、第二方波做回音、震音／顫音、滑音、占空比切換、三角波兼任低音與大鼓（摘要 §4）；回音軌**微微失諧（detune，FamiTracker `Pxx`）**可做合唱／閃爍效果，但會整個佔用 Pulse 2 ⇒ 需要和聲的段落必須放棄回音（§2.2）；同時最多 3~4 個音效，超過丟棄低優先權（§5）；引擎給每個音效一個 priority，高優先權可打斷低的，同軌上新音效直接覆蓋舊的（§1.6）。

### 20.2 「Konami 式回音軌」的具體配方

[源] 通用的 NES 延遲做法是「用音量控制把同一個聲音重複、一次比一次小聲」——NES 沒有真的 delay，回音是**手工排出來的**。

[推論] 射擊遊戲版的具體參數（給 audio agent）：

| 參數 | 建議值 | 說明 |
|---|---|---|
| 延遲 | **3 row**（以 6 row/beat 計 = 半拍） | 太短會糊成和聲，太長會變成對位 |
| 音量 | 主旋律的 **40%**（例如主 15 → 回音 6） | 再低就聽不到 |
| 占空比 | 主旋律 25%，回音軌 **12.5%**（更細） | 音色上區分主從 |
| detune | **+2 ~ +4**（以 11-bit timer 的 LSB 計） | 產生每秒數次的緩慢拍頻，像合唱 |
| 何時關掉 | 需要三度 / 六度和聲的段落、魔王曲的緊張段 | Pulse 2 一次只能做一件事 |

### 20.3 射擊遊戲的聲部分配模板

| 聲道 | 開場 / 關卡曲 | 魔王曲 | 過關 jingle |
|---|---|---|---|
| **Pulse 1**（25%） | 16 分音符主旋律，大量滑音與上行 | 短動機重複 + 半音上行（緊張） | 大三和弦琶音上行 |
| **Pulse 2**（12.5%） | **回音軌**（延遲 3 row、40% 音量、detune +3） | 切換成**琶音和弦墊**（`0-3-7` 小三和弦，每幀換一音） | 三度平行 |
| **Triangle** | **走動式低音線**（幾乎是第二旋律，八分音符不停） | 持續低音（踏板音）+ 偶爾的半音下行 | 根音 |
| **Noise** | 16 beat 鼓組（短模式 hi-hat + 長模式 snare） | 密集 16 分 + 每 4 小節一次 fill | 一擊 crash |
| **DPCM** | 不用（省 ROM / 省 CPU） | 不用 | 不用 |

- [推論] 橫向射擊的關卡曲**必須有持續前進感**。做法：三角波走十六分或八分音符的 walking bass，**不停**。這是 Gradius / 沙羅曼蛇 系列辨識度的來源之一，也是最容易被新手漏掉的一點。
- [推論] 曲長建議 **32~64 小節後循環**，關卡長度 3~5 分鐘 ⇒ 循環 2~3 次，不會膩。

### 20.4 音效搶聲道優先權表（射擊遊戲版）

> 規則：音效要用哪一軌，就把音樂那一軌「靜音」N 幀，結束後音樂自動接回（音樂資料照跑，只是不寫暫存器）。

| 音效 | 建議軌 | 優先權 | 長度（幀） | 音色 | 音樂影響 |
|---|---|---|---|---|---|
| `shot`（一般射擊） | **Pulse 2** | 1（最低） | 3 | 12.5%，高音下掃 | 幾乎聽不出來；**每 4 幀最多一次**，避免連射蓋掉音樂 |
| `laser` | Pulse 2 | 2 | 8 | 12.5% + 快速下掃 | 短 |
| `missile` | Noise | 2 | 6 | 短模式高頻 | 借鼓一拍 |
| `hit`（打中敵人） | Noise | 3 | 4 | 短模式 | 借鼓 |
| `capsule`（撿膠囊） | Pulse 2 | 4 | 10 | 上行兩音（完全五度） | 明確的正回饋 |
| `powerup`（按 B 啟用） | **Pulse 1 + 2** | 6 | 20 | 上行琶音 4 音 | 搶主旋律 20 幀是值得的 |
| `explode`（敵人爆炸） | Noise | 5 | 14 | 長模式 + 音量下滑 | 借鼓 |
| `bossHit` | Noise | 5 | 8 | 長模式低頻 | 借鼓 |
| `die`（自機死亡） | **全部** | 9（最高） | 60 | 下行半音階 + 雜訊爆 | **音樂停止**，死亡演出結束後才重啟 |
| `extend`（加命） | Pulse 1 + 2 | 8 | 40 | 上行琶音 8 音 | 音樂 duck（音量減半） |
| `bossWarn`（魔王警報） | Pulse 1 | 8 | 90 | 兩音交替（大二度） | **音樂切到 boss 曲**之前的空檔播 |

- [推論] 射擊遊戲的特殊問題是**射擊音效太頻繁**。若每發子彈都搶 Pulse 2，音樂會變成篩子。解法三選一：① 射擊音效限流（每 4 幀最多一次）② 射擊音效改用 Noise 的極短脈衝 ③ 射擊音效音量壓到 6~8（不搶滿）。**本專案建議 ① + ③ 並用。**
- [推論] `die` 是唯一應該**完全停止音樂**的音效。其他都只是暫借一軌。

| 項 | 規格 |
|---|---|

```
232 ║ ▲▲                                              SHIELD ███     ║  列 29
239 ╚════════════════════════════════════════════════════════════════╝
```

#### 逐列磚配置（32 格 / 列）

| 列 | 格 0-3 | 格 4-11 | 格 12-15 | 格 16-23 | 格 24-31 |
|---|---|---|---|---|---|
| **26** | `1P ` | 分數 7 位 + 空白 | `HI  ` | 最高分 7 位 + 空白 | `STAGE 1` |
| **27** | 能量表項目（縮寫版，見下） | | | | |
| **28** | 能量表底線（每項一段 `───`，目前格位換成 `███`） | | | | |
| **29** | `▲▲` 剩餘船數（最多 4 個圖示） | 空白 | 空白 | 空白 | `SHIELD ███`（有護盾時） |

- [推論] 32 格放不下 `SPEED MISSILE DOUBLE LASER OPTION ?` 六個完整英文字，**改用縮寫**：`SPD  MSL  DBL  LSR  OPT  ?` = 26 格，左右各留 3 格 ✓。

```
格:  0123456789.....................31
列27 ░░░SPD  MSL  DBL  LSR  OPT  ?░░░
列28 ░░░───  ───  ───  ───  ───  ─░░░   ← 目前格位的底線換成 █
```

#### 能量表反白的實作

| 方式 | 做法 | 成本 | 選用 |
|---|---|---|---|
| 換磚 | 準備「正常」與「反白」兩組字型磚（52 塊 → 104 塊） | CHR 吃掉一半；每次切換寫 ~8 byte | ✗ |
| **換屬性** | 能量表的 6 個項目各佔一個 16×16 屬性格區；切換時只改屬性表 **1~2 byte** | 極省；但字的位置要對齊 16px 邊界 | **✓ 採用** |
| 換底線磚 | 只有列 28 的底線換成實心條 | 每次 ~6 byte | ✓ 備選（視覺更明顯） |

- [推論] **建議兩者並用**：屬性換色（字變亮黃）+ 列 28 的底線從 `─` 換成 `█`。玩家在戰鬥中掃一眼就能看到。
- 欄位對齊（列 27，格 0..31）：留白(0-2) `SPD`(3-5) 留白(6-7) `MSL`(8-10) 留白(11-12) `DBL`(13-15) 留白(16-17) `LSR`(18-20) 留白(21-22) `OPT`(23-25) 留白(26-27) `?`(28) 留白(29-31)。每項起點都落在偶數格 ⇒ 可用 16×16 屬性格區換色 ✓。

#### HUD 更新時機與成本

| 元素 | 何時更新 | byte |

| 護盾格 | 護盾變化時 | 3 |
| STAGE | 過關時 | 1 |
| **每幀平均** | | **< 2 byte** ✓ |
